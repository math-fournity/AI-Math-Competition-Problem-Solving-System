# 认知闭包与 checklist 影响分析铁律

**硬约束**：用户提出需求时、AI 工作完成进行 git 提交前，必须分析本次需求/改动是否涉及对认知闭包（`docs/sop/SYSTEM_CLOSURE.md`）的更新，以及对 `checklist/` 目录中内容的更新或添加。

## 两个必须检查的资产

| 资产 | 路径 | 作用 | 过期的后果 |
|---|---|---|---|
| 认知闭包 | `docs/sop/SYSTEM_CLOSURE.md` | AI 每步 SOP 执行前注入的"系统正常工作时是怎样的"知识底座——§1使命/§2架构/§3生命周期/§4模块职责/§5数据产出/§6判定框架/§7铁律索引 | AI 按过时知识推理"系统是否正常"= 误判 |
| checklist 目录 | `checklist/` | 检查需求点的索引（MON-A/B/C/SELF/HARD/SESS/LAUNCH/DOC/AUDIT 等门类） | SOP 检查项与实际代码脱节= 检查失效 |

## 触发时机

### 时机1：用户提出需求时

收到用户需求后，在制定方案/开始执行**之前**，分析：

1. **认知闭包影响**——这个需求是否改变了系统的：
   - 使命/功能（§1）→ 新增/删除/改变了系统做的事？
   - 架构/数据流（§2）→ 新增/删除/改变了模块或数据流向？
   - 生命周期（§3）→ 改变了题目的状态流转/判定条件/终态？
   - 模块职责（§4）→ 新增/删除/改变了模块？模块的异常表现变了？
   - 数据产出（§5）→ 新增/删除/改变了产出文件/DB集合/字段/Redis key/配置参数/门闸？
   - 判定框架（§6）→ 改变了"正常工作"的标准？新增了检查项/正常标准/alert_type？
   - 铁律索引（§7）→ 新增/改变了硬约束？

2. **checklist 影响**——这个需求是否：
   - 新增了需要检查的需求点 → 应在 `checklist/` 新建对应 checkpoint
   - 改变了现有检查项的标准/方法 → 应更新对应 checkpoint 文件
   - 新增了 alert_type → 应在对应 MON 检查项中记录

### 时机2：AI 工作完成 git 提交前

在 `git commit` **之前**，对照本次改动的文件，分析：

1. **认知闭包是否需要同步更新**——逐项检查本次改动是否触及 §1-§7 的任何一项：
   - 改了 `src/continuation_config.py` 的常量 → §5 配置参数表/§3 判定条件
   - 改了 `src/continuation_launcher.py` 的判定逻辑 → §3 生命周期/§6 判定框架
   - 新增/删除了 `@gated` 门闸 → §5 门闸ID清单
   - 新增/删除了 `src/` 下的模块 → §2 架构图/§4 模块职责表
   - 改了 `src/monitor_continuation.py` 的 alert_type → §6 alert_type 清单
   - 新增了硬约束 → §7 铁律索引
   - 改了 Redis key 结构 → §5 Redis key 结构
   - 改了 DB 集合/字段 → §5 DB 集合

2. **checklist 是否需要更新或新建**——检查本次改动是否：
   - 新增了系统功能/检查能力 → 新建 checkpoint 文件
   - 改变了现有检查项的判定标准 → 更新对应 checkpoint
   - 新增了 alert_type → 更新对应 MON 检查项

## 分析输出格式

分析后必须输出明确结论，不能跳过：

```
=== 认知闭包与 checklist 影响分析 ===
认知闭包（SYSTEM_CLOSURE.md）：
  - [需更新] §X <章节名>：<具体什么变了>
  - [无需更新] 原因：<本次改动不触及认知闭包内容>
checklist/：
  - [需新建] <文件名>：<新建什么 checkpoint>
  - [需更新] <文件名>：<更新什么内容>
  - [无需更新] 原因：<本次改动不涉及检查需求点>
```

## 禁止

- 禁止跳过影响分析直接 commit
- 禁止"改了代码但认知闭包/checklist 不同步"——这会让下一个 SOP 循环的 AI 按过时知识推理
- 禁止"分析后不输出结论"——必须明确写出需更新/无需更新及原因
- 禁止"只分析认知闭包不分析 checklist"或反过来——两者都必须分析

## 为什么

认知闭包是 AI "时刻推理系统是否正常"的知识底座，checklist 是 SOP 检查项的索引。两者过时会导致：
- AI 按过时的"正常标准"判断 → 把异常当正常，或把正常当异常
- SOP 检查项与实际代码脱节 → 检查失效，问题漏检
- 跨 session 的 AI 认知不一致 → 每个 AI 对"系统应怎样工作"的理解不同

历史教训：`204f6b5` 在 §4 模块表补了3个模块但 §2 架构图没同步，导致内部自相矛盾；§7 铁律索引只6条而 SOP_OP 有14条，漏了"每轮SOP_01必查行为流水"这条016核心铁律。
