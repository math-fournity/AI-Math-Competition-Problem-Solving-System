# 认知闭包信任但不能盲信——冲突时时间比对+智能判定

**硬约束**：AI 不能完全信任认知闭包（`docs/sop/SYSTEM_CLOSURE.md`）的内容。当认知闭包的描述与系统实际代码/配置/提示词等目标文件出现冲突时，必须用时间比对定位差异来源，再用智能分析判定该更新谁——不能默认认知闭包对，也不能默认代码对。

## 为什么不能盲信

认知闭包是"系统正常工作时是怎样的"的知识底座，但它本质是**文档**——文档会过时。历史教训：
- `204f6b5` 在§4模块表补了3个模块但§2架构图没同步→内部自相矛盾
- §7铁律索引只6条而SOP_OP有14条→漏了016核心铁律"每轮SOP_01必查行为流水"
- 这些过期不是代码变了没更新文档，而是**文档自己内部不一致**

所以：认知闭包可能与代码不一致（代码变了文档没跟），也可能自身内部不一致（改了一处漏改另一处）。两种情况都要能发现。

## 冲突发现时的处理流程

### 步骤1：时间比对

当发现认知闭包的某项描述与目标文件（代码/配置/提示词/任何被引用的资产）实际内容冲突时：

```bash
# 认知闭包最后修改时间
git log -1 --format="%ci %H %s" -- docs/sop/SYSTEM_CLOSURE.md

# 目标文件最后修改时间（如某份代码）
git log -1 --format="%ci %H %s" -- src/continuation_launcher.py

# 也可看认知闭包某次修改之后，目标文件是否被改过
git log --oneline <closure_commit>..HEAD -- src/continuation_launcher.py
```

时间比对给出**差异来源的方向**：

| 时间关系 | 含义 | 倾向（非定论） |
|---|---|---|
| 认知闭包比目标文件新 | 闭包改了但目标文件没跟 | 可能目标文件需要更新以匹配闭包 |
| 目标文件比认知闭包新 | 目标文件改了但闭包没跟 | 可能闭包需要更新以匹配目标文件 |
| 两者时间接近且在同一commit | 同步改过但可能改漏了 | 可能是内部不一致，需细查 |

### 步骤2：智能判定（时间最新不等于内容最对）

**时间比对只给出方向线索，不给出最终结论。** 时间最新的不一定是对的——必须用智能分析判定：

#### 情况A：代码比闭包新 → 通常是闭包需更新，但要确认代码改对了

- 读代码的 commit message 和 diff，理解**为什么改**——是修bug、加功能、还是AI改错了？
- 如果改动有明确合理的原因（修bug/加功能/用户要求）→ **闭包需更新**以匹配代码
- 如果改动看起来不合理（AI改错了、误删、引入了不一致）→ **代码可能需要回退或修复**，闭包不用更新
- 判断"改对没有"的依据：commit message 的理由、改动是否符合系统设计、改动是否引入了新问题

#### 情况B：闭包比代码新 → 通常是代码需更新，但要确认闭包描述对

- 读闭包的 commit message 和 diff，理解**为什么改闭包**——是补漏、修正描述、还是AI写错了描述？
- 如果闭包改动是修正过时描述/补全缺失内容 → **代码需检查**是否确实与闭包新描述不符，若不符则代码需更新
- 如果闭包改动是AI写错了（描述了不存在的东西、与代码实际行为矛盾）→ **闭包需回退或修正**，代码不用动

#### 情况C：闭包内部不一致（§2与§4矛盾等）→ 纯文档问题

- 不涉及代码，直接以代码为事实源，修正闭包中与代码不符的那一处
- 历史教训：§4模块表补了3个模块但§2架构图没补——两处都该以代码为准

### 步骤3：输出判定结论

```
=== 认知闭包冲突判定 ===
冲突项：<闭包§X 描述> vs <目标文件:行 实际内容>
时间比对：
  闭包最后修改：<commit时间> <hash> <message>
  目标文件最后修改：<commit时间> <hash> <message>
  方向：<闭包更新/目标文件更新/同期>
智能判定：
  - [闭包需更新] 原因：<代码因X原因改了，闭包没跟，代码改动合理>
  - [代码需修复] 原因：<代码被AI改错，闭包描述才是对的>
  - [闭包内部不一致] 原因：<§X与§Y矛盾，以代码为准修正§X>
```

## 禁止

- 禁止默认"认知闭包一定对"——它是文档，会过时
- 禁止默认"代码一定对"——AI可能改错代码
- 禁止默认"时间最新的一定对"——时间只给方向，不给结论
- 禁止跳过智能判定直接按时间方向改——必须读commit message+diff理解改动原因
- 禁止发现冲突不输出判定结论——必须明确写出改谁、为什么

## 与 closure-checklist-impact-analysis rule 的关系

| rule | 触发时机 | 作用 |
|---|---|---|
| `closure-checklist-impact-analysis` | 需求提出时 + commit前 | 主动分析"本次改动是否涉及闭包/checklist更新"——**预防冲突** |
| 本 rule（`closure-trust-but-verify`） | 发现冲突时 | 被动判定"冲突时改闭包还是改代码"——**解决冲突** |

两者互补：前者防止"改了代码忘更新闭包"，后者处理"已经不一致了怎么办"。
