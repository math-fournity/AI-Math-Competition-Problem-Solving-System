## 一、用户原话（完整保留）

> 所以，我们会发现：你要认知包的交付包，存在什么组成部分？首先，论文一样的综述文档，这是认知包的核心，也就是N。其次，还要有论证文档。其实此刻，关键点就落到了论证文档上。因为上下文的压力来了。认知动力过程中的一个认知包，也就是一份综述文档，给出来是简单的，但是完整的论证给出来，并不简单，因为AI上下文有限的原因，如果必须"同时"看到repo元素A和B，才能够确定A和B应该进入此次认知包，而单独看到任何一个都不会产生这种认知，那么A和B凭什么一定会在一个上下文受限的AI在按照目录递归遍历、同时使用了trace进行遍历的过程中，必然会同时出现呢？

## 二、AI 的理解

### 2.1 认知包交付包的两个组成部分

用户定义了认知包交付包的结构：

1. **综述文档**（N，面相3，见 011）——认知包的核心，"这个工作包需要这些认知，因为……"。是**结论**。
2. **论证文档**——为什么这些元素应该进入认知包的完整论证。是**推理过程**。

两者缺一不可：
- 没有论证的综述 = 断言（"N 就是这些"但不证明为什么）
- 没有综述的论证 = 过程记录（记了推理但没产出结论）

综述文档的形态已在 011 定义（面相3：正文带引用 ID 论述 + 参考文献序号化 xpath 列表）。论证文档是 011 未覆盖的新组成部分。

### 2.2 论证文档为什么是关键点

用户说"关键点落到了论证文档上"——因为综述文档给出来是简单的（列出 N 的成员 + 论述关系），但**完整的论证给出来并不简单**。

论证的困难来自一个根本条件：**某些纳入决策需要同时看到多个元素**。

"如果必须同时看到 A 和 B，才能确定 A 和 B 都应该进入认知包，而单独看到任何一个都不会产生这种认知"——这是**协同可见性要求**。A 和 B 各自看起来都可能无关，只有同时出现时，它们之间的关系才显现，纳入决策才成立。

### 2.3 用户的核心质问

"A 和 B 凭什么一定会在一个上下文受限的 AI 在按照目录递归遍历、同时使用了 trace 进行遍历的过程中，必然会同时出现呢？"

答案是：**不保证。** 没有任何遍历方法能保证需要协同可见的元素对一定在同一时刻都在上下文中。原因：

1. **目录递归遍历是序贯的**——遍历到 A 时 B 还没加载，遍历到 B 时 A 可能已被压缩出上下文
2. **trace 遍历也是序贯的**——沿 trace 链从 A 追到 B，但追到 B 时 A 的细节可能已被压缩
3. **上下文窗口是有限的**——即使 A 和 B 都被加载过，它们不一定同时"活着"在上下文中
4. **遍历顺序影响可见性**——如果先遍历 A 所在目录，再遍历 B 所在目录，两者在时间上分离

### 2.4 问题的本质：已记录关系 vs 未发现关系

这其实是**已记录关系 vs 未发现关系**的分界：

- **如果 trace 已经记录了 A 和 B 的关系**（如 A depends-on B）→ AI 不需要同时看到 A 和 B，只需要读 trace 记录。trace 是**外化的关系记忆**，不需要协同可见。
- **如果 A 和 B 的关系尚未记录在 trace 中** → AI 必须同时看到 A 和 B 才能**发现**这个关系。这需要协同可见，而协同可见不被保证。

所以问题的本质是：**认知闭包的形成过程本身需要发现 trace 中未记录的关系，而发现需要协同可见，协同可见不被上下文窗口保证。**

### 2.5 和 010 的鸡生蛋问题

这和 010 的 trace 幂等形成了一个鸡生蛋问题：

- trace 幂等（所有实际关系都被记录）→ 认知闭包形成不需要协同可见（trace 已经告诉你关系）
- 但 trace 幂等本身需要发现所有实际关系 → 发现需要协同可见 → 协同可见不被保证

**你用 trace 来补偿上下文窗口的局限，但 trace 的完备性本身又受限于上下文窗口的局限。**

这是一个循环：
```
上下文窗口有限 → 需要 trace 外化关系记忆
  ↓
trace 幂等需要发现所有关系 → 发现需要协同可见 → 协同可见受上下文窗口限制
  ↓
回到起点：上下文窗口有限
```

### 2.6 协同可见性的双重困难

用户问题的真正尖锐之处：**协同可见性要求不仅关乎"同时出现"，还关乎"同时出现才能知道该记录什么"**。

- 如果 A 单独看起来无关，AI 在只看到 A 时会在论证文档中记录关于 A 的什么？
- 如果 A 的相关性只有在和 B 一起时才显现，那 AI 在只看到 A 时可能根本不会记录 A——它不知道 A 重要。

这是比"同时出现"更深的困难：**"同时出现才能知道该记录什么"**。即使 AI 在 session 1 访问了 A，它可能不会在论证文档中记录 A 的任何有意义内容，因为 A 的意义需要 B 来显现。

## 三、论证文档的结构与角色

### 3.1 论证文档记录什么

论证文档记录每个纳入/排除决策的推理过程：

对每个纳入决策（"X 进入认知包"）：
- **X 是什么**——xpath + 一句话描述
- **为什么纳入**——基于什么关系/什么发现
- **证据来源**——trace 记录的关系 / AI 发现的关系 / 用户的明确指示
- **协同可见性情况**——这个决策是否需要协同可见？如果需要，相关元素是否同时出现过？

对每个排除决策（"Y 不进入认知包"）：
- **Y 是什么**——xpath + 一句话描述
- **为什么排除**——基于什么判断它和任务无关
- **协同可见性情况**——排除决策是否可能因为协同元素未同时出现而误判？

对每个**无法验证的协同关系**：
- **A 和 B 的关系**——AI 怀疑 A 和 B 有关系，但未能同时看到两者来确认
- **状态**——"待验证"（显式标记，不是隐性遗漏）

### 3.2 论证文档的双重角色

论证文档既是问题的一部分，也是问题的部分解法：

**作为问题的一部分**：论证文档需要记录"A 和 B 一起进入认知包，因为它们有 X 关系"——但写出这个论证的前提是 AI 曾经同时看到了 A 和 B。如果协同可见从未发生，这个论证写不出来。

**作为部分解法**：论证文档是**持久化的中间状态**——session 1 看到 A 时记录关于 A 的发现，session 2 看到 B 时可以读取 session 1 关于 A 的记录，即使 A 不在 session 2 的上下文中。论证文档让"跨 session 的协同可见"成为可能——A 和 B 不需要在同一个 session 的上下文中同时出现，只需要 A 的记录（论证文档中）和 B（当前上下文中）同时出现。

### 3.3 跨 session 协同可见的限制

但 §2.6 指出了更深的问题：**如果 A 单独看起来无关，session 1 的 AI 不知道该在论证文档中记录关于 A 的什么。** 跨 session 协同可见只能解决"A 的记录和 B 同时出现"，但不能解决"A 的记录中是否有足够信息让 B 的 session 判断 A 相关"。

如果 session 1 只记录了"A 是一个处理 rate limit 的函数"（因为只看到 A，不知道它和 B 的关系），session 2 看到 B（一个 stall 检测函数）时，能否从"A 处理 rate limit"判断出"A 应该和 B 一起进入认知包"？这依赖 AI 的推理能力——能否从两个元素的独立描述推断出它们可能的协同关系。

这引出一个设计要求：**论证文档对每个被访问的元素，不只是记录"看起来是否相关"，还要记录足够多的特征，让后续 session 能做跨 session 推理。** 详见 §四 方向 1（激进记录）。

## 四、可能的方向

### 方向1：激进记录

目录遍历时，每个被访问的元素都记录一个"已访问标记"和"初步观察"，不管它看起来是否相关。这样即使 session 1 不知道 A 重要，至少记录了"A 被访问过，初步观察是……"。session 2 看到 B 时可以回看 A 的记录。

**优点**：不遗漏任何被访问过的元素，为跨 session 协同可见提供最大信息量。
**缺点**：记录量大，论证文档膨胀。可能记录大量最终无关的元素。
**缓解**：记录是有结构的（xpath + 一句话特征 + 已访问标记），不是全文复制，量可控。

**关键设计**：初步观察不只记"看起来是否相关"，还要记**元素的特征**（做什么的、依赖什么、被什么依赖）。这些特征是后续 session 做跨 session 推理的原料。即使 session 1 不知道 A 和 B 的关系，记录了 A 的特征（"处理 rate limit"），session 2 看到 B（"检测 stall"）时可能推断出"A 影响 rate limit → rate limit 影响 stall → A 和 B 可能相关"。

### 方向2：trace 作为关系的外化记忆

如果 trace 已经记录了 A-B 关系，协同可见就不需要了。问题转化为"如何让 trace 尽可能完备"，这又回到 010 的 trace 幂等维护。但这是一个渐进过程——每次认知包形成时发现的未记录关系，应该回写到 trace 中。

**优点**：trace 记录的关系不需要协同可见，直接可用。
**缺点**：trace 的初始完备性无法保证（鸡生蛋问题）。只能渐进改善，不能一步到位。
**关键**：认知包形成过程中发现的未记录关系，**必须回写 trace**——这是 trace 幂等维护的新来源（除了代码/文档变更时的同步，还有认知包形成时的关系发现回写）。

### 方向3：多 session 的交叉验证

不依赖单次遍历发现所有协同关系。session 1 从 A 出发遍历，session 2 从 B 出发遍历，两次遍历的论证文档交叉对比，发现 A-B 关系。

**优点**：不同起点可能覆盖不同的关系网络，交叉对比能发现单次遍历遗漏的关系。
**缺点**：需要多次 session，成本高。交叉对比本身也可能需要协同可见（对比两份论证文档时，A 的记录和 B 的记录需要同时出现）。
**关键**：这和 008 的认知动力过程一致——多代认知包的迭代逼近。交叉验证是多代迭代的一种形态：不同代从不同起点出发，代际对比发现遗漏。

### 方向4：接受不完备性，显式声明

承认认知闭包可能不完备（某些需要协同可见才能发现的关系被遗漏），但在论证文档中显式记录"哪些协同关系我无法验证"（因为相关元素未同时出现）。这把隐性缺陷变成显性声明，至少可审计。

**优点**：诚实，不假装完备。显式声明让下游（执行 AI 或审计 AI）知道哪里可能有遗漏，可以针对性地补充验证。
**缺点**：不完备性被接受而非解决。显式声明的"待验证关系"可能积累太多，失去实用价值。
**关键**：这和 006 §3.3 问题A（AI 自觉闭包不可靠）一致——AI 不知道自己缺什么。但方向4 要求 AI 至少记录"我怀疑但无法验证的"，这比完全不知道好。

### 方向综合

四个方向不互斥，可以组合：
- **方向2（trace 回写）**是基础——每次发现未记录关系都回写，渐进改善 trace 完备性
- **方向1（激进记录）**是遍历策略——遍历时多记录特征，为跨 session 推理提供原料
- **方向3（交叉验证）**是迭代策略——不同代从不同起点出发，交叉发现遗漏
- **方向4（显式声明）**是兜底——无法验证的显式标记，不假装完备

## 五、对 006-011 的影响

### 5.1 对 008（认知动力过程）

008 的认知包 n[x] 只包含综述文档（面相3）。本文档指出认知包交付包还应包含**论证文档**。008 的持久化机制需要扩展——不只持久化综述文档（n[x] 的候选集），还要持久化论证文档（每个纳入/排除决策的推理过程 + 无法验证的协同关系声明）。

### 5.3 对 011（认知闭包与认知包的文档形态）

011 的面相3 不变，但认知包交付包的结构扩展为两部分。

### 5.4 对 009（孤岛认知危机）

009 的孤岛检测依赖 trace 关系图。但本文档指出，即使目录遍历覆盖了所有岛屿，岛屿内部的某些关系可能因为协同可见性限制而未被发现。这是 009 之外的另一种"隐性孤岛"——不是拓扑上的 disconnected components，而是**认知上的未被发现的连接**。

## 六、论证文档与综述文档的关系

### 6.1 类比：数学论文的证明 vs 定理

- 综述文档（面相3）= 定理 + 定理的陈述（N 是什么 + 关系论述）
- 论证文档 = 证明（为什么 N 是这些 + 每个纳入/排除决策的推理）

数学论文中定理和证明在一起，但逻辑上分离——定理是结论，证明是论证。认知包交付包同理：综述文档是结论，论证文档是推理。两者在同一交付包中，但是不同的文档。

### 6.2 读者不同

- **综述文档的读者**：执行 AI——它需要知道 N 是什么、元素间什么关系，据此工作
- **论证文档的读者**：审计 AI / 下一代的探索 AI——它需要知道 N 为什么是这些、哪些决策可能有问题、哪些协同关系待验证

### 6.3 演化不同

- **综述文档**：随认知动力过程迭代，代际 diff 体现 n[x] 的演化（011 §4.3）
- **论证文档**：累积式增长——每代探索新增发现和验证，不删除旧记录（旧的纳入/排除决策是审计 trail，不能删）。待验证关系被验证后标记为"已验证"，但不删除原始的"待验证"记录

## 七、开放问题

1. **论证文档的具体格式**——markdown 按元素分节？还是 CSV 结构化（每个纳入/排除决策一行）？可能需要两者：markdown 存叙述性论证，CSV 存结构化的决策清单（可 diff、可统计待验证关系数量）。
2. **激进记录的粒度**——"初步观察"记多详细？一句话特征？还是一段话描述？记太详细等于面相2（纯摘录），记太简略又不足以支撑跨 session 推理。
3. **trace 回写的触发条件**——认知包形成过程中，什么样的"发现"应该回写 trace？AI 推断的"可能关系"还是确认的"实际关系"？如果回写推断关系，可能污染 trace with 噪声。
4. **交叉验证的协调机制**——方向3 说不同 session 从不同起点出发。谁决定起点？如何确保不同起点覆盖不同岛屿？需要一种"起点分配"机制。
5. **待验证关系的处理流程**——方向4 说显式声明待验证关系。后续如何处理？专门的验证 session？还是在后续认知包迭代中顺便验证？
6. **论证文档和 trace 回写的协作**——发现未记录关系时，是先写论证文档再回写 trace，还是先回写 trace 再在论证文档中引用？顺序影响一致性。
