## 正文

### 一、体系缘起：从"工作包自包含"到"认知闭包"

现有三层认知体系（AGENTS.md → README.md → 看法文件 → 具体文档/代码）解决了"repo 太大无法全加载"的问题，让 AI 只加载必要认知[1]。在此基础上，akash 流程的阶段3要求工作包自包含——README.md 列出执行 AI 需要的 View 和具体文档[2]。workflow.md 进一步定义了方案"完备"的含义：通过 trace.csv 追溯链，认知等价于"整个 repo 所有元素都放入上下文"[3]。

但现有体系停留在"列出要加载什么"，没有把这件事提升为一个有名字、有判定标准、可审计的认知产物。006 提出了"认知闭包"概念来填补这个空白：针对某具体任务，从 repo 中提取的完备且不冗余的认知集合，每条认知带 xpath 引用，构成可审计的闭合单元[4]。这个概念由两个系统协作形成——三层体系负责"启动"（导航和发现），trace.csv 负责"封闭"（划定精确边界、保证完备且不冗余），两者可交替迭代而非严格线性[4][5]。

006 最关键的贡献是概念层级提升（§2.8）：认知闭包不是工作包拆解阶段的一个步骤，而是贯穿所有人机协同开发阶段的底层必要条件。read/akash/workflow/make-plan 表面是不同 skill，底层都是认知闭包形成机制的不同环节——read 是启动算子，read-sync 是基础设施维护，make-plan 阶段4是显式步骤，akash 保障每个阶段先形成闭包再执行[4]。闭包形成前不能做产出性思考，但闭包形成本身需要探索性思考[4]。这对 AI 比对人更重要——人的认知获取是持续的，AI 的上下文是固定窗口，产出开始后补认知成本极高[4]。

006 还包含一次自我指涉验证（§三）：AI 在论述"认知闭包要完备"时，自己的闭包并不完备——只看了 read/read-sync 的 SKILL.md 一句话触发器，没跟进加载完整内容文档。补加载后做出三个实质修正[4]。这个案例佐证了两个深层问题：AI 的"自觉闭包"不可靠（不知道自己缺什么），一句话触发器是闭包漏洞的高发点[4]。

### 二、单次获取的工程优化：最小 M 问题

007 把认知闭包的获取形式化为一个优化问题：`min |M| s.t. N ⊆ M`——在保证 N 完整出现前提下，实际上下文 M 越小越好[6]。这里 N 是闭包内容（006 定义），M 是实际进入 AI 上下文的内容。007 区分了两个独立问题：从 M 中提炼 N（AI 的理解能力，在小 M 中可靠）和获取最小的 M（何种前置索引体系能让我们得到所有 M 中最小的那个）[6]。

M 大于 N 的冗余来自三个层面，按贡献从大到小：加载粒度冗余（需要某函数但加载了整个文件）、导航开销冗余（加载整个 README/看法文件只为找几个条目）、探索性冗余（边界不确定时保险性多加载）[6]。针对这三个冗余源，007 列出五种获取策略，从全量加载到 trace+xpath 精确加载（理论最优），并指出务实路径：先实现策略5（trace 缩小范围 + AI 提炼，低工程成本），再向策略4（trace 闭包遍历 + xpath 精确加载，理论最优）演进[6]。

007 的关键洞察是：trace 的真正价值不是精确计算 N，而是把 M 从 AI 看不过来的规模（GB 级）缩小到 AI 看得过来且能可靠提炼的规模（KB 级）[6]。这和 006 §3.3 问题A（AI 自觉闭包不可靠）不矛盾——问题A 说的是 AI 在大 M 中提炼 N 不可靠，但在小 M 中提炼是可靠的[6]。007 还识别了鸡生蛋问题：起点明确则 M 小，起点模糊需要导航开销确定起点——akash 阶段1需求分析的价值就是把模糊任务映射到 trace 图上的明确起点[6]。

### 三、复杂 N 的跨 session 迭代逼近

008 指出 007 有一个隐含假设：N 可在一次 session 中从 M 里提炼出来（单次快照模型）。但复杂工作包挑战了这个假设——发现 N 需要什么本身需要探索而探索消耗上下文，有些"需要什么"只有加载了另一些内容后才显现（序贯依赖），上下文窗口限制了单次探索深度[7]。

因此 008 提出迭代逼近模型：N 不是一次提炼出来的，是多代认知包 n[x] 逐代逼近出来的[7]。这里最关键的区分是 n[x] 不是 M——n[x] 是关于"N 包含什么"的带证据候选集（假设），M 是进入上下文的原始内容（冗余散乱的）[7]。认知动力过程不是"多加载几次"（那是多次获取 M），而是"多代假设的修正"[7]。

008 强调非单调性是精髓而非缺陷——成员在 n1 到 N 的过程中进进出出，反映认知逼近真相的过程[7]。这要求每一代必须记录纳入/排除理由作为审计 trail[7]。收敛判据是 n[x] = n[x+1]（一代探索后没有加入也没有移除）[7]。认知包需要持久化（cognitive-pack.md），让下一个 session 从 n[x] 而不是从零开始，这和 trace.csv 选择 CSV 而非 SQLite 的设计哲学一致——git 可逐行 diff，保留完整演化历史[7][8]。

### 四、孤岛认知危机：008 的根本性缺陷修正

009 识别了 008 的一个根本性缺陷：收敛判据 n[x]=n[x+1] 只能保证连通分量内的完备性。如果 trace 关系图有多个连通分量（岛屿），从起点所在岛屿出发永远到不了其他岛屿，收敛判据照样满足但 N 不完备——这是"收敛于错误终点"，不是收敛太慢[9]。

岛屿的来源有四种：trace 关系缺失、关系类型不被遍历、目录结构天然分区、新资产未录入 trace[9]。009 的解法精妙之处在于用目录结构作为不依赖 trace 的分类学——目录结构是事实层（物理存在，不依赖维护质量），即使 trace 完全坏了，目录结构仍然把 repo 分成了可遍历的岛屿[9]。

009 最精髓的洞察是"套娃"——孤岛认知危机不是仅仅在最高层能看到，在任何一个套娃层次都可能出现[9]。如果某层子目录缺 README，该层之下的所有内容对该层来说都是孤岛。这要求 README 是递归全覆盖的——每个子目录都有 README，每个 README 索引直接子目录和直接文件，形成完整入口树[9]。这本质上是把三层体系从顶层推广到递归：AGENTS.md→每层README，顶层分类法→每层子目录分类法，看法文件→每层文档索引[9]。

对 008 的修正是增加阶段0（岛屿遍历）——在闭包迭代之前，先递归遍历所有子目录的 README，确保 n1 候选集覆盖所有岛屿[9]。阶段0和阶段1+（闭包迭代）可以交替，和 006 §2.3 修正后的"启动与封闭可交替迭代"一致[9]。009 还要求 trace_verify.py 升级：从检测孤立节点升级到检测孤立连通分量[9]。

### 五、trace 幂等的实用边界：基础设施定义

006-009 都假设 trace 幂等，但都没说清幂等的边界。010 质疑了这个共同前提并给出精确定义[10]。用户提出两个关键问题：trace 幂等的精确含义是什么（所有实际上存在的关系都被记录），以及什么算 trace 节点（实用 vs 形式）[10]。

010 最重要的澄清是：trace 幂等不是"所有可追溯的都追溯"的无限制幂等，而是在实用粒度上的幂等[10]。粒度决策原则是"这个粒度上的关系，对理解和工作有意义吗"——函数级有意义（改哪个函数影响什么），行级通常没意义（改第23行和改第24行没区别）；DB 表级有意义，DB 记录级通常没意义[10]。010 给出了三个判定维度：影响性、可定位性、独立身份——三者都有意义则追溯，都无意义则不追溯，混合则按例外处理[10]。

010 定义了幂等的两层含义：层1关系完备性（所有实际关系都被记录）AND 层2粒度合理性（在合理粒度上追溯）[10]。幂等的实用价值检验是"query 一个 checkpoint 能不能得到它的完整关系图"——本次事实层核对验证了这一点：`trace.py query checkpoint MON-A1` 返回了 MON-A1 的完整关系（implements/specified-by/part-of/changed-in），证明幂等在实用粒度上成立[10][11]。010 是 006-009 的基础设施定义——四篇都假设 trace 幂等，010 定义了这个边界，没有 010，006-009 的"依赖 trace 幂等"是悬空的[10]。

### 六、文档形态：三种面相与综述论文体例

011 回答了 006 §2.9 开放问题 #4（闭包文档的模板）。核心洞察是认知闭包的本质是一个特殊的 view——不是 repo 中已有的视角，而是为某个具体工作包临时构建的跨视角 view[12]。关键澄清是认知包 n[x]（008 的迭代候选集）和认知闭包 N（收敛后）是同一个东西的不同代，共用同一文档形态[12]。

011 定义了三种面相（同一闭包的三个抽象层级）：面相1（纯索引，xpath列表，闭包骨架）、面相2（纯摘录，直接复制内容，闭包肉）、面相3（综述论文，正文带引用ID论述+参考文献序号化xpath列表，骨架+肉+关系论述）[12]。面相3 是唯一同时满足"是认知/可审计/不过大/可验证/表达关系"五项要求的面相[12]。

面相3 的结构精确化为学术论文体例：正文是带引用ID的论述（不是复制），正文后是序号化xpath参考文献列表[12]。对 008 的关键意义是从 n[x] 到 N 的演化就是面相3文档的代际 diff——xpath 进出体现为参考文献列表变化，论述修正体现为正文变化，认知动力过程的持久化机制就是一份面相3文档的 git 版本历史[12]。本文档就是面相3的一个实例——正文论述七篇文档的递进关系，参考文献列出所有被引用的 xpath。

### 七、协同可见性困境：认知闭包体系的最后一个困境

012 识别了认知闭包体系的最后一个困境。认知包交付包应包含两部分：综述文档（N，面相3，结论）和论证文档（推理过程）[13]。关键困难落在论证文档上——某些纳入决策需要同时看到 A 和 B 才能确定它们都该进入认知包，单独看任何一个都不会产生这种认知，这是协同可见性要求[13]。

用户的尖锐质问是：A 和 B 凭什么一定会在一个上下文受限的 AI 在序贯遍历中同时出现？答案是不保证——目录递归遍历是序贯的，trace 遍历也是序贯的，上下文窗口有限，遍历顺序影响可见性[13]。问题本质是已记录关系 vs 未发现关系的分界：trace 已记录的关系不需要协同可见（外化记忆），未记录的关系需要协同可见来发现，而协同可见不被保证[13]。

这和 010 形成鸡生蛋问题：trace 幂等需要发现所有关系 → 发现需要协同可见 → 协同可见受上下文窗口限制 → 回到起点[13]。更深的困难是"同时出现才能知道该记录什么"——A 单独看起来无关时，session 1 不知道该记录 A 的什么[13]。012 给出四个可组合的方向：激进记录（遍历时多记特征为跨 session 推理提供原料）、trace 回写（认知包形成中发现未记录关系必须回写 trace，这是 trace 幂等维护的新来源）、交叉验证（不同 session 从不同起点出发代际对比）、显式声明（无法验证的协同关系显式标记"待验证"）[13]。012 还补充了 008 的收敛判据：不只"参考文献列表不再变化"，还要"论证文档中没有待验证的协同关系"[13]。

### 八、体系的整体结构

七篇文档构成一个递进体系，每篇解决上一步的问题并留下新的开放问题：

006 定义 N（认知闭包是什么）→ 留下"如何获取 N"的开放问题
007 优化单次获取 M（最小 M 问题）→ 留下"N 不可一次确定怎么办"
008 处理复杂 N 的迭代逼近（n1→n2→…→N）→ 留下"收敛于错误终点"的根本性缺陷
009 修正 008 的孤岛缺陷（递归 README 遍历）→ 假设 trace 幂等但没说清边界
010 定义 trace 幂等的实用边界（基础设施定义）→ 留下"闭包和认知包的文档形态是什么"
011 定义文档形态（面相3综述论文）→ 留下"论证文档和协同可见性"
012 识别协同可见性困境并给出四个方向 → 体系的当前前沿

七篇文档共同依赖的基础设施是 trace.csv 的幂等性（010 定义其边界）和三层认知体系（006 定义其角色转变）。所有文档都标注"待落地为工具/workflow.md 新章节"，目前均留在 dev-docs 作为工作痕迹。落地的关键方向是：闭包遍历算法（007 §八）、xpath 行范围映射工具（007 §八）、递归 README 规范（009 §六）、trace_verify.py 升级检测孤立连通分量（009 §六）、面相3 作为工作包 README.md 模板（011 §八）、认知包交付包=面相3+论证文档（012 §八）。
