## 一、用户原话（完整保留）

> 我们设计了akash，设计了read、read-sync、trace，但是我总觉得，存在这样一个阶段，就是在我们形成真正的单一任务指导手册的时候，也就是形成工作包的时候，我们需要把这个工作包需要的所有的认知，从repo中提取出来——不多不少。而且必须是可审计的，也就是说，这些认知来源于哪里？必须像一篇综述论文一样，带着引用，其实就是我们在trace中用的xpath的id，比如说是行号。我们要在某个基础上，或者说起点上，形成事关某事的"认知闭包"，这个概念，非常重要，因为这个认知闭包，是靠三层体系启动的，是靠trace封闭的。

## 二、AI 的理解

### 2.1 这个概念在现有体系中的位置

用户描述的"认知闭包"不是一个新的独立阶段，而是对**阶段3（工作包拆解）**中"工作包自包含"这一要求的精确化和升华。

现有体系（akash 5 阶段 + workflow + make-plan）已经说了：

- 工作包是自包含的——README.md 列出执行 AI 需要的 View（看法文件）和具体文档/代码（workflow.md §4 "工作包自包含设计"、akash.md 阶段3）
- 方案"完备"= 通过 trace.csv 追溯链，认知等价于"整个 repo 所有元素都放入上下文"（workflow.md §4、§5 阶段2）

但现有体系停留在"列出要加载什么"，没有把这件事提升为一个**有名字的、有判定标准的、可审计的认知产物**。"认知闭包"就是给这件事命名、定标准、定形态。

### 2.2 "认知闭包"的核心定义

**认知闭包** = 针对某一个具体任务（工作包），从整个 repo 中提取出的、完备且不冗余的认知集合，其中每一份认知都带着它在 repo 中的精确出处（xpath id），整体构成一个可审计的、闭合的认知单元。

拆开看四个关键词：

1. **完备且不冗余（不多不少）**
   - "不少" = 完备性。执行这个工作包所需的全部认知都在里面，不会执行到一半发现"还需要某个上下文但闭包里没有"。
   - "不多" = 极小性。闭包里没有和这个工作包无关的认知。不把整个 repo 塞进来，也不凭感觉多塞"可能有用"的东西。
   - 完备性和极小性同时成立，才叫"闭包"——边界是精确的，不是模糊的"相关内容"。

2. **可审计（带着引用，像综述论文）**
   - 闭包里每一份认知都标注它来自 repo 的哪个精确位置——这就是 trace 的 xpath id：`path::function`、`path#section`、`path#section>subsection`，乃至行号。
   - 类比综述论文：综述不是凭空写观点，而是每个论断都引一篇文献。认知闭包不是凭空列"你需要了解这些"，而是每条认知都引一个 repo 里的 xpath。
   - 可审计的含义：任何人（或下一个 AI）拿到这个闭包，能逐条回溯——"你说做这个工作包需要懂 X，X 在 repo 的哪里？"——闭包能回答，且回答精确到函数/章节/行。

3. **在某个起点上形成**
   - "起点"= 工作包的目标/任务定义本身（要做什么、验收标准是什么）。
   - 闭包不是从"整个 repo"出发去筛，而是从"这个任务需要什么"出发去追溯。起点是任务，终点是闭包边界。

4. **事关某事**
   - "某事"= 这个工作包要解决的具体问题。闭包是"关于这件事"的闭包，不是"关于这个项目"的索引。

### 2.3 "靠三层体系启动，靠 trace 封闭"——这是最关键的一句

用户用"启动"和"封闭"两个词，精确描述了认知闭包的形成机制是**两个不同的系统协作，各管一端**：

**三层体系（AGENTS.md → README.md → 看法文件 → 具体文档/代码）负责"启动"——即发现和导航。**

- 三层体系解决的是"repo 这么大，我怎么找到和这个任务相关的认知在哪"。
- 它是一个**导航/发现机制**：从铁律知道行为约束，从分类法索引判断需要哪种视角，从看法文件找到具体文档/代码。
- "启动"的含义：三层体系让 AI 能够**进入** repo、**定位**到相关区域、**开始**提取认知。它是闭包形成的入口和寻路系统。
- 但三层体系本身**不保证边界精确**——它给你"相关的认知"，但可能多（视角重叠、看法文件索引了多余内容）也可能少（看法文件没覆盖到的孤立资产）。三层体系是"必要不充分"的。

**trace.csv 负责封闭——即划定精确边界、保证完备且不冗余。**

- trace 解决的是"我怎么确定我提取的认知恰好是完备且不冗余的，不多不少"。
- 它是一个**追溯/闭合机制**：从工作包的任务定义出发，沿 trace 的有向关系图做闭包遍历（`trace.py trace` / `query` / `query-prefix`），所有可达的资产构成闭包的精确成员。
- "封闭"的含义：trace 的追溯链是**数学意义上的闭包运算**——从一个起点出发，沿关系图遍历，所有可达节点构成一个闭合集合。遍历完了，边界就确定了，没有遗漏（可达的都进了）也没有多余（不可达的都不进）。
- trace 还提供**可审计性**——每条追溯路径上的关系都带 xpath id 和 commit id，闭包里每个成员都能说清"我是被哪条关系从起点带进来的"。

**两者协作的完整图景**（注：本图景在 §四 自我指涉验证后做了修正，启动与封闭可交替迭代，不是严格线性）：

```
任务定义（起点）
  ↓
三层体系启动：导航到 repo 中和任务相关的区域
  ↓ （发现候选认知，但边界尚不精确）
  ↓ （过程中可回溯：发现不够→回 README.md 加载其他看法文件→再深入）
trace 封闭：从起点沿追溯链做闭包遍历
  ↓ （精确划定边界：可达 = 闭包成员）
  ↓ （若遍历发现闭包内有资产未被任何看法文件索引→回溯启动补看法文件）
认知闭包形成：完备且不冗余的认知集合 + 每条的 xpath 引用
  ↓
输出：工作包的"单一任务指导手册"= 认知闭包的可审计文档
```

**启动与封闭可交替迭代**——不是严格的两阶段串行。read skill 的步骤5明确有"回溯"机制：加载具体文档时发现不够，回到 README.md 加载其他看法文件再深入。同理，trace 闭包遍历发现某资产未被任何看法文件覆盖时，需要回溯到三层体系补充看法文件。启动和封闭是两个可反复交替的算子，直到闭包稳定（边界精确 + 边界内成员都有可加载组织形态）。

为什么缺一不可：
- **只有三层体系没有 trace** → 能找到相关认知，但不知道边界在哪，可能多可能少，不可审计（不知道某条认知"凭什么"在闭包里）。这是现在工作包 README.md 的现状——列了 View 和文档，但没法证明"恰好这些，不多不少"。
- **只有 trace 没有三层体系** → 有精确的追溯图，但无法把认知**组织成 AI 可加载的形态**。trace 给你一串 xpath，但 xpath 指向的内容需要三层体系的看法文件来组织和表述。trace 是图谱，三层体系是阅读图谱的视角。
- **两者协作** → 三层体系提供"怎么找、怎么读"，trace 提供"找全了没、边界对不对、每条哪来的"。前者是导航和表述，后者是闭合和审计。

### 2.3.1 两个维度的幂等性（view-index vs trace）——对"启动/封闭"分工的精确化

笼统说"三层体系管启动，trace管封闭"不够精确。read-sync.md 步骤2C 明确区分了两个维度的幂等性：

- **view-index.csv / 看法文件**管**认知组织维度**——"文档怎么被索引"、闭包成员怎么被组织成 AI 可加载的形态（按视角分组、带描述、带依赖关系）
- **trace.csv** 管**追溯维度**——"资产之间有什么关系"、闭包成员是哪些（可达遍历划定边界）

认知闭包需要**两个维度都闭合**：
- 追溯维度闭合（trace）→ 边界精确，不多不少
- 认知组织维度闭合（view-index）→ 边界内每个成员都有可加载的组织形态（被某个看法文件索引，有描述）

如果 trace 闭合但 view-index 不闭合 → 知道闭包有哪些成员，但有些成员没有被任何看法文件索引，AI 无法通过三层体系加载它。这就是"孤立资产"问题——trace 里有这个节点，但没有 view-file 索引它，三层体系导航不到。

### 2.3.2 trace 身兼两职——既是被索引的视角，又是封闭运算的工具

在已落地的项目中（如错题分析系统），trace.csv 自身也被三层体系索引为一个视角——`views/idempotency.md`（幂等追溯分类法）。这意味着 trace 在认知闭包形成中身兼两职：

1. **被索引的视角**——当你需要"追溯任何资产的关系链"时，通过三层体系导航到 idempotency 视角，加载它的看法文件，了解 trace.py 怎么用、trace.csv 有哪些关系类型
2. **封闭运算的工具**——做闭包遍历时，用 trace.py trace/query/query-prefix 从任务起点沿关系图求可达集合

这形成了一个自洽的闭环：trace 既是三层体系的一个成员（被索引），又是检验三层体系覆盖完整性的工具（做闭包遍历时能发现哪些资产没被看法文件索引）。

### 2.4 "像综述论文一样带着引用"——这个类比揭示了闭包的形态

综述论文的形态：
- 有一个明确的主题（对应工作包的"某事"）
- 每个论断都引一篇文献（对应每条认知都引一个 xpath）
- 引用是精确的（文献有卷期页码；xpath 有 path::function / path#section / 行号）
- 综述本身是新的认知产物，不是文献的堆砌（闭包是组织好的认知单元，不是 xpath 的列表）

这给工作包 README.md 提出了一个**形态要求**：它不应该只是"加载这些文件"的清单，而应该是一份**带引用的认知论述**——

> 做这个工作包，你需要理解 X。X 来自 `monitoring/continuation_control.py::ContinuationControl.start`（第 210-245 行），它做的是……。你还需要理解 Y，Y 来自 `docs/specs/p27_monitor_spec.md#A类检查项`，它规定的是……。X 和 Y 的关系是 implements（trace.csv 第 12 行），即 X 实现了 Y 的要求。

每条认知 = 一段论述 + 一个 xpath 引用 + （可选）它和起点的追溯路径。

### 2.5 认知闭包和工作包 README.md 的关系

现有工作包 README.md（akash.md 阶段3）列的是：
- 需要的 View（看法文件）列表
- 甚至直接列出需要加载的具体文档和代码
- 工作包目标、验收标准

认知闭包要求工作包 README.md 升级为：
- 工作包目标（起点）
- **认知闭包正文**：逐条列出所需认知，每条带 xpath 引用 + 一句话说明它为什么在这个闭包里（来自哪条追溯关系）
- 闭包完备性声明：列出做闭包遍历时从起点出发经过的所有追溯路径，证明"可达的都进了"
- 闭包极小性声明：说明没有引入任何不可达的资产（可由 trace 遍历的算法性质保证）
- View 引用：闭包成员按三层体系组织成可加载的形态（哪些看法文件覆盖了这些 xpath）

也就是说，**工作包 README.md = 认知闭包的可审计文档化**。它既是"执行指南"（告诉 AI 加载什么），也是"闭包证明"（证明这个加载集合是完备且不冗余的），还是"审计材料"（每条认知可回溯到 repo 精确位置）。

### 2.6 为什么这个概念"非常重要"

现有体系的隐患：工作包自包含只说了"要列全"，但"全"的判定标准是模糊的。AI 凭经验判断"我觉得这些够了"，可能漏（执行到一半缺上下文）可能多（塞了一堆无关的撑爆上下文）。没有"闭包"这个概念，就没有"边界是否精确"的判定标准，也没有"每条认知凭什么在闭包里"的审计能力。

认知闭包把"工作包需要什么认知"从一个**经验判断**提升为一个**可计算、可审计、可验证**的产物：
- **可计算**：闭包成员 = 从任务起点沿 trace 关系图的可达集合（有明确算法）
- **可审计**：每个成员带 xpath 引用和追溯路径（有出处）
- **可验证**：完备性 = 可达集合无遗漏；极小性 = 无不可达成员（有判定标准）

这正是 trace.csv 幂等关系的最终价值兑现——幂等关系保证了 trace 精确反映 repo 状态，而认知闭包是**在精确 trace 上做闭包运算得到的产物**。trace 的幂等性是闭包正确性的前提；闭包是 trace 幂等性之所以重要的最直接理由。两者互为支撑。

### 2.8 认知闭包是人机协同开发的底层必要条件——概念层级提升

**核心论断**：认知闭包不是工作包拆解阶段的一个步骤，而是**贯穿所有人机协同开发阶段的底层必要条件**。read / akash / workflow / make-plan 表面是不同 skill，底层都是认知闭包形成机制的不同环节或保障。只有闭包形成了，产出性思考（设计、实施、论证）才能开始；在不完备闭包上做产出性思考 = 在错误前提上推理 = 产出错误结论。

**三套体系的底层角色重新理解**：

| 体系 | 表面功能 | 底层角色 |
|---|---|---|
| read | 加载认知 | 闭包形成的**启动算子**（导航+加载） |
| read-sync | 维护认知地图 | 闭包**基础设施的维护**——保持认知地图和追溯关系幂等，使下次闭包形成时能找到完备且准确的成员 |
| make-plan 阶段4 | 认知准备 | 闭包形成的**显式步骤** |
| make-plan 阶段5 | 元数据更新 | 闭包形成后的**基础设施更新**——下次闭包形成时基础准确 |
| akash | 5阶段流程保障 | 保障**每个阶段都先形成该阶段的闭包再执行** |
| workflow | 工作流总纲 | 闭包理念的**总纲** |

**工作主线的重新理解**：akash 的5阶段（需求→方案→工作包→执行→结果）是**产出性思考的5种形态**，每个阶段都需要先形成该阶段的闭包。真正的工作主线不是"5个阶段依次走"，而是"**闭包形成 → 产出性思考 → 闭包更新 → 产出性思考 → ...**"的循环。akash 的5阶段是这个循环中产出性思考的5个切片。

**探索性思考 vs 产出性思考的区分**（对"闭包形成前不能思考"的精确化）：
- **探索性思考**（判断需要什么视角、追溯什么关系、发现还缺什么）——这是闭包形成**的一部分**，是闭包形成的内部过程
- **产出性思考**（设计、实施、论证、写方案）——这是闭包形成**之后**的事

精确表述：**闭包形成前不能做产出性思考，但闭包形成本身需要探索性思考。** 闭包形成不是"不思考就加载"，而是"用探索性思考确定边界，边界稳定后才转入产出性思考"。

**为什么这对 AI 比对人更重要**：人可以边产出边补认知——持续学习是人的常态。但 AI 的上下文是**固定窗口**，产出开始后补认知的成本很高（要停下来加载、可能要返工已产出的部分）。所以"产出前完成闭包"对 AI 不是优化项，是**补偿上下文窗口局限的必要机制**。这解释了为什么我们需要这套体系——它本质是在补偿 AI 和人在认知获取方式上的根本差异。本文档 §三 的两次自我指涉验证就是证据：AI 在不完备闭包上产出，会产出错误内容，而且**自己不知道**（§3.3 问题A：AI 自觉闭包不可靠）。

**和 akash 触发判断的一致性**：akash 自己说"单文件单行修改→不需要走完整流程"。这和闭包视角一致——单行修改的闭包太小（就是那一行及其直接上下文），形成成本低于走完整流程的成本。"需要走完整流程"="需要显式形成闭包"。平凡工作的闭包是隐式的（AI 自然形成），非平凡工作的闭包必须显式形成。

### 2.9 待落地的开放问题

这个概念要真正落地，还有几个问题需要后续想清楚（不在本次讨论范围，记录在此供后续推进）：

1. **闭包遍历的算法定义**：从任务起点出发，沿哪些关系类型遍历？遍历几层？不同关系类型（implements / specified-by / depends-on / part-of / changes ...）是否都要走？还是按工作包性质选择子集？——这决定了闭包的"形状"。**→ 工程化分析见 `basement/007-cognitive-closure-acquisition-optimization.md` §八**
2. **"起点"的形式化**：任务起点是 checkpoint？是工作包目标的一句话描述？还是一组 xpath？起点如何映射到 trace 图上的初始节点集合？**→ 工程化分析见 007 §七（鸡生蛋问题）**
3. **闭包的 token 预算约束**：闭包成员可能很多，超过上下文上限。这时需要在闭包内做二次裁剪——但裁剪后还是"闭包"吗？还是需要进一步拆工作包？这引出"闭包大小 ↔ 工作包粒度"的耦合关系。
4. **闭包文档的模板**：综述论文有体例，认知闭包文档也需要一个标准模板（起点声明 / 闭包正文带引用 / 完备性证明 / 极小性声明 / View 组织）。
5. **和 make-plan 阶段4（认知准备）的关系**：make-plan 的"认知准备"是"列出每个执行步骤需要的视角"，认知闭包是它的精确化版本——从"列视角"升级到"带引用的完备闭包"。是否把认知闭包作为 make-plan 步骤4的升级形态？

## 三、自我指涉验证——构建本概念时的认知闭包复盘

### 3.1 事件

本文档 §二 的初稿写于一次 session 中。AI 在论述"认知闭包要完备"时，用户指出反讽：**你论述认知闭包的过程本身就需要一个认知闭包，而你的闭包完备吗？**

AI 盘点后承认不完备：

| 该加载的 | 初稿时加载了？ |
|---|---|
| workflow.md | ✓ 完整加载 |
| akash.md | ✓ 完整加载 |
| make-plan.md | ✓ 完整加载 |
| read/SKILL.md | ✓ 但只是一句话触发器 |
| **read.md 完整内容** | ✗ 没加载 |
| read-sync/SKILL.md | ✓ 但只是一句话触发器 |
| **read-sync.md 完整内容** | ✗ 没加载 |
| **项目本地 README.md** | ✗ 没加载 |

AI 只看了 read 和 read-sync 的 SKILL.md（一句话触发器），按三层体系自己的规则，触发器说"完整加载 /Users/user/skills-devin/read.md"，应该跟进去加载完整内容，但没跟。这是真实疏漏，不是修辞。

### 3.2 补加载后的三个实质修正

补加载 read.md / read-sync.md / 项目本地 README.md 后，发现初稿有三个实质性错误，已回写到 §2.3、新增 §2.3.1、§2.3.2：

1. **启动与封闭不是严格两阶段，可交替迭代**——read.md 步骤5 的"回溯"机制证明三层体系启动是可迭代的。初稿画成线性两阶段是错的。
2. **view-index 和 trace 是两个不同维度的幂等性**——read-sync.md 步骤2C 明确区分"认知组织维度"（view-index）和"追溯维度"（trace）。初稿笼统说"三层体系管启动"，丢了 view-index 的独立角色。
3. **trace 身兼两职**——项目本地 README.md 第六节显示 trace.csv 自身被索引为 `views/idempotency.md` 视角。初稿只说了 trace 是封闭工具，没说它也是被索引的视角。

这三个修正都不是小修小补——第一个改了闭包形成机制的图景（线性→迭代），第二个拆分了"启动"的内部结构（导航 vs 组织），第三个揭示了 trace 的自指性质。

### 3.3 这个案例本身是认知闭包概念的最佳佐证

**如果连提出"认知闭包"这个概念都需要完备闭包，那任何工作包的执行就更需要了。** 完备闭包不是奢侈品，是最低门槛。

这个自我指涉案例还揭示了两个深层问题：

**问题A：AI 的"自觉闭包"不可靠。** AI 在初稿时并没有意识到自己没加载 read.md 完整内容——它看了 SKILL.md 的一句话触发器就以为自己"加载了 read skill"。这说明 AI 对"我的闭包是否完备"缺乏自检能力。认知闭包如果只靠 AI 自觉，会系统性漏项。**需要一个强制性的闭包完备性检查步骤**——就像 akash 的幂等检查清单一样，闭包形成后必须逐项核对"该加载的都加载了吗"。

**问题B：一句话触发器是闭包漏洞的高发点。** SKILL.md 的极简化设计（一句话触发器+独立内容文档）本身是对的，但它制造了一个陷阱——AI 看到 SKILL.md 就以为"加载完了"，不跟进加载独立内容文档。这个陷阱在认知闭包形成时必须被显式规避：闭包清单里不能只列"加载 read skill"，必须列"加载 read.md 完整内容（不只是 SKILL.md）"。

### 3.4 对认知闭包落地设计的反推

这个案例直接反推了 §2.7 的开放问题，特别是第4点（闭包文档模板）和第1点（闭包遍历算法）：

- **闭包文档模板必须含"完备性核对清单"**——不是只列闭包成员，还要列"我检查过这些来源，确认没有遗漏"的核对过程。类似 akash 的幂等检查清单，但是针对认知加载的。
- **闭包遍历算法必须穿透"触发器→完整内容"这一跳**——遍历 trace 关系图时，遇到 view-file 节点不能停，要继续遍历到它索引的具体文档；遇到 skill 的 SKILL.md 不能停，要跟进到独立内容文档。否则闭包会在"索引层"断裂。
- **闭包必须区分"描述层"和"事实层"，并核对两者一致**——文档说某资产存在/某机制在用，和该资产/机制在 repo 中真的存在/真的在用，是两回事。闭包不能只含描述层文档（workflow.md / read-sync.md 怎么说），还要含事实层证据（view-index.csv / view_index.py 实际是否存在、是否在用）。完备性核对清单里必须有一条"描述层和事实层是否一致"——否则会基于过时描述写出错误内容。本次 view-index vs trace 的查证就是案例：如果文档真的过时（比如 view-index 被合并但文档没更新），只信描述层的闭包会产出错误论述。
