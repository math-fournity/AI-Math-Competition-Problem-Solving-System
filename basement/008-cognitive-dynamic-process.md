## 一、用户原话（完整保留）

> 所以，我们是否需要发明一个认知动力过程：为了构建N，我们需要连续地构建`认知包`:n1，n2，n3，……，N这个过程n[x]每次都更靠近N，或许有些内容，在从n1到N的过程中，进进出出过程中的一代又一代认知包，也就是说，我们并不是无限量地去加载上下文，而是总是尝试为了问题去记录我们认为的最终输出N的候选信息，然后基于这些候选信息，在一个新的Session中，再次展开探索，得到下一代认知包，直至最终得到为了处理一个工作包而需要的认知闭包N。

## 二、为什么需要发明这个概念

### 2.1 007 的隐含假设及其局限

007 的整个框架有一个隐含假设：**N 是可以在一次 session 中从 M 里提炼出来的**——先获取 M，再从 M 提炼 N，一次完成。这是"单次快照模型"。

但复杂工作包的现实挑战了这个假设：

1. **发现 N 需要什么本身需要探索，而探索消耗上下文**——你沿着 trace 链追溯，每追一层消耗上下文，追到后面可能前面的已经要被压缩了。探索本身和上下文窗口竞争。

2. **有些"需要什么"只有加载了另一些内容后才显现**——你不知道你需要 D，直到你加载了 B 并理解了 B 和 D 的关系。这种依赖是序贯的，不是一次能看全的。N 的成员不是同时可见的，是逐个显现的。

3. **上下文窗口限制了单次探索的深度**——复杂工作包的 trace 追溯链可能很长，一次 session 走不完。走到中途上下文已满，必须停下来落盘，否则前面的探索成果被压缩丢失。

### 2.2 因此需要的是迭代逼近模型

N 不是一次提炼出来的，是多代认知包逐代逼近出来的。这是"迭代逼近模型"，和 007 的"单次快照模型"是两种不同的认知获取模式，适用于不同复杂度的工作包。

## 三、核心概念：认知包 n[x] 与认知动力过程

### 3.1 认知包 n[x] 的定义

**n[x]** = 第 x 代认知包，是关于"N 包含什么"的一个**带证据的候选集**。

每个 n[x] 的成员不只是"在上下文里"，而是"我认为它在 N 里，理由是……"。n[x] 是假设，不是原始材料。

### 3.2 n[x] 和 M 的本质区别——概念的核心

**n[x] 不是 M。** 这是整个概念最关键的区分。

| | M（007） | n[x]（008） |
|---|---|---|
| 本质 | 进入上下文的原始内容 | 关于 N 是什么的假设 |
| 是什么 | "加载了什么" | "我认为 N 包含这些" |
| 状态 | 冗余的、散乱的 | 经过提炼的、带引用的、有理由的 |
| 和 N 的关系 | N ⊆ M（N 散落在 M 中） | n[x] → N（n[x] 逼近 N） |
| 生命周期 | session 内存在，session 结束消失 | 持久化，跨 session 传递 |

n[x] 是对 N 的一个**猜想**，每一代基于新探索修正这个猜想。认知动力过程不是"多加载几次"（那是多次获取 M），而是"多代假设的修正"（每代修正 n[x]）。

### 3.3 认知动力过程

```
任务起点（工作包目标）
  ↓
n1 = 初始认知包（基于起点和初步 trace 追溯的候选集）
  ↓ 持久化 n1，session 可结束
session 2：加载 n1 → 基于 n1 展开新探索 → 发现需要加入/移除的成员
  ↓
n2 = 修正后的认知包
  ↓ 持久化 n2，session 可结束
session 3：加载 n2 → 基于 n2 展开新探索 → 发现需要加入/移除的成员
  ↓
n3 = 修正后的认知包
  ↓
...
  ↓
n[x] = n[x+1]（稳定，没有加入也没有移除）
  ↓
n[x] = N（认知闭包形成）
  ↓
开始产出性思考（设计/实施/论证）
```

### 3.4 收敛判据

**n[x] = n[x+1]**：一代探索后没有加入新成员也没有移除旧成员，认知包稳定。

此时 n[x] = N，认知闭包形成，可以开始产出性思考（见 006 §2.8：闭包形成前不能做产出性思考）。

**⚠️ 根本性缺陷（由 009 识别）**：这个收敛判据只能保证**连通分量内的完备性**——在当前岛屿内探索完了。但如果 trace 关系图有多个连通分量（岛屿），从起点所在岛屿出发永远到不了其他岛屿，收敛判据照样满足但 N 不完备。这是"收敛于错误终点"——收敛判据无法检测跨岛屿的遗漏。修正方案见 `basement/009-island-cognitive-crisis.md`（增加岛屿遍历阶段0，用递归目录结构 + README 作为不依赖 trace 的 fallback 分类学）。

收敛不是"加载完了"，而是"假设不再变化"——这是假设修正过程的收敛判据，和迭代算法的收敛判据一致。

## 四、非单调性——"进进出出"是精髓

### 4.1 非单调演化

用户明确指出"有些内容在从 n1 到 N 的过程中，进进出出"——这是非单调的，不是只增不减的。

```
n1: {A, B, C}          ← 初始猜测
n2: {A, B, D}          ← 移除 C（发现无关），加入 D（发现需要）
n3: {A, B, C, D, E}    ← 重新加入 C（发现其实需要），加入 E
n4: {A, B, D, E}       ← 再次移除 C（确认无关）
...
N:  {A, B, D, E, F}    ← 稳定
```

这像科学共识的演化——有反复，有修正，不是直线前进。

### 4.2 为什么非单调性是精髓而非缺陷

如果认知包只增不减（单调），那意味着每次探索只会"发现需要更多"，永远不会"发现之前以为需要其实不需要"。但现实是：

- **初判错误的成员会被移除**——n1 时以为 C 相关，深入后发现 C 其实是另一个工作包的
- **被移除的成员可能重新加入**——n2 移除了 C，n3 时加载了新证据发现 C 其实和本工作包有关（只是关系链更长，n2 时没追到）
- **反复进出最终收敛**——C 进出几次后，证据充分了，确定在或不在，稳定下来

非单调性反映了**认知逼近真相的过程**——真相不是一次到达的，是在反复验证中收敛的。

### 4.3 因此每一代必须记录纳入/排除理由

非单调性意味着每一代 n[x] 必须记录**为什么加入、为什么移除**——这是审计 trail，像系统综述里的证据纳入/排除理由。

没有这个 trail，"进进出出"就变成无序震荡，无法收敛——AI 可能反复在同一个成员上进进出出，不知道之前为什么移除过、为什么又要加入。

**n[x] 的成员结构**（每个成员）：
- **xpath 引用**——这个成员在 repo 中的精确位置（和 006 §2.4 一致）
- **纳入理由**——为什么认为它在 N 里（基于哪条 trace 关系 / 哪次探索发现）
- **状态**——当前是"纳入"还是"候选"还是"已排除"
- **变更历史**——这个成员在哪些代被加入、移除、重新加入（审计 trail）

## 五、跨 session 的持久化机制

### 5.1 为什么需要持久化

用户明确说"在一个新的 Session 中，再次展开探索，得到下一代认知包"——这意味着 n[x] 必须被持久化，让下一个 session 能从 n[x] 而不是从零开始。

如果不持久化，每个 session 都从零开始构建认知包，无法累积逼近——这退化回 007 的单次模型，且复杂工作包根本无法完成。

### 5.2 和现有跨 session 机制的关系

| 机制 | 跨 session 传递什么 | 粒度 | 和认知动力过程的关系 |
|---|---|---|---|
| akash-new | akash 工作流做到哪个阶段 | 阶段 | 传递"工作流进度"，不传递"认知包内容" |
| HANDOFF | 研究状态交接 | 通用 | 通用交接，没有"认知包逼近 N"的结构 |
| trace.csv | 资产关系图 | 资产关系 | 外化记忆，是认知包形成的*基础设施*，不是认知包本身 |

认知动力过程需要的是：**一个持久化的、带引用的、可 diff 的认知包文档**，每代更新，git 追踪每一代的变化。

### 5.3 设计要求

认知包文档（建议命名 `cognitive-pack.md`，放在工作包目录下）：

- **可持久化**——文件形式，git 可追踪
- **可 diff**——文本格式（markdown 或 CSV），每代变化可逐行 diff，保留完整演化历史
- **带引用**——每个成员带 xpath 引用和纳入/排除理由（和 006 §2.4 综述论文形态一致）
- **跨 session 可加载**——下一个 session 加载这个文档，就知道上一代认知包是什么，从哪里继续
- **和 trace.csv 协作**——认知包成员的 xpath 引用指向 trace.csv 中的资产；trace 追溯是探索 n[x+1] 的工具

### 5.4 和 trace.csv 的设计哲学一致

trace.csv 选择 CSV 而非 SQLite，是因为"CSV 是文本文件，git 可以逐行 diff，保留完整变更历史"（workflow.md §3）。认知包文档同理——每代 n[x] 的变化可 diff，能看到"n2 比 n1 多了 D、少了 C"，保留完整的认知演化历史。

## 六、认知动力过程的完整工作流

### 6.1 单代工作流（session x）

```
1. 加载上一代认知包 n[x-1]（如果是 n1，从任务起点开始）
2. 基于 n[x-1] 的成员，展开新探索：
   a. 对每个 n[x-1] 成员，用 trace 追溯它的关系链
   b. 追溯中发现新成员 → 标记为"候选加入"
   c. 深入理解后发现某成员其实无关 → 标记为"候选移除"
3. 验证候选变更：
   a. 候选加入的成员：确认它和任务起点有 trace 追溯路径
   b. 候选移除的成员：确认它和任务起点没有 trace 追溯路径（或路径断裂）
4. 应用变更，形成 n[x]
5. 检查收敛：n[x] == n[x-1]？
   a. 是 → n[x] = N，认知闭包形成，可开始产出性思考
   b. 否 → 持久化 n[x]，可在新 session 继续
6. 持久化 n[x]（无论是否收敛）
```

### 6.2 多代工作流（跨 session）

```
session 1: 任务起点 → n1 → 持久化
session 2: 加载 n1 → 探索 → n2 → 持久化
session 3: 加载 n2 → 探索 → n3 → 持久化
...
session k: 加载 n[k-1] → 探索 → n[k] == n[k-1] → n[k] = N → 开始产出性思考
```

每个 session 做的事是相同的（加载上代 → 探索 → 修正 → 持久化），只是输入和输出不同。这是**幂等的单代算子反复应用**，直到收敛。

### 6.3 和 akash 的关系

认知动力过程是 akash 阶段3（工作包拆解）的**前置子过程**——在拆解工作包之前，先形成该工作包的认知闭包 N。

```
akash 阶段1：需求分析
akash 阶段2：方案制定
  ↓
认知动力过程：n1 → n2 → ... → N（跨 session，可能多代）
  ↓
akash 阶段3：工作包拆解（基于已形成的 N）
akash 阶段4：执行
akash 阶段5：结果记录
```

认知动力过程嵌在 akash 阶段2和阶段3之间，是"方案已定但工作包认知闭包未形成"的过渡阶段。

## 七、什么时候需要认知动力过程

### 7.1 不是所有工作包都需要

和 akash 的触发判断一致（akash.md：单文件单行修改→不需要走完整流程）：

- **简单工作包**（N 小且明确）→ 一次 session 形成 N，不需要认知动力过程。退化为 007 的单次模型。
- **复杂工作包**（N 大或不确定）→ 需要多代逼近。使用认知动力过程。

### 7.2 判定标准

**一次 session 能否走完 trace 追溯链并稳定闭包？**

- 能 → 单次模型（007）：获取 M → 提炼 N → 开始产出
- 不能 → 迭代模型（008）：n1 → n2 → ... → N → 开始产出

### 7.3 复杂度的信号

以下信号提示需要认知动力过程：
- trace 追溯链深度 > 3 层（一层的追溯就消耗大量上下文）
- 闭包成员跨多个分类法（需要多个视角的探索，单 session 难以覆盖）
- 工作包涉及大量代码文件（每个文件的函数级追溯都很长）
- 探索中发现"需要加载 X 才知道是否需要 Y"的序贯依赖（单次难以看全）

## 八、和 006/007 的关系

### 8.1 三篇文档的递进关系

| 文档 | 问题 | 模型 | 适用场景 |
|---|---|---|---|
| 006 | 认知闭包是什么 | 概念定义（N 是什么、完备性、可审计性） | 所有工作包 |
| 007 | 如何获取最小 M | 单次优化（min \|M\| s.t. N⊆M） | N 可一次提炼的简单工作包 |
| 008（本文档） | 复杂 N 如何跨 session 逼近 | 迭代逼近（n1→n2→…→N） | N 无法一次确定的复杂工作包 |

三者递进：006 定义 N → 007 优化单次获取 M → 008 处理 N 本身的迭代形成。

### 8.2 008 填补的空白

008 回答的是 006/007 都没覆盖的问题：**当 N 本身无法在一次 session 中确定时怎么办**。

- 006 假设 N 是已知的（定义它是什么）
- 007 假设 N 可从 M 一次提炼（优化获取 M）
- 008 说复杂情况下 N 需要多代逼近（处理 N 的形成过程本身）

### 8.3 008 不是 007 的附属，是平行的另一个问题维度

007 是"给定 N 可知，如何高效获取包含 N 的最小 M"——空间维度优化（一次获取的效率）。
008 是"当 N 不可一次知，如何跨 session 逼近 N"——时间维度优化（多次逼近的收敛）。

两者正交：一个优化单次获取的效率，一个处理多次逼近的收敛。复杂工作包可能同时需要两者——用 008 的迭代逼近确定 N，每代迭代内部用 007 的最小 M 策略获取该代的探索上下文。

## 九、开放问题

1. **认知包文档的具体格式**——markdown 还是 CSV？markdown 适合人/AI 可读的带论述的候选集；CSV 适合纯结构化的成员清单（像 trace.csv）。可能需要两者：CSV 存成员清单（可 diff），markdown 存论述和理由（可读）。
2. **收敛判据的严格性**——n[x] == n[x+1] 是严格相等还是"无显著变化"？如果允许"无显著变化"，阈值如何定？严格相等可能需要太多代才能收敛。
3. **探索的终止条件**——单代探索什么时候停止？上下文满了？追溯链走完了？没有新发现了？需要明确的单代终止条件，否则单代可能无限探索。
4. **认知包和工作包 README.md 的关系**——认知包是工作包 README.md 的前置产物还是一部分？收敛后的 N 是否直接成为工作包 README.md 的"认知闭包正文"（006 §2.5）？
5. **和 akash-new 的集成**——akash-new 跨 session 续传 akash 工作流。认知动力过程跨 session 续传认知包。两者如何协作？akash-new 是否需要知道"当前在认知动力过程中，第几代"？
6. **认知包的版本管理**——每代 n[x] 是覆盖上一代还是保留所有代？如果保留所有代（git 追踪），如何避免文档膨胀？如果覆盖，如何保留审计 trail（进出的历史）？
