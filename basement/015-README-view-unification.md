## 二、AI 的理解

### 2.1 核心论断：README 和 view 是同一种东西

011 §四.1 已经说了最关键的一句："认知闭包的本质是一个特殊的 view——为某个具体工作包临时构建的跨视角 view。"

把这个洞察展开，"view"（索引）其实有三种分类法：

| | 分类法 | 边界 | 例子 |
|---|---|---|---|
| **README** | 目录结构（事实层） | 物理位置——某个目录下 | `basement/README.md` |
| **看法文件** | 知识主题（描述层） | 逻辑主题——跨越目录 | `views/idempotency.md` |
| **认知闭包 N** | 具体任务（临时构建） | 当前工作包——跨越视角 | 面相3 文档 |

三者都是"索引"——从某个视角看哪些资产。区别只在分类法和边界：

- README 以目录结构为分类法 → 边界是物理位置 → **不依赖维护质量**（事实层，009 §2.3）
- 看法文件以知识主题为分类法 → 边界是逻辑主题 → **依赖维护质量**（描述层）
- N 以具体任务为分类法 → 边界是当前工作包 → **临时构建，用完即弃**

因此用户的两种表述都对：
- **README 是特殊的 view**——特殊在分类法是目录结构（事实层）
- **view 是特殊的 README**——特殊在跨越目录（按主题而非按物理位置组织）

### 2.2 view 支撑哪个过程

009 把认知闭包形成分成两个阶段：
- **阶段0（岛屿遍历）**：保证跨岛屿完备性——用目录结构 + 递归 README
- **阶段1+（闭包迭代）**：保证岛屿内完备性——用 trace 追溯链迭代逼近

但 011 的洞察让这个分工需要重新理解。如果 N 本身是一个 view，那 view 不只是"支撑"闭包形成——**view 既是闭包形成的起点，也是闭包形成的终点**：

```
预设的 view（README + 看法文件）   ← 起点：已经组织好的视角
        ↓ 闭包形成过程
临时的 view（N，面相3 文档）       ← 终点：为当前任务临时构建的视角
```

- **README 作为起点**：AI 在阶段0 从目录结构这个视角出发，判断哪些岛屿相关
- **看法文件作为起点**：AI 在阶段1+ 从知识主题这个视角出发，在岛屿内做闭包迭代
- **N 作为终点**：AI 最终构建出一个以"当前任务"为分类法的临时 view

**闭包形成过程 = 从预设 view 出发，逐步构建临时 view。**

### 2.3 view 需要为这个过程提供什么

既然 view 是起点，它需要提供的是**让 AI 判断"这个视角和当前任务是否相关"的信息**：

1. **这个视角看到哪些资产**（索引）——让 AI 知道这个视角的覆盖范围
2. **每个资产讲什么**（一句话）——让 AI 判断单个资产是否相关
3. **覆盖哪些问题场景**——让 AI 匹配当前任务的问题场景
4. **依赖关系**——让 AI 知道加载这个资产后还需要加载什么

这正好是三要素（讲什么/覆盖场景/依赖关系）——**README 的格式和看法文件的格式本质上是同一个格式，因为它们都是预设的 view**。

但分工不同导致详细度不同：
- **README（目录入口）**：服务阶段0，AI 的问题是"这个目录要不要进入？"——需要一句话说明，够判断相关性即可
- **看法文件（主题视图）**：服务阶段1+，AI 的问题是"这个主题下有哪些资产？"——需要完整三要素，支撑闭包迭代

## 三、对 009 递归 README 规范的格式确立

### 3.1 009 留下的开放问题

009 §四.4 提出了递归 README 要求——"每个子目录都有 README，每个 README 索引该目录的直接子目录和直接文件"。但 009 §八开放问题 #1 #2 明确指出：
- #1：递归 README 的维护成本——是否所有子目录都需要 README？
- #2：README 的粒度——只列文件名（纯索引），还是带描述（索引+一句话说明）？带描述的话维护成本更高，但 AI 判断"是否相关"更准确。

009 没有给出答案，留作开放问题。本文档通过 §二的概念澄清，给出了答案。

### 3.2 格式确立：目录入口格式

基于 §二.3 的分析，README 作为目录入口（服务阶段0），格式应该是：

```markdown
# <目录名>/ — <一句话主题>

> **本目录是什么**：<2-3句，这个目录的知识主题和用途>
>
> **与看法文件/根README的关系**：<如果有重叠的view，说明分工>

## 直接子目录（如果有）

| 子目录 | 一句话说明 |
|---|---|
| `subdir_a/` | <这个子目录讲什么> |

## 直接文件（如果有）

| 文件 | 一句话说明 |
|---|---|
| `file_a.py` | <这个文件做什么> |

## 本目录依赖关系

<本目录和其他目录/资产的关系，或"无外部依赖">
```

### 3.3 回答 009 §八开放问题

**开放问题 #1（是否所有子目录都需要 README）**：
答案：所有含知识资产（.md/.py/.sh/.csv）的子目录都需要。判定标准——该目录下有 AI 可能需要加载的资产，就需要 README 作为入口。例外：纯数据目录（如 `data/poc_2.7/`）如果内容是运行产物而非知识资产，可以在父目录 README 中一句话带过，不单独建 README。

**开放问题 #2（README 的粒度）**：
答案：**索引 + 一句话说明**（表格形式）。不是纯索引（AI 无法判断相关性，009 §四.3 第3点无法满足），也不是完整三要素（和看法文件重叠时冗余）。一句话说明要够 AI 判断"该岛屿和当前工作包是否相关"，但不需要完整覆盖场景和依赖列表——那些在看法文件中。

### 3.4 README 和看法文件的重叠处理

当某个目录的所有文件都属于同一个主题时（如 `basement/` 的所有文件都属于"认知闭包体系"），该目录 README 和对应看法文件索引同一批文件。处理方式：**保持两份，明确分工**。

| | README（目录入口） | 看法文件（主题视图） |
|---|---|---|
| 服务阶段 | 阶段0（岛屿遍历） | 阶段1+（闭包迭代） |
| AI 的问题 | "这个目录要不要进入？" | "这个主题下有哪些资产？" |
| 格式 | 文件名 + 一句话说明（表格） | 完整三要素（讲什么/覆盖场景/依赖） |
| 详细度 | 简洁——够判断相关性即可 | 详细——支撑闭包迭代 |

**不是冗余，因为服务不同阶段、回答不同问题。** 但需要在 README 中显式声明分工关系（"与看法文件的关系"节），避免维护者困惑。

### 3.5 "与看法文件/根README的关系"声明

当 README 和某个 view 索引同一批资产时，README 必须在开头声明这个关系：

```markdown
> **与看法文件的关系**：本目录所有文件都属于"XXX"主题，因此本目录 README 和 `views/xxx.md` 索引同一批文件。分工：本 README 是目录入口（服务阶段0），`views/xxx.md` 是主题视图（服务阶段1+）。需要详细覆盖场景和依赖关系时，加载看法文件。
```

当目录和主题不重合时（如 `docs/` 包含多个主题的文档），声明与根 README 的关系：

```markdown
> **与根 README 的关系**：根 `README.md` 的分类法索引已覆盖本目录的文档。本 README 是目录入口（服务阶段0），根 README 是分类法索引（服务阶段1+）。
```

### 4.3 015 揭示了 view 的双重角色

011 说 N（闭包）是 view 的终点。015 补充了 view 也是闭包的起点——README 和看法文件作为预设的 view，是闭包形成过程的输入。这构成了 view 的双重角色：

```
预设 view（README + 看法文件）→ 闭包形成过程 → 临时 view（N，面相3）
     ↑ 起点                                      ↑ 终点
```

这个双重角色在 011 中隐含但未显式论述。015 把它显式化。

1. **view 的三层分类法是否完备**——README（事实层）/ 看法文件（描述层）/ N（临时层）是否覆盖了所有 view 类型？是否存在其他分类法的 view？
