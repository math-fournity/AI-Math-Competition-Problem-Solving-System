# 007 — 认知闭包获取的工程优化：最小 M 问题

**日期**：2026-08-19
**性质**：工程方案分析（认知闭包概念的工程化落地）
**前置**：`basement/006-cognitive-closure-concept.md`（认知闭包概念定义）
**状态**：分析完成，待落地为工具改进和工作包

---

## 一、用户原话（完整保留）

> 如果我们把一个工作包需要的认知闭包的内容看成是N，那么通过无论何种手段，无论是遍历git log，还是走我们的read三层体系，亦或是通过trace系统，甚至是直接全部加载所有的文档。无论那种方式，当上下文中存在N，或者说某种意义上，对AI来说，N在它的上下文中出现了。所谓的某种意义，就是说，这个N，可以被完整地提炼出来，但是以往，更多的时候，是加载了很多文档和代码之后，在一个更大的、冗余的上下文M中，所有N的内容，散落在各处。然而真正重要的是：或许，当我们有M的时候，从M中提炼N是有系统化的方法的，但是何种前置的各种索引体系，才能让我们有效地得到M，且这个M在得到的时候，是所有M中，最小的？换句话说，如何能够在不浪费更多上下文的情况下，得到所有进行一个工作包所需要的repo中的各种知识？

---

## 二、问题形式化

### 2.1 两个变量

- **N** = 工作包需要的认知闭包内容（完备且不冗余的精确集合，见 006 §2.2）
- **M** = 实际进入 AI 上下文的内容（包含 N，但通常有冗余）

### 2.2 优化目标

**min |M| s.t. N ⊆ M**

在保证 N 完整出现（可被提炼）的前提下，M 越小越好。

### 2.3 两个独立问题

用户做了一个重要区分：**获取 M** 和 **从 M 中提炼 N** 是两个独立问题。

- **从 M 中提炼 N**——用户判断"有系统化的方法"。AI 的理解能力就是提炼方法：给定一个包含 N 的上下文 M，AI 能识别出哪些是 N、哪些是冗余，并基于 N 工作。这个能力是存在的，且在小 M 中可靠（详见 §四 精度-成本权衡）。
- **获取最小的 M**——这是用户真正问的问题。何种前置索引体系能让我们得到所有 M 中最小的那个？

本文档聚焦后者。

**重要补充**：本文档的"单次快照模型"（先获取 M，再从 M 一次提炼 N）有一个隐含假设——N 可在一次 session 中确定。对于复杂工作包，这个假设不成立：N 本身需要跨 session 多代逼近。这个情况由 `basement/008-cognitive-dynamic-process.md` 处理（迭代逼近模型：n1→n2→…→N）。007 和 008 是正交的两个问题维度——007 优化单次获取效率（空间维度），008 处理多次逼近收敛（时间维度）。复杂工作包可能同时需要两者。

## 三、M > N 的冗余来源

M 大于 N 的冗余来自三个层面，按冗余贡献从大到小排列：

### 3.1 加载粒度冗余（最大冗余源）

闭包成员的粒度是 xpath（`path::function`、`path#section`），但加载工具的粒度是文件。

你需要 `continuation_control.py::start` 这个函数，但你加载了整个 `continuation_control.py`——文件里另外 30 个函数全是冗余。一个 800 行的文件，你只需要 50 行，冗余率 94%。

**特征**：文件越大、闭包成员越细粒度，冗余率越高。代码文件的加载粒度冗余通常比文档更严重（代码文件常含大量与当前任务无关的函数/类）。

### 3.2 导航开销冗余（三层体系的固有代价）

为了找到相关文档，你加载了整个 README.md（所有分类法的描述）和整个看法文件（所有文档的描述）。这些是"导航路费"——你只需要其中几个条目，但加载了全文。

**特征**：导航开销本身不在 N 里（它不是工作包需要的认知，是找到这些认知的路费），但必须出现在 M 里才能导航。它是"获取成本"而非"闭包内容"。

### 3.3 探索性冗余（AI 不确定时的保险性多加载）

"这个文件可能有用，先加载了再说"——这是 AI 在闭包边界不确定时的补偿行为。越不确定，越多加载，M 越大。

**特征**：这是最隐蔽的冗余——AI 自己造成的，且 AI 不容易意识到（和 006 §3.3 问题A 一致：AI 自觉闭包不可靠）。探索性冗余和闭包边界的不确定性正相关：边界越确定，探索性冗余越少。

## 四、最小 M 的获取策略——按冗余从大到小排列

### 策略1：全量加载

- **M** = 全 repo
- **冗余**：最大
- **N ⊆ M** ✓ 但浪费巨大，通常超出上下文上限
- **适用**：repo 极小（< 上下文上限的 10%），不值得建索引

### 策略2：三层体系导航 + 文件粒度加载（当前体系）

- **M** = README.md 全文 + 相关看法文件全文 + 相关文件全文
- **冗余**：导航开销 + 文件内冗余 + 探索性冗余
- **N ⊆ M** 通常 ✓（依赖 AI 判断准确，可能漏）
- **适用**：当前体系，所有项目
- **问题**：M 中可能有 70-90% 是冗余的（导航开销 + 文件内冗余）

### 策略3：trace 缩小范围 + 文件粒度加载

- **M** = trace 查询输出 + 相关文件全文（trace 给出的文件集合）
- **冗余**：文件内冗余 + trace 可能多包含的文件
- **N ⊆ M** 通常 ✓（依赖 trace 幂等正确 + 闭包遍历覆盖完整）
- **和策略2的区别**：省去了导航开销（不需要加载 README/看法文件全文，trace 直接给出文件列表）
- **M 比策略2小**，因为消除了导航开销冗余

### 策略4：trace 闭包遍历 + xpath 精确加载（理论最优）

- **M** = trace 查询输出 + grep 输出 + 闭包成员的精确内容（按 xpath 行范围加载）
- **冗余**：几乎只有 trace/grep 的输出（很小）
- **N ⊆ M** ✓（如果闭包遍历算法正确 + trace 幂等正确）
- **M ≈ N**，接近理论下界
- **前提**：闭包遍历算法实现 + xpath→行范围映射 + read 支持 xpath 精确加载
- **工程成本**：最高（需要实现闭包遍历算法 + 行范围映射工具）

### 策略5：trace 缩小范围 + AI 提炼（务实混合）

- **M** = trace 查询输出 + 一小撮文件（trace 缩小后的文件集合）
- **冗余**：文件内冗余 + trace 可能多包含的文件
- **N ⊆ M** 通常 ✓
- **和策略4的区别**：不要求精确闭包，只要求 trace 足够好地缩小了范围。AI 在小 M 中提炼 N。
- **和策略3的区别**：策略3 是文件粒度加载，策略5 强调"一小撮"——trace 把范围缩到很小，AI 提炼可靠。
- **工程成本**：低（只需要 trace 能缩小范围，不需要完美闭包算法）
- **M 略大于 N**，但 AI 在小 M 中提炼是可靠的

### 策略对比表

| 策略 | M 组成 | 冗余来源 | M 相对 N | 工程成本 | 依赖 |
|---|---|---|---|---|---|
| 1 全量加载 | 全 repo | 全部 | 最大 | 无 | 无 |
| 2 三层+文件（当前） | README+看法文件+文件全文 | 导航+文件内+探索性 | 70-90% 冗余 | 已实现 | 三层体系 |
| 3 trace+文件 | trace输出+文件全文 | 文件内+trace多包含 | 比策略2小 | 中 | trace 幂等 |
| 4 trace+xpath（理论最优） | trace输出+grep输出+精确内容 | 几乎无 | M≈N | 高 | 闭包算法+行范围映射+xpath加载 |
| 5 trace缩小+AI提炼（务实） | trace输出+一小撮文件 | 文件内+trace多包含 | 略大于N | 低 | trace 能缩小范围 |

## 五、关键洞察：trace 的价值是缩小 M，不是精确给出 N

### 5.1 精确 N vs 近似 N

精确给出 N（策略4）是理想，但需要：
- 闭包遍历算法完美实现（遍历哪些关系类型、几层、起点如何映射——见 006 §2.9 开放问题 #1 #2）
- trace 幂等绝对正确（现实中只能尽量维护，不能保证绝对）

现实中这很难保证。但即使 trace 不完美——可能多包含几个文件、少包含几个——它已经把 M 从"全 repo"（GB 级）缩小到"一小撮文件"（KB 级）。

### 5.2 AI 在小 M 中提炼 N 是可靠的

AI 在 GB 级的 M 中提炼 N 不可靠——不是能力问题，是上下文窗口装不下，AI 根本看不到全貌。

但 AI 在 KB 级的 M 中提炼 N 是可靠的——干扰项少，AI 能识别出哪些是 N、哪些是冗余。

这和 006 §3.3 问题A（AI 自觉闭包不可靠）不矛盾——问题A 说的是 AI 在**大 M** 中提炼 N 不可靠。但在**小 M** 中提炼是可靠的。关键是 M 有多小。

### 5.3 trace 的真正价值

trace 的真正价值不是"精确计算 N"，而是**"把 M 从 AI 看不过来的规模缩小到 AI 看得过来且能可靠提炼的规模"**。

这引出**精度-成本权衡**：
- 追求精确 N（策略4）→ 需要完美闭包算法，工程成本高，但 M ≈ N
- 接受近似 N（策略5）→ 只需要 trace 缩小范围，工程成本低，M 略大于 N 但 AI 能可靠提炼

**务实建议**：先实现策略5（低工程成本，立即改善），再逐步向策略4演进（高工程成本，理论最优）。

## 六、最小 M 的理论下界

### 6.1 M 的组成

M = 启动开销 + 闭包内容 + 索引开销

- **启动开销** = 理解任务 + 确定起点（任务描述 + 起点在 trace 中的映射）—— 很小，不可消除
- **闭包内容** = N —— 不可消除（这就是你要的）
- **索引开销** = trace 查询输出 + grep 输出 —— 很小，不可完全消除（你需要查询来确定 N 是什么）

### 6.2 理论最小 |M|

**理论最小 |M| = |N| + 启动开销 + 索引开销**，其中后两项都很小。

策略4 接近这个下界。当前体系（策略2）的 |M| ≈ |N| + 导航开销 + 文件内冗余，其中后两项可能占 M 的 70-90%。

### 6.3 从策略2到策略4的跃迁核心

从策略2（当前）跃迁到策略4（理论最优），核心是两件事：

1. **用 trace 替代三层体系导航**——消除导航开销（不需要加载 README/看法文件全文，trace 直接给出 xpath）
2. **用 xpath 精确加载替代文件粒度加载**——消除文件内冗余（只读函数体/章节，不读整个文件）

## 七、鸡生蛋问题：起点确定需要多少启动上下文

### 7.1 问题

trace 闭包遍历需要**起点**，起点需要**理解任务**，理解任务可能需要**一些上下文**。这个"启动上下文"也是 M 的一部分。

### 7.2 两种情况

**情况A：任务起点明确**（起点在 trace 中有记录）

如果任务是用户的一句话（"修复续传 stall 问题"），起点是某个 checkpoint/code 资产，那启动上下文 = 用户的一句话 + trace.csv 中起点的记录。这非常小。

**情况B：任务起点模糊**（起点在 trace 中没有直接记录）

如果任务模糊（"改进系统"），起点不明确，可能需要先加载 README.md 来理解项目全貌，才能确定起点。这时启动上下文 = README.md 全文，导航开销又回来了。

### 7.3 含义

**最小 M 的前提是任务起点明确**。起点越明确，M 越小。起点越模糊，越需要导航开销来确定起点。

这和 akash 阶段1（需求分析）的价值一致——需求分析就是把模糊任务变成明确起点。需求分析做得越好（起点越明确），后续获取最小 M 的成本越低。

**推论**：akash 阶段1 不只是"记录需求"，更是"为最小 M 做准备"——它把模糊任务映射到 trace 图上的明确起点，使后续闭包获取能从策略2跃迁到策略4/5。

## 八、对现有体系的改进方向

如果以上分析成立，现有体系的改进方向是：

### 8.1 trace 闭包遍历算法（对应 006 §2.9 开放问题 #1 #2）

这是从策略2跃迁到策略4/5的关键。不需要完美，只需要足够好地缩小范围。

需要定义：
- 从任务起点出发，沿哪些关系类型遍历？（implements / specified-by / depends-on / part-of / changes / contains ...）
- 遍历几层？
- 不同关系类型是否按工作包性质选择子集？

### 8.2 xpath → 行范围的映射工具

trace 给出 xpath（`path::function`、`path#section`），但加载需要行号。需要一个工具把 xpath 转成行范围：
- `path::function` → grep 函数定义 → 起止行
- `path#section` → grep 章节标题 → 起止行（到下一章节标题前）

这个工具的输出不进 M 主体，只提供加载坐标。

### 8.3 read 工具支持 xpath 精确加载

目前 read 有 offset/limit，可以按行加载。但如果能直接接受 xpath（`path::function`），自动定位行范围，就更顺滑。

实现方式：read 接受 xpath → 内部调用 §8.2 的映射工具 → 自动转换为 offset/limit → 加载。

### 8.4 三层体系的角色转变

从"导航工具"变成：
- **trace 不可用时的 fallback**——trace 没覆盖的资产，回退到三层体系导航
- **闭包成员的组织形态**——trace 给出 xpath 集合后，三层体系把 xpath 组织成 AI 可读的加载路径（§2.3.1 的认知组织维度）

三层体系不再是最小 M 的获取手段，而是闭包成员的**组织形态**（把 xpath 集合组织成 AI 可读的加载路径）。

### 8.5 改进优先级

务实路径：先策略5（低工程成本，立即改善），再策略4（高工程成本，理论最优）。

1. **P0：trace 缩小范围能力**——确保 trace 能可靠地缩小文件范围（策略3/5的基础）。这依赖 trace 幂等正确，是现有体系已经在维护的。
2. **P1：xpath → 行范围映射工具**——让加载能精确到函数/章节（策略4的基础）。
3. **P2：read 支持 xpath 精确加载**——让 xpath 精确加载顺滑化。
4. **P3：trace 闭包遍历算法**——从"缩小范围"升级到"精确闭包"。
