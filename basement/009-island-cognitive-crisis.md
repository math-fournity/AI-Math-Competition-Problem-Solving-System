## 一、用户原话（完整保留）

> 其实如果仔细想想，是否每一轮对认知包的迭代，都会忽略到一些最终应该进入工作包的认知闭包的内容呢？这是非常可能的。我们不妨把trace中的矩阵全体元素看成是一片海洋，我们会发现，这片海洋之中，存在着岛屿。也就是说，从比如一个view-1出发，AI开始为了一个工作包，开始连续地利用trace形成一个有一个的认知动力过程中的认知包。可是这个view-1，配合trace，无论如何都是无法到达另外一个比如目录下的内容的。这种情况是很有可能存在的。所以对于repo中的各种元素，所构成的trace矩阵中的不同的岛屿，可能需要单独处理每个岛屿。或者我们有一种系统化的分类学，让AI去遍历这个多view构成的分类，最终也可以完成对每个岛屿的处理。比如说，最基本的，处理每一个repo的子目录，因为它们都是一种特殊透视系统的view，它们也算是从无理文件夹上，把系统划分成个各个岛屿。但是值得指出的是，最好是每个递归的子目录，都有一个README，每个README，AI在连续的认知动力过程中都要去遍历，这样才能保证大的岛屿不丢，大岛屿中的各个小岛屿，也不丢，也就是说："孤岛认知危机"，不是仅仅在最高层能看到，在任何一个套娃层次中，都可能出现。

## 二、AI 的理解

### 2.1 你发现的问题：闭包收敛 ≠ 闭包完备

008 的收敛判据是 `n[x] = n[x+1]`——一代探索后没有加入也没有移除，就算收敛。但岛屿隐喻揭示了一个致命问题：

**如果起点在岛屿 A 上，无论迭代多少代，n[x] 永远不会包含岛屿 B 上的任何内容。而收敛判据照样满足——因为没有新成员加入，n[x] = n[x+1]——但 N 是不完备的。**

这不是"收敛太慢"，是"收敛到一个错误的终点"。闭包遍历的数学性质保证了**连通分量内的完备性**，但不保证**跨连通分量的完备性**。trace 关系图如果有多个连通分量（岛屿），从一个岛屿出发永远到不了另一个。

这比 006/007/008 识别的所有问题都更严重——那些问题都是"在一个连通分量内如何做到完备/高效/收敛"，而你指出的是"**连通分量本身可能被遗漏**"。

### 2.2 岛屿从哪来——trace 关系图出现 disconnected components 的原因

1. **trace 关系缺失**——两个资产本应有关系但没录入 trace。这是 trace 幂等维护的漏洞。
2. **关系类型不被遍历**——闭包遍历算法选择只走某些关系类型（如 implements/depends-on），不走另一些（如 changed-in），导致本应连通的资产被切断。
3. **目录结构天然分区**——repo 的子目录本身就是一种分区。如果跨目录的 trace 关系没录入，目录之间就是岛屿。
4. **新资产未录入 trace**——新增的代码/文档如果没有录入 trace 关系，它就是一个孤立节点（单节点岛屿）。

### 2.3 你的解法为什么对——目录结构作为不依赖 trace 的分类学

你说"每个递归的子目录都有一个 README，AI 在连续的认知动力过程中都要去遍历"——这个解法的精妙之处在于：**它用目录结构作为不依赖 trace 的分类学。**

trace 可能不完整（有遗漏的关系），但目录结构是**事实层**（006 §3.4 的术语）——它物理存在，不依赖任何索引的维护质量。即使 trace 完全坏了，目录结构仍然把 repo 分成了可遍历的岛屿。

这意味着：**目录结构 + README 是 trace 的 fallback 分类学。** trace 好用时，trace 闭包遍历高效精确；trace 有岛屿时，目录结构遍历保证不遗漏整片大陆。

### 2.4 "套娃"是精髓——递归的孤岛

你说"孤岛认知危机不是仅仅在最高层能看到，在任何一个套娃层次中都可能出现"——这是整个洞察最关键的部分。

如果只是顶层有岛屿，那遍历顶层子目录就够了。但你说的是**递归的岛屿**：

```
repo/
  README.md          ← 顶层岛屿入口
  src/
    README.md        ← src 岛屿入口
    module_a/
      README.md      ← module_a 子岛屿入口
      utils/
        (没有README)  ← utils 子子岛屿，无入口 → 孤岛！
    module_b/
      (没有README)    ← module_b 子岛屿，无入口 → 孤岛！
  docs/
    README.md        ← docs 岛屿入口
    specs/
      (没有README)    ← specs 子岛屿，无入口 → 孤岛！
```

每一层都可能有岛屿，每一层的岛屿都需要入口（README）。如果某一层缺 README，那层之下的所有内容对该层来说都是孤岛——即使上层 README 遍历了，也无法进入没有入口的子岛屿。

这要求 **README 是递归的、全覆盖的**——每个子目录都有 README，每个 README 都索引该目录的直接子目录（让 AI 知道有哪些子岛屿），形成一棵完整的入口树。

### 2.5 和三层体系的关系——从顶层推广到递归

这其实是把三层体系**从顶层推广到递归**：

| 现有三层体系 | 递归推广 |
|---|---|
| AGENTS.md（顶层铁律） | 每层目录的 README（该层岛屿的入口） |
| README.md（顶层分类法索引） | 每层 README 索引该层子目录（子岛屿分类法） |
| 看法文件（顶层文档索引） | 每层 README 索引该层文档/代码 |

现有三层体系只在顶层做了一次。你的洞察是：**三层体系需要在每个子目录递归应用**，否则任何中间层的缺入口都会造成孤岛。

## 三、核心概念：孤岛认知危机

### 3.1 定义

**孤岛认知危机** = trace 关系图存在多个连通分量（岛屿），认知动力过程（008）从一个岛屿出发迭代逼近 N 时，永远无法到达其他岛屿上的资产，导致收敛于一个不完备的 N，而收敛判据（n[x]=n[x+1]）无法检测这种不完备。

### 3.2 为什么收敛判据检测不到

008 的收敛判据是"一代探索后没有加入也没有移除"。这个判据检测的是**连通分量内的稳定性**——在当前岛屿内探索完了，没有新发现了，就判定收敛。

但它无法检测**连通分量外的遗漏**——因为从当前岛屿出发根本看不到其他岛屿，"没有新成员加入"既可能意味着"当前岛屿探索完了"，也可能意味着"还有其他岛屿但你看不到"。收敛判据无法区分这两种情况。

### 3.3 和 006 §3.3 问题A 的关系

006 §3.3 问题A 说"AI 的自觉闭包不可靠"——AI 不知道自己缺什么。孤岛认知危机是这个问题在**拓扑结构层面**的具体化：AI 不知道有其他岛屿，不是因为它不够聪明，而是因为**它所在的连通分量在拓扑上不可达其他岛屿**。这是结构性的不可见，不是能力不足。

### 3.4 和 006 §3.4 描述层/事实层一致性的关系

006 §3.4 说闭包必须核对描述层和事实层一致。孤岛认知危机是这个问题在**索引完整性层面**的具体化：trace（描述层）说这些资产有关系，但 trace 没说这些资产和那些资产有关系——而目录结构（事实层）显示它们在同一个 repo 里。如果只信 trace，就会遗漏 trace 没覆盖的岛屿。目录结构遍历是事实层对描述层的纠偏。

## 四、解法：递归 README 遍历

### 4.1 核心思想

**目录结构 + 递归 README 是 trace 的 fallback 分类学。** 在认知动力过程之前（或并行于），先遍历所有岛屿的 README，确保认知包的候选集覆盖所有岛屿。

### 4.2 为什么目录结构是可靠的 fallback

trace 可能不完整（有遗漏的关系），但目录结构是**事实层**——它物理存在，不依赖任何索引的维护质量。即使 trace 完全坏了，目录结构仍然把 repo 分成了可遍历的岛屿。

目录结构的可靠性来自：
- **物理存在**——文件系统是 ground truth，不依赖维护
- **全覆盖**——每个资产必然在某个目录下，不存在"不在任何岛屿上"的资产
- **递归可遍历**——从根目录出发，递归遍历所有子目录，必然覆盖所有资产

### 4.3 README 作为岛屿入口

光有目录结构不够——目录结构只告诉你"有哪些子目录"，不告诉你"这些子目录里有什么、和当前工作包是否相关"。README 是岛屿的入口，它提供：

- **该岛屿有什么**——这个子目录里的文件/代码/子目录
- **该岛屿讲什么**——这个子目录的知识主题
- **该岛屿和当前工作包是否相关**——AI 据此判断是否需要深入这个岛屿
- **子岛屿入口**——这个子目录下还有哪些子目录（递归）

没有 README 的子目录是"无入口岛屿"——AI 知道它存在（目录结构可见），但不知道它里面有什么、是否相关，无法决定是否深入。

### 4.4 递归 README 要求

**每个子目录都有 README，每个 README 索引该目录的直接子目录和直接文件。**

这形成一棵完整的入口树：
```
repo/README.md
  → 索引 src/、docs/、monitoring/、scripts/、checklist/、working-packages/、dev-docs/
    → src/README.md
      → 索引 module_a/、module_b/、config.py、...
        → src/module_a/README.md
          → 索引 utils/、core.py、...
            → src/module_a/utils/README.md
              → 索引 helper.py、constants.py、...
```

每个 README 只索引**直接子目录和直接文件**（不跨层），但递归遍历整棵树就能覆盖所有资产。

### 4.5 套娃层次的孤岛

用户的核心洞察："孤岛认知危机不是仅仅在最高层能看到，在任何一个套娃层次中，都可能出现。"

这意味着：
- 顶层 README 遍历了 src/、docs/，但 src/module_b/ 没有 README → module_b 是 src 层的孤岛
- src/README.md 遍历了 module_a/、module_b/，但 module_a/utils/ 没有 README → utils 是 module_a 层的孤岛
- 任何一层的缺 README 都会让该层之下的内容成为孤岛

**因此 README 必须是递归全覆盖的**——不是只有顶层有 README，而是每个子目录都有 README。任何缺失都会在该层造成孤岛。

## 五、对认知动力过程（008）的修正

### 5.1 008 的缺陷

008 的认知动力过程假设：从起点出发，沿 trace 追溯链迭代逼近，最终收敛到 N。这个假设在 trace 关系图是连通图时成立，但在有岛屿时不成立——收敛于一个不完备的 N 而收敛判据无法检测。

### 5.2 修正：增加岛屿遍历阶段

认知动力过程需要增加一个**岛屿遍历阶段**——在闭包迭代之前（或并行于），先遍历所有岛屿的 README，确保认知包的候选集覆盖所有岛屿：

```
阶段0（新增）：岛屿遍历
  → 递归遍历所有子目录的 README
  → 每个岛屿至少有一个代表成员进入 n1 的候选集
  → 确保 n1 的候选集覆盖所有岛屿（不遗漏整片大陆）

阶段1+（原有）：闭包迭代
  → 从 n1 出发，在每个岛屿内部做闭包遍历
  → n1 → n2 → ... → N
```

没有阶段0，闭包迭代可能在一个岛屿内收敛而遗漏其他岛屿。有了阶段0，n1 至少在每个岛屿上有一个锚点，后续闭包迭代可以在每个锚点周围展开。

### 5.3 两个阶段的关系

- **阶段0（岛屿遍历）**：保证**跨岛屿的完备性**——所有岛屿都被纳入候选集。用目录结构 + 递归 README，不依赖 trace。
- **阶段1+（闭包迭代）**：保证**岛屿内的完备性**——每个岛屿内部的闭包成员被精确确定。用 trace 追溯链迭代逼近。

两者解决不同层面的完备性问题：阶段0 解决"有没有遗漏整片大陆"，阶段1+ 解决"大陆内部有没有遗漏具体资产"。

### 5.4 阶段0 和阶段1+ 可以交替

阶段0 不必完全在阶段1+ 之前完成。可以：
- 阶段0 遍历顶层 README → 发现 src/ 可能相关
- 阶段1+ 在 src/ 内部做闭包迭代 → 发现需要深入 src/module_a/
- 阶段0 遍历 src/module_a/README.md → 发现 module_a/utils/ 可能相关
- 阶段1+ 在 utils/ 内部做闭包迭代
- ...

这是**岛屿遍历和闭包迭代的交替**——和 006 §2.3 修正后的"启动与封闭可交替迭代"一致。目录遍历（启动）和闭包迭代（封闭）也是两个可反复交替的算子。

## 六、对现有体系的含义

### 6.1 递归 README 规范

现有体系只在 repo 根目录有 README.md（分类法索引）。你的洞察要求：

**每个子目录都有 README.md，每个 README.md 索引该目录的直接子目录和直接文件。**

这是对 read-sync skill 的扩展——read-sync 不只维护根目录 README，还要维护所有子目录的 README。或者更准确地说，read-sync 需要一个"递归模式"——递归遍历所有子目录，确保每个子目录都有 README 且 README 索引完整。

### 6.2 read skill 的递归化

现有 read skill 从根目录 README.md 出发，加载看法文件，再加载具体文档。你的洞察要求 read 可以从**任意子目录的 README** 出发——当 AI 在认知动力过程中深入到某个子目录时，它应该加载该子目录的 README（而不是回到根目录 README）来了解这个子岛屿。

### 6.3 trace.csv 的孤立资产检测升级

现有 trace_verify.py 检测"孤立资产"（无任何 trace 关系的资产）。但孤岛认知危机揭示的是更广的问题——不只是孤立节点，还有**孤立连通分量**（一组资产内部有关系，但和其他资产没有关系）。

需要升级孤立资产检测：
- **孤立节点**（单节点岛屿）——现有检测已覆盖
- **孤立连通分量**（多节点岛屿）——需要新增检测：哪些连通分量之间没有关系？它们是否应该有？

### 6.4 目录结构作为事实层分类学

006 §3.4 说闭包必须核对描述层和事实层一致。目录结构是事实层分类学——它不依赖 trace 的维护质量，是 ground truth。体系应该显式承认目录结构作为一种分类学（虽然粗糙但可靠），并在 trace 不可靠时回退到它。

## 八、开放问题

1. **递归 README 的维护成本**——每个子目录都有 README 是理想，但维护成本高。如何平衡？是否所有子目录都需要 README，还是只有"知识密集"的子目录需要？判定标准是什么？
2. **README 的粒度**——子目录 README 应该多详细？只列子目录和文件名（纯索引），还是带描述（索引+一句话说明）？带描述的话维护成本更高，但 AI 判断"是否相关"更准确。
3. **岛屿遍历的 token 成本**——递归遍历所有子目录 README 本身消耗上下文。如何控制？是否只遍历"可能相关"的子目录（但这又依赖 AI 判断，可能漏）？
4. **孤立连通分量的检测算法**——如何检测 trace 关系图中的孤立连通分量？需要实现连通分量分析工具。
5. **目录结构和 trace 的优先级**——当目录结构说"这个子目录和当前工作包相关"但 trace 说"没有关系"时，信谁？目录结构是事实层但粒度粗（只到目录），trace 是描述层但粒度细（到函数/章节）。
6. **阶段0 和阶段1+ 的交替策略**——§5.4 说两者可以交替，但具体什么时候切换？每代闭包迭代后都做一次岛屿遍历？还是收敛后才做岛屿遍历验证？
