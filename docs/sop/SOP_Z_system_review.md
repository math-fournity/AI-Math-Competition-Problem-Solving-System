## 你要审视什么

上方已经打印了 SOP 系统全貌（11 步循环结构）。思考以下问题：

### 1. 5 步划分是否还合理？

- 健康检查 → alert分类 → AI判断 → 代码修复 → 报告 —— 这个流程是否还自然？
- 有没有步骤太重（做太多事）或太轻（几乎没事做）？
- 是否需要新增步骤（如"环境检查"、"数据备份"、"用户通知"）？
- 是否需要合并步骤（如 alert分类+AI判断 合并）？

### 2. 步骤顺序是否需要调整？

- 当前顺序是先检查再分类再判断再修复再报告。有没有更好的顺序？
- 比如：先修复上轮遗留的问题，再做本轮检查？

### 3. 元检查机制本身是否有效？

- 5 个元检查步骤（01m-05m）是否真的在帮你发现问题？
- 还是它们大多数时候都是"没问题，保持现状"？
- 元检查的频率是否合适（每轮都做 vs 每 N 轮做一次）？
- 是否应该把元检查改为"每 N 轮触发一次"以提高效率？

### 4. _state.json 机制是否可靠？

- 状态文件有没有出现过不一致？
- 顺序校验是否过于严格（阻碍了合理的跳步）？
- `cycle` 计数是否准确？

### 5. SOP 系统与目标系统的适配度

- SOP 循环的节奏（每轮多长时间）是否匹配目标系统（continuation_launcher）的节奏？
- 有没有 SOP 循环太快（重复检查同样的状态）或太慢（alert 堆积）的问题？
- batch_id 是否需要更新（p27-full 完成后切换到新批次）？

### 6. AGENTS.md 中的 SOP 说明是否还准确？

- AGENTS.md 最前面的"Master Agent SOP 流程控制机制"是否和实际机制一致？
- 5 步表格是否需要更新（现在有 11 步了）？
