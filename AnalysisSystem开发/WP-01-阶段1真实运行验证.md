## 任务清单

### 1. 启动系统并发1

```bash
cd analysis-devin-failure-system
../.venv/bin/python3 -m monitoring.continuation_control start --batch-id p27-full --concurrency 1
```

### 2. 观察5道题完整流程

- [ ] 确认launcher启动后从DB读到concurrency=1（日志显示`concurrency=1`）
- [ ] 确认第一道题启动时分配了seq（session名为`p27-s0001-solve-...`格式）
- [ ] 确认session注册表（p27_sessions集合）中有对应记录
- [ ] 确认解题完成后session状态从running→done（DONE.md出现后）
- [ ] 确认handover session也有注册表记录（type=handover）

### 3. 验证seq递增

- [ ] 查DB: `FOR s IN p27_sessions FILTER s._key != 'p27_session_counter' SORT s.seq RETURN s.seq` —— seq应递增无跳号
- [ ] 确认session_counter文档的counter字段递增（不是seq字段——见commit cafd195的修复）

### 4. 验证状态流转

- [ ] 确认session记录有完整的status流转：running→done
- [ ] 确认done状态的session有done_md=true和done_md_at时间戳
- [ ] 确认tmux_alive字段在每轮检查时被更新

### 5. 模拟rate_limited验证stuck不kill

- [ ] 手动构造rate_limit场景（或等真实rate_limit发生）
- [ ] 确认launcher把session标记为stuck而非tmux_kill
- [ ] 确认stuck session在tmux中仍然存在（没被kill）
- [ ] 确认stuck session不占并发槽（launcher继续启动新run）

### 6. 模拟stop --force验证分类处理

- [ ] 在有running session时执行`stop --force`
- [ ] 确认done状态的session被清理（tmux kill）
- [ ] 确认running/stuck状态的session未被kill（提示用户手动处理）
- [ ] 确认Redis队列被清空

### 7. sessions命令验证

- [ ] `continuation_control sessions` —— 列出所有session
- [ ] `continuation_control sessions --status running` —— 过滤running
- [ ] `continuation_control sessions --consistency-check` —— 对比注册表 vs tmux
- [ ] `continuation_control sessions --clean-done` —— 批量清理done的

### 8. A10/A11/A12检查验证

- [ ] 确认monitor_continuation.py的A10（session_registry_consistency）在运行
- [ ] 确认A11（stuck_sessions）在运行
- [ ] 确认A12（done_sessions_uncleaned）在运行
- [ ] 确认这些检查的alert被正确写入p27_monitor_alerts集合

## 验证标准

- 5道题完整流程跑通，seq递增无跳号
- stuck session不被kill，留在tmux中
- stop --force分类处理正确
- sessions命令全部可用
