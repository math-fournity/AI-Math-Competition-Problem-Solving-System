## 三、SOP 拆分粒度合理性分析

### 当前 8 步结构

| 步骤 | 名称 | 检查函数 | 合理性 |
|---|---|---|---|
| 01 | 系统存活+进度+Session | check_01（调 monitor_check_continuation.sh + 门闸 + 行为流水）| ✅ 合理——系统健康是第一步 |
| 02 | 数据完整性 | check_02（全量检查 rounds_log/文件/DB集合/events/prepared堆积/题源完成率/round连续性）| ✅ 合理——数据是基础 |
| 03 | alert分类 | check_03（查未处理 alert）| ✅ 合理——alert 是 01/02 发现问题的入口 |
| 04 | C类AI判断 | check_04（查 needs_ai_review 的 run）| ⚠️ 见下方 |
| 05 | 代码修复 | check_05（显示 git log）| ⚠️ 见下方 |
| 06 | 报告+WORKLOG+Self-check | check_06（显示 WORKLOG 状态）| ✅ 合理 |
| Z | 元检查+整体检查 | check_Z（显示 SOP 全貌）| ✅ 合理——自我进化 |
| OP | 运营知识刷新 | check_OP（环境验证 + 注入运营知识）| ✅ 合理——突破 AGENTS.md 16K |

### 需要关注的点

**04 C类AI判断**：check_04 只查 `needs_ai_review == true` 的 run，但 monitor_exec_launcher.py 从未实现。当前系统中 `needs_ai_review` 标记由 monitor_continuation.py 的 `flag_for_ai_review()` 设置（抽样标记），真正的 AI 判断由 Master Agent 自己做。**这一步实际上是 Master Agent 读 proof.md/HANDOVER.md 做 C1-C5 判断——check 函数只提供候选列表，判断全靠 AI。** 这是合理的设计，但 SOP_04 文档需要明确"判断由你（Master Agent）做，不是由脚本做"。

**05 代码修复**：check_05 只显示最近 5 个 git log——它不做任何修复。真正的修复由 Master Agent 在 SOP_03 分类后决定是否需要，然后在 05 步执行。**check 函数过于简单（只 git log），但这是 by design——修复是 AI 的工作，不是脚本的。** 合理。

**拆分粒度总体合理**：8 步覆盖了"检查→分类→判断→修复→报告→元检查→知识刷新"的完整循环。没有明显冗余或缺失。唯一可考虑的是 03 和 04 的关系——03 分类 alert 时可能已经需要 AI 判断（比如判断 alert 是代码 bug 还是数据问题），04 又做 C 类 AI 判断。但两者对象不同（03 是 alert，04 是 run 的数学正确性），拆分合理。

## 四、todo_write 点检查

### 当前状态

每个 SOP 文档末尾都有"你需要建立的 todo list"段，格式统一：
- 列出该步骤需要做的 todo
- 倒数第二项是"填写 report.md 报表"
- 最后一项固定是"执行下一个脚本: python -m scripts.sop.run"

run.py 的 `print_todo_directive()`（sop_state.py:186-196）也打印 todo 指令。

### 问题

**todo 指令是文本提示，不是自动执行。** Master Agent 需要自己用 todo_write 工具建立 todo list。如果 Master Agent 忽略了文本提示，循环就会中断。这是设计的固有限制——依赖 AI 遵守文本指令。

**无自动验证**：没有机制验证 Master Agent 是否真的建立了 todo list。报表的 report.md 是审计痕迹，但 report.md 本身也需要 Master Agent 手动填写。

**建议**：当前设计可接受（依赖 AI 遵守指令是 SOP 机制的核心假设）。如需加固，可在 run.py 末尾加一句"如果你没有看到 todo list，请现在用 todo_write 工具建立"的强化提示。

## 八、结论

**SOP 机制本身（脚本+流程+状态管理）是健全的**——8 步循环、顺序校验、自驱动 todo、报表系统都正常工作，checks.py 只引用 continuation_* 模块。

**主要问题是认知污染**：SYSTEM_CLOSURE.md 和 SOP_OP 的系统使命描述还是旧 Pipe 1/2/3 的，每次 SOP 执行都注入给 Master Agent，会误导每一步的推理。这是 P0，应优先修复。

**次要问题是残留引用**：大量文档和 checklist 指向已删文件/已废弃文档，Master Agent 按引用去找会找不到或找到过时内容。应批量清理。

**建议修复顺序**：先修 P0（认知污染，2 个文件 4 段内容），再修 P1（残留引用，批量但机械），P2/P3 可后续逐步处理。
