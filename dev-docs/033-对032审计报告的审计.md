## 二、对 032 新发现（E1/E2）与建议的核查

### E1：check_audit_complete 只看 DONE.md — 属实，采纳并扩大范围

代码验证：`proof_audit_launcher.py:192-196`——`done_marker.exists()` 直接 `return True`。
DONE.md 内容是 `echo $?` 的 exit code（devin 退出码），devin 崩溃（exit=1）同样产生
DONE.md。所以 launcher 的 "completed" 语义 = **"devin cli 已退出"**，≠ "审计成功"。
审计是否成功要看 `p27_proof_audits.audit_status`（result_collector 解析 export 后写入）。

**补充（032 未提）**：`:376-390` 的 dead_done 分支（session 消失 + export 存在 → completed）
同样不看 export 内容——E1 的语义歧义覆盖**全部完成判定路径**，不只是 DONE.md 路径。

**落地**：采纳 032 建议，且不止写文档——进 WP-A 的 4 个审计门控 docstring 重写
（GATE-AUDIT-KILL-SESSION 的检查项明确"completed=devin已退出，审计成败看
p27_proof_audits"）+ SYSTEM_CLOSURE 审计段（WP-F 范围）。

### E2：sleep 999999 保 session — 属实，采纳

代码验证：`proof_audit_launcher.py:145-154` 与续传 `continuation_launcher.py:712-721`
同款结构。session 在 devin 退出后不消失是**有意设计**（保 pane 可查、靠 launcher 判定后
kill）。孤儿 session 的根因是"launcher 被杀后无人执行 kill"，不是 sleep 本身。

**落地**：WP-P 补一句说明（032 建议 2 采纳）。

### D3 商榷（小标题分隔）— 接受，零成本

031 裁定 4 要素、【论证依据】含"系统正常运行表现"；032 商榷两者是不同问题（单动作
决策 vs 系统健康判断），建议段内分小标题。**裁定：接受**——固定格式为：

```
【论证依据——放行/不放行判定】
放行/不放行：…（单个动作的决策）
系统正常运行表现：…（此门控处系统健康的样子，异常时如何处置）
```

`extract_checklist` 从"放行前"截到末尾，两个小标题都在闭包内，机制无需改动。

## 三、032 的问题（本文新发现）

### 1. [P1] §7.6 实测声称 2 处与现场不符——真实情况更严重

032 声称（以 `p27-full-deepmath_103k_00001653` 为证）：
- 声称 A："round1 的 export 目录……exports/ 目录存在但里面没有 conversation.json"
- 声称 B："round1 的 export 只存在于 work_dir 的 round1_export.json"

**现场实测**（本文）：
- trajectory 目录下**根本没有 round1/ 目录**（只有 `round2/`）——不是"目录存在但空"
- work_dir 里**也没有 round1_export.json**（只有 problem.txt / proof.md /
  round1_handover_run / round2_prompt.txt）——不是"只存在于 work_dir"
- DB rounds_log 两条记录的 export **都指向 round2**，且轮号重复 `[2,2]`
  （SYSTEM_CLOSURE §3 明示"重复轮号=旧数据或bug复发"——此 run 属 017 修复前入队的
  旧数据残留，round1 条目从未被补录）

**裁定**：032 的核心方向（round1 export 存放不统一）成立，但实测精度不合格——
真实情况是该 run 的 round1 export **两处都没有**（比 032 说的更严重），round1 的
seed 镜像是否还在原 seed_export 路径需 WP-S 的存量盘点确认。这本身是个警示：
**写"实测"就必须真的看了底层**——032 在直接检查铁律的例证文档里犯了间接推断的错。

### 2. [P1] 资产保留铁律的实质漏洞——remove_old_proof 删除从未归档的 partial proof

这是本次审计最重要的发现。链条如下：

**代码事实**：
- `remove_old_proof()`（`continuation_launcher.py:156-162`）对旧 proof.md **直接
  `unlink()`，没有任何归档步骤**
- 归档（`shutil.copy2` → `round{N}_proof.md`）**只在成功轮分支**执行
  （`:1508-1512`，proof_found 时）——无 boxed 的部分证明**从不归档**

**AGENTS.md 新铁律的表述与代码不符**（`AGENTS.md:238`）：
> "唯一允许的删除：remove_old_proof……**但前提是上一轮的 proof 已归档为
> round{N}_proof.md**（门闸检查项 2）"

这个"前提"在代码里不存在：门闸检查项 2 是给 Master Agent 在 **hold 模式**放行前
人工核对用的，auto 模式（常态）下代码直接删。部分 proof（AI 写了证明但没写到
boxed）会被下一轮启动前的 remove_old_proof 无声删除。

**现场实证**：`00001653` 的 `work_dir/proof.md`（3777 字节、无 boxed、DB 状态
dead_session、mtime 08-21 07:02）就是一份待删资产——该 run 一旦重试启动 round3，
这份部分证明即被删除。**用户需求原文**（"无论做出来没做出来……必须每一个 round 都
全部保留"）在这里没有被落地，而 032 的调查摸到了边（"失败轮的 proof.md 没有归档……
如果有部分内容的 proof 也应保留"）却在行动项 1-4 里漏掉了对应措施，AGENTS.md 的
表述反而制造了"已归档前提总是满足"的错觉。

**修复（进 WP-S 行动项 1，两全方案）**：
- `remove_old_proof` 删除前，若旧 proof.md 非空则先归档为
  `round{N}_proof_partial.md`，再删 work_dir/proof.md
- 016 P0-2 的防误判目的不受影响（work_dir/proof.md 仍被删除，新一轮完成判定不会
  撞旧文件）；资产保留目的达成（部分证明留档）
- 门闸 GATE-REMOVE-OLD-PROOF 的 docstring 检查项 2 同步改写（"上轮 proof 已归档
  **或已存为 _partial**"）；AGENTS.md:238 表述修正

## 四、对两条新需求的落地裁定

### 1. "适度依赖 Master Agent 介入"（032 §7.5）— 采纳，但补边界判据

原则正确，且它把 031 的几处设计（WP-N 的 PARSE_ERROR 待人工、WP-J 删 detect_stall
用 max_runtime 兜底）上升成了明确准则。**采纳 032 据此提出的范围收缩**：

| 032 建议收缩 | 本文裁定 | 理由 |
|---|---|---|
| is_thinking / is_devin_waiting_api 不提取 | **接受**（031 原标"可选提取"，改"不提取"） | thinking spin 精细区分需 pane spinner/代理端口检测（后者依赖平凡系统 7897 端口假设），可靠性存疑；Master Agent 用行为流水 + SOP 可见可处。stall 阈值兜底 + retry 上限兜住风险 |
| crash_recovered 不细分 | **接受**（WP-K 从"ai_gave_up + 可选 crash_recovered"缩为**仅 ai_gave_up**） | 细分只提升分类精度，不改变应对（都 infra 可重试）；批量 crash 类异常由 SOP/行为流水发现 |

**但必须补边界**（032 版无边界，"交给 Master Agent"可能被滥用为代码偷懒的借口）。
边界判据（建议补入 AGENTS.md 该硬约束段）：

> **代码做**：规则可机械化 + 单一数据源 + 误判率低的判定（有 proof/无 proof/超时/
> rate_limit 文本模式/ai_gave_up 文本模式——这些是可靠的模式匹配）。
> **Master Agent 做**：需要语义理解、跨源综合、或上下文权衡的判定（proof 数学正确性/
> 审计质量/异常处置方案/是否翻案）。
> 检验一个问题属于哪边：**"这个判定能否写成一个确定性函数并单测覆盖？"** 能→代码；
> 不能→标记"待人工"+alert，绝不硬写启发式。

按此判据自查 031 方案：WP-I 保留的 AI_GAVE_UP_PATTERNS / RATE_LIMIT_PATTERNS /
classify_failure 都过界（确定性模式匹配）；WP-J 删 detect_stall 过界；WP-N PARSE_ERROR
待人工过界。无需再改。

### 2. "解题运行结果资产保留铁律"（032 §7.6）— 采纳，WP-S 修订版

需求正确。但 032 版 WP-S 的行动项不完整（漏 partial proof 归档——本文 §三.2），
且部分"实测"失真（§三.1）。修订后的 **WP-S（6 项）**：

1. **partial proof 归档**（032 版没有，本文新增，最高优先）：`remove_old_proof`
   删前归档非空旧 proof 为 `round{N}_proof_partial.md`；门闸 docstring 检查项 2 同步；
   AGENTS.md:238 "前提是已归档"表述修正（当前该前提在代码中不存在）
2. **round1 export 双写统一**（032 行动项 1）：`overwrite_round1_seed` 除 work_dir
   镜像外，同步复制到 `round1/exports/conversation.json`——与其他轮目录结构一致。
   注意：只对新 run 生效；`00001653` 这类旧数据 round1 export 已两处皆无，无法补救
   （除非 seed_export 原路径仍在，WP-S.6 盘点确认）
3. **SOP_02 升级**（032 行动项 3）：每轮 export 直接存在性检查（含 round1 新路径）——
   checks.py 的 file_checks 已有框架，扩展即可
4. **审计系统产保留**（032 行动项 4）：审计失败（dead_session/stall_timeout）的
   export 有则必留（代码本就不删）；SOP_07 加"失败审计 export 抽样存在性"检查
5. **清理脚本审计**（本文补）：`cleanup_continuation_runs.py` 只删 prepared 的 DB
   记录（无产出、风险低）——加一行守卫注释"绝不删有 rounds_log 的 run"防未来改坏；
   `sim/teardown.py` 维持 018 防误删守卫
6. **存量资产盘点**（本文补）：全量扫描所有 run 的每轮 export 文件存在性（028 做过
   proof.md 维度，这里补 export 维度），量化历史丢失面，结果写入 dev-docs——这既是
   资产盘点也是 SOP_02 升级（项 3）的基线数据
