## 二、后端接口定义（任务 1）

```python
# src/acp/backend_base.py
@dataclass
class BackendTask:
    prompt: str                 # 题目/任务指令全文
    work_dir: Path              # 工作目录
    traj_dir: Path              # 产物落盘目录（通知 jsonl/export 等）
    model: str                  # 从 DB batch 读（铁律15/9：不写死）
    reasoning_effort: str       # 同上（opencode 用；devin 无此概念传 None）
    max_runtime: int

@dataclass
class BackendHandle:
    backend: str                # "ptmux"|"devin_acp"|"opencode_acp"
    session_id: str | None      # ACP sessionId / ptmux 的 session_name
    proc: subprocess.Popen | None   # acp 后端持有；ptmux=None（进程在 tmux 里）
    work_dir, traj_dir: Path
    started_at: float
    last_signal_ts: float       # spin 检测的数据源（双管线通用）

@dataclass
class BackendStatus:
    state: Literal["starting","thinking","tool_running","message_out",
                   "done","failed"]
    detail: str
    last_signal_ts: float
    finish_reason: str | None   # 协议原生收尾原因（Devin stopReason /
                                # OpenCode step-finish.reason）。⚠️ 仅信息性：
                                # end_turn 会掩盖截断（043），成败判据看组装结构

class ExecutionBackend(ABC):
    @abstractmethod
    def start(self, task: BackendTask) -> BackendHandle:
        """启动会话并注入任务。契约：
        - OpenCode：initialize→session/new→set_config_option(model)断言回显→
          set_config_option(effort)断言回显→prompt（铁律15，任一不符抛 BackendError）
        - Devin：initialize→session/new→prompt；校验 task.model 已配置
        - ptmux：构造 devin -p 命令经 tmux 启动（行为与现 launcher 逐行一致）"""

    @abstractmethod
    def poll(self, handle) -> BackendStatus:
        """非阻塞读通知/检查进程，更新 handle.last_signal_ts。
        ptmux 实现 = tmux_running + DONE.md + capture-pane（V3 原样迁移）"""

    @abstractmethod
    def terminate(self, handle, reason): ...
    @abstractmethod
    def done_marker_semantics(self) -> str: ...   # E1 澄清的后端版文案
    @property
    def trunc_comp_threshold(self) -> int: ...    # 实测有效上限×0.96（038§三.三；
                                                  # 以观测校准为准——043 发现 ox-alpha
                                                  # 实际生效 32000 而非宣称 131072）
    @property
    def spin_window_seconds(self) -> int: return 300   # 037 不变量
    @property
    def done_silence_seconds(self) -> int | None: ...  # OpenCode=U5 实测值；Devin=None

    def health_probe(self) -> bool:
        """initialize 握手 5s 超时（切换机制用）"""
```

**产物契约（判定链复用的落点）**：所有后端最终产出 ATIF 同构 conversation.json 喂
原生 is_truncated/is_completed。来源三层（OpenCode）：通知组装（主）→ opencode
export 兜底（须 JSON 校验+重试，043 首次截断实证）→ SQLite 直读（禁作主路径）。

**comp 取数路径（每后端声明）**：ptmux=final_metrics.total_completion_tokens /
devin_acp=prompt response usage.outputTokens / opencode_acp=response usage
（流内 usage_update 为空——043）。

## 三、差异适配层逐点方案（任务 2，8 点）

| # | 差异点 | ptmux（现状） | devin_acp | opencode_acp |
|---|---|---|---|---|
| 1 | 完成检测 | DONE.md 存在 | response 到达（stopReason） | response 到达为主（043 实证会返回）；静默窗口兜底（🔶 U5 定值）+ max_runtime 终兜底 |
| 2 | 权限 | --permission-mode dangerous | request_permission 自动响应 allow_once（客户端实现，U1 已验） | opencode.json `"*":"allow"` 零交互 |
| 3 | session 管理 | tmux kill-session | cancel+terminate（无 close） | close 可用；兜底 terminate |
| 4 | 模型指定 | DEVIN_MODEL 配置常量进命令行 | acp --model | set_config_option（铁律15 断言链）；model/effort 从 DB batch 读 |
| 5 | 推理强度 | 无开关（工具事实） | 无开关 | effort 显式设置+回显断言 |
| 6 | 自定义通知 | — | _cognition.ai/thinking_complete（可用作状态加速） | 无——统一"通知流转变推断，有显式标记时加速" |
| 7 | 错误模式信号 | pane 文本匹配（WP-I PATTERNS） | 通知文本同 PATTERNS 匹配 + stderr | 通知文本匹配 + stderr（真实形态=U5 实测位） |
| 8 | 截断检测分层（038§九） | 结构启发式（rc/msg/tc/comp≥24000） | 第一层 stopReason（若 max_tokens 类值出现则优先）+ 第二层结构启发式（comp≥25000×0.96） | 第一层不可靠（end_turn 掩盖截断——043），以第二层为主：rc/msg/tc 主判 + comp≥实测有效上限×0.96 辅助 |

**截断检测的统一语义（重要修正）**：无论哪层信号，"成功"的最终分界 =
**组装产物 message 非空且含预期产出标记**。end_turn/max_tokens 都只是参考——
043 实证 end_turn 下可能零正文。launcher 判定段消费的是组装后的结构事实。

## 四、管线选择与切换机制（任务 3）

```
配置源：p27_continuation_batches 集合加 backend 字段
  （"ptmux"|"devin_acp"|"opencode_acp"，默认值策略=DB 有则用之，
    批次创建时由 control start --backend 写入或默认 ptmux）
修改命令：continuation_control set-backend --batch-id X --backend Y
  （与 set-concurrency 同构；launcher 每轮 poll 刷新——WP-G 模式复用）
生效边界：只影响后续新启动的任务；running 的任务不迁移

健康探测：backend.health_probe()（initialize 5s 超时）——批次启动时对目标后端
  探一次，失败即报错退出（不自动换）

auto-fallback（设计但默认关闭——用户拍板项）：
  触发：某后端连续 N(=2) 个任务启动失败（非题目性失败）→ 该批次后续任务切备用
  后端重试 + 创建 alert（Master Agent 可见）
  启用方式：DB batch.auto_fallback=true（用户显式开启才生效）
切回：永远人工（Master Agent 决策——适度依赖边界：确定性触发可代码化，
  系统级判断留人）
```

## 五、架构验证：执行后端抽象 vs 备选（任务 4）

| 方案 | 优点 | 缺点 | 裁定 |
|---|---|---|---|
| **A. 执行后端抽象（本方案）** | 业务逻辑零改动复用（2031 行 launcher 的调度/门闸/续传/优雅停止全保留）；三后端行为等价表可穷举；sim 门禁直接适用 | 抽象层本身 ~500 行新代码；接口演进需纪律 | **采纳** |
| B. 新建独立 ACP launcher（复制业务逻辑改启动段） | 无抽象成本 | 两份调度/判定/门闸代码并行演化——036 D6 已裁定"同一 repo 两套机制是分歧源"；每个 bug 修两遍 | 否决 |
| C. 全管线围绕 ACP 重写 | 无历史包袱 | 丢弃 016/017/018 事故换来的防御体系；风险不可控；违反资产保留精神 | 否决 |

工作量佐证（引 044 影响面清单）：tmux 功能点 40 处中仅 12 处属 agent 会话层
（其余为服务编排/注册表/监控口径），后端化的实际手术范围是可控的。
