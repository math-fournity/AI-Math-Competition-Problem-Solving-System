## 三、问题清单

### 1. [方法论] P3-c 的验证是循环论证——结论侥幸成立

034 用"**被判 truncated 的样本** comp 全部 25000"证明"24000 阈值不漏判"。这在方法上
不成立：`is_truncated` 的判定条件本身就要求 comp≥24000——被判 truncated 的样本
comp≥24000 是**构造性必然**，不构成"不漏判"的证据。真正的检验应该查 **dead_session
样本中是否存在截断特征但 comp<24000 的**（被漏判者落在那里）。本文做了这个检验：
当前 batch 的 dead_session 仅 1 个样本——**无法从该维度证实或证伪**。

结论仍然成立，但依据换血：39 处 comp 恒=25000（无一例外）是 **devin cli 输出硬上限
= 25000 的证据**——"因输出上限截断"必然 comp=25000 > 24000，不会漏判。"因上下文
不够"的情形（input+output 超 200K）表现为 API 报错（走 connection/dead 路径），
不是静默截断。所以当前配置下漏判风险确实极低；033 的"实验验证项"保留（防 devin cli
升级改变上限），但 034 的验证过程应在文档中标注为"循环论证，结论由硬上限证据另行支撑"。

### 2. [P1] 035 内部矛盾——§六 与 §四/§七 给出相反的行动指引

035 是两阶段写作（初版 + 实测后更新），更新时没有清理初版结论：

- **§四.2 / §七（更新版）**："首选方案1（ACP）……放弃方案2（交互模式）"
- **§六 末尾（初版遗留）**："**不建议立即推进 WP-U**——改造量大，且**方案2（交互模式）
  能快速解决短期问题**。WP-U 作为长期方案，在**方案2验证成功后再考虑**"

两段直接冲突。034 引用 035 时（"034 此处不再重复 035 的内容"）没有发现。风险：未来
AI 读 035 §六 会得出"先做方案2"的相反行动。**必须修**：删除 §六 过时段落，或整段
标注"⚠️ 初版遗留，已被 §四/§七 取代"。

同源的数字混乱：§4.2"补充 200-400 行"、§4.3 路线图"总计 400-670 行"、§六 WP-U 表格
"总计 840-1370 行"——三个估计并存。收敛口径：以 §4.3 路线图（400-670）为准，§六
表格随矛盾段落一并清理。

### 3. [P1] 035 §5.1"实时 trajectory 采集"夸大——检测可用 ≠ 采集完整

035 实测2 的 22 个 `agent_thought_chunk` 总内容量极小（单词级分片，首个内容就是
"The"；√2 题 thinking 全程约 1 秒/约 22 词）。而 `--export` 的 reasoning_content
对 glm-5-2 数学题动辄几千至几万字符（本 repo 截断案例 rc=70632 字符）。

**必须区分两件事**：
- **卡死检测（WP-T.1）**：只需信号**存在性**（有 chunk 流=活着）——实测已验证 ✅
- **trajectory 采集（035 §5.1"实时落盘 trajectory"、WP-U.4"组装 conversation.json"）**：
  需要**内容完整性**（ACP 推送 ≈ export 的 reasoning_content）——**未验证**。22 词/1 秒
  的样本既可能是"该题 thinking 本来就短"，也可能是"ACP 只推送 thinking 的开头/摘要/
  低 thinking level 版本"。不能排除。

**处置**：WP-U.9（"对比 ACP 采集与 --export 的一致性"）**前置为 WP-U 的第一个实验**——
用一个真实长 thinking 数学题（现有 138 题任选）分别在 `-p` 和 ACP 模式跑同题，
对比 reasoning_content 字符量与内容。此实验不过，§5.1 的采集愿景和 WP-U.4 的组装
方案都要降级（ACP 只做检测+实时状态，trajectory 仍靠 --export）。

### 4. [新发现] 平凡系统 is_thinking 在 -p 模式下系统性失效——034/035 均未追究

034 调查4 确认"THINKING_PATTERNS 是 TUI 渲染产物、-p 模式不渲染"，但只把它当本
repo 的事。实际上：**平凡解题系统也是 `-p` 模式**（`solver_harness.py:615`
`devin -p '{prompt}' ... --export ...`）。

推论：平凡系统 `collector.py:154-170` 的 `is_thinking()` 第一条路径（THINKING_PATTERNS
匹配）在 `-p` 下**永远 False**——只剩数学内容计数路径（且要求 pane 里已有输出文本，
thinking 期间没有）。因此平凡系统的 `failed_thinking_spin` vs `failed_timeout` 区分
（`collector.py:394-402`：超时后靠 is_thinking 分流）在 `-p` 模式下**系统性失效**，
thinking_spin 历史数据大量实际落在了 failed_timeout。

影响与处置：
- 进一步支持 031/033"WP-I 不提取 is_thinking"的裁定（连来源系统自己的这个检测在
  `-p` 下都失效）——写进 WP-I 背景
- **数据使用警告**：未来若用平凡系统数据做 Profile/能力边界分析，`failed_thinking_spin`
  维度不可信——记录到 031 的平凡系统引用注意事项（033 已记录过平凡系统 INFRA_FAILURES
  两处不一致，此为第二项）

### 2. WP-U（ACP 管线全面改造调查）——接受启动，范围必须补 3 项

034 的 8 点调查范围合理但有两个**硬遗漏**和一个**顺序问题**：

**a. sim 模拟系统适配（硬依赖，034 完全没提）**：
铁律 12（改调度逻辑后跑 sim 发布门禁）——ACP 改造是本系统**最大的调度逻辑改动**，
`src/sim/fake_devin.py`（剧本演员）必须先改造成 ACP server 形态（或写 ACP 模式的
新演员），否则 sim 门禁无法运行、launcher 改造无法验证。**sim 适配应列为 WP-U
调查范围第 0 项**（影响面+改造方案+剧本适配工作量），且是后续任何 ACP 改造的前置。

**b. tmux 依赖体系影响面（034 范围1 只覆盖"devin -p 启动位置"，严重低估）**：
ACP 化消灭的不只是"启动命令"，而是整个 tmux 存在性体系。需逐一调查：
- `session_registry` 的 `tmux_alive` 检查 / SOP_01 SESS 一致性检查（注册表 vs tmux）
- **A13 四源一致检查**（tmux 实际数是四源之一——ACP 化后变"三源+ACP 进程源"，
  整个 A13/SOP_01 检查体系要重新定义）
- `monitoring/continuation_control.py` 的 sessions 管理/stop（kill-session 语义）/
  watchdog 脚本
- 门闸 `resource="tmux"` 的 kill_session 语义（GATE-KILL-SESSION/GATE-AUDIT-KILL-SESSION）
- SOP_07 检查项 7（孤儿审计 session 对账）、E2（sleep 999999 设计）——ACP 下不存在
- `crash_recovered`/`dead_session` 判定依据（session 消失=tmux 死）在 ACP 下的等价物
  （subprocess 退出码/stdin 关闭）
- 行为流水 observability 的 session_name 维度

**c. 顺序问题**：内容完整性实验（本文 §三.3）前置为 WP-U 第一步——它决定 WP-U.4
（conversation.json 组装）是否存在，进而决定改造是"全面 ACP 化"还是"ACP 只做
检测层、execution 层保留 -p"两种截然不同的方案。**这个分叉应在调查开始时先探明，
否则 WP-U.2~U.7 的工作量估计都建立在未验证的假设上。**

补充后的 WP-U 范围（034 的 8 点 + 本文 3 点）：**0**. sim 适配 · **0.5**. ACP 内容
完整性前置实验 · 1~8. 原 034 范围（第 1 点扩为"tmux 依赖体系全量影响面"）。

## 六、最终结论

1. **034/035 的事实层全部独立复现通过**——session.db 一次性写入、pipe log 占比、
   ACP 信号流、权限处理、comp=25000（39 处，比 034 的样本更强）。用户的两级洞察
   （session.db 不落盘 → ACP）有扎实的实测支撑。
2. **方法层一处不合格**：P3-c 循环论证（结论侥幸成立，依据已换血为硬上限证据）。
3. **文档层一处必修**：035 §六 初版遗留与 §四/§七 矛盾——给出相反行动指引。
4. **愿景层一处夸大**："实时 trajectory 采集"未经内容完整性验证——WP-U.9 前置为
   第一步实验，实验结果决定改造方案分叉。
5. **两个新发现**：平凡系统 is_thinking 在 -p 下系统性失效（数据使用警告）；
   WP-U 漏 sim 适配（硬依赖）。
6. **裁定**：WP-T 接受（T.2/T.3 降级可选）；WP-U 接受启动（范围补 0/0.5/扩大 1）；
   执行结构按 §五 两线并行——**线1 的 WP-P~S 不等 ACP**。

**审计链 030→031→032→033→034(+035)→036 至此收敛。等用户批准后执行。**
