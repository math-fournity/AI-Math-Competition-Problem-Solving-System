## 三、采纳保留意见一：既有语义与新增 schema 必须分开

这是外部审计最重要的意见，完全采纳。

### 3.1 从 053 恢复的不可退化语义

以下属于 053/1962 的既有要求，后续 adapter 不得删除：

- observer 获得完整原始现场，而不是只有摘要；
- observer 亲自使用 reader；
- 第一层廉价概览；
- thinking/reasoning 尾部收殓；
- 稳定定位后定点读取；
- reasoning、tool 实证和 error 可核实；
- map、HANDOVER、notes 只能作索引；
- solver 默认不通读完整历史；
- backend 切换不能使 observer 的核心认知能力退化。

### 3.2 065 新增的工程设计决策

以下不是 053 原文字面规定，而是 065 为跨包闭环新增的 schema v1：

- `schema_version=1`；
- `command_prefix`、`trajectory_root`；
- 八个 capability 字符串；
- scan row 的九个必需字段；
- `trajectory_reads` 的具体 JSON 形态；
- 共同命令使用 `inspect` 名称；
- `--tool-input/--tool-result/--error` 等确切 flag。

这些决策有充分来源：

- `oc-trajectory` 的 scan/tail/search/read；
- `zcode-trajectory` 的 scan/idx/inspect；
- ACP runtime 的 reasoning/message/tool/error/usage/终因；
- 系统“过程证据+直接检查”铁律。

但它们仍然是新的具体化，不能被描述为“053 原文逐字段恢复”。

### 3.3 正式稳定性裁定

```text
语义不变量：冻结，不得退化
字段和CLI：schema v1，经真实adapter验证后可最小演进
```

允许 WP-02/07/12 根据实测调整：

- 字段名和 JSON 层次；
- `inspect` 是否命名为 `read`；
- scan 是一个命令还是拆成事件概览与 reasoning 段落概览；
- usage/finish/error 位于 scan 主行还是 runtime metadata；
- OpenCode/Devin 的 source reference 表达。

不允许借 schema 调整删除：

- 完整原始数据；
- scan/tail；
- 稳定定位；
- reasoning/tool/error 下钻；
- observer 实际使用证据；
- backend 能力不退化。

因此，不把 `trajectory_reader_contract.py` 当成不可变最终标准，也不把它降级成可随意忽略的
参考草案。准确称谓是：

> 语义冻结、字段版本化、待真实 adapter 验证的 v1 机器合同。

## 四、进一步技术校准：当前 v1 可能混合两个层次

外部审计指出，053 的 `oc_traj scan` 与 065 的 scan row 范围不同。这个提醒成立，并揭示了
真实 adapter 需要验证的一个设计点。

### 4.1 Reasoning 内容层

原始 `oc_traj` 主要面向 `thoughts.jsonl`：

```text
段号
字符/行范围
字符数
首句
tail
search/read
```

### 4.2 Runtime 事件层

`zcode_traj` 和 ACP 通知还包含：

```text
model call / turn / notification
role / time / usage
finish reason / provider error
tool call / result / permission
pending / retry
```

当前 v1 合同把两者综合到一个 scan 能力中。真实 OpenCode adapter 可能选择：

```text
方案A：一个scan输出异构但统一idx的事件
方案B：scan-events + scan-reasoning两层
方案C：scan输出事件，inspect内部再提供reasoning段落索引
```

选择标准不是接口漂亮，而是：

- 流式处理大数据；
- 不展开大正文；
- 来源可回溯；
- observer 使用成本低；
- fake/真实测试可验证。

所以 WP-02/07 实施时可以调整 v1 字段，但必须写证据和迁移测试。

065 §一把 WP-02 概括成“只验 notes 结果”，语气偏重。

因此今后引用 065 时应使用上述准确表述，而不是说 WP-02 完全没有过程要求。

## 六、采纳保留意见三：问题必须按严重度分级

外部审计正确指出，WP-03 的实物退化与 WP-08 的预防性风险不能等权并列。

### C 级：预防性闭环增强

其中 WP-08 纠偏前已经有较客观的 evidence package；本次主要是固定数据源和防止重复建设，
不应描述成已发生设计失败。

### 不受影响、明确不扩项

#### WP-01、WP-04、WP-06、WP-09

这些包的核心职责与 trajectory reader 正交。本次总控“不负责 reader”的说明用于防止范围
膨胀，不表示它们原来有缺陷。

## 七、采纳保留意见四：责任在工作包设计，不在初次实现者

初次 WP-03 实现者完成了当时 checklist 的全部七项，测试也与 checklist 一致。它没有违反
明确规格。

真正问题是：

```text
触点段承诺reader
  但
实施任务和验收checklist没有把reader变成闭环项
```

所以这是规格/工作包设计缺陷，而不是实现者擅自省略需求。

因为工作包设计者与初次实现者都是当前实现 AI，这个区分不用于转移责任，而用于建立正确的
工程事故分类：

- “实现不符合规格”和
- “规格本身不闭合”

需要不同修复方法。本案属于后者。065 中“完成状态判早”应理解为工作包验收闭包判早，而非
初次实现者草率。
