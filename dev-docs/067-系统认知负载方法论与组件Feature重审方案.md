## 一、问题起源与核心归因

065 修复了"分层 trajectory 要求被有损压缩"的具体缺陷，066 校准了 065 的边界。但两者都没有
回答更根本的问题：**为什么架构 AI 对系统整体的认知得到用户认可，对最核心的观察者/解题者
内核却出了错？**

用户归因（经调查验证成立）：**认知负载加载不充分**。

- 整体认知之所以立得住：用户全程裁定陪跑（057 自述"需求来源：用户对 031~056 演进的连续
  裁定"）——用户无意间引导架构 AI 加载了建立整体认知所需的上下文。
- 内核认知之所以失败：内核的实践现场**从未被加载**。调查确认以下资产全部在盘、且在
  057~064 与 12 工作包中**一次都未被引用**：
  - 1962 发明史完整现场（`v2run/rounds/round1..6/`、v1 HANDOVER 尸体、v2 演化模板）；
  - 本 repo v2 管线六题实际运行产出（`/Volumes/data/math-agent-glm5.2-tmux-agents-trajectory/
    v2-continuation/`：2 题完成含一条 8 轮成功链、2 题九轮耗尽——递归消化链衰减的第一手
    数据，正是 053 §11.4 自认未量化开放问题的答案所在）；
  - reader 工具本体与范式原型（`oc_traj.py`、`zcode_traj.py`）；
  - 史前层资产（`v2/poc25c_experiment_design.md`、`poc1rev_driver.py`、
    `hintinstance_candidate*.md`——连 053 都未记录）。

**机制命名**：认知与信任同理，不通过文档自动传递（053 §1 的核心规律在设计过程中复发）。
架构 AI 对 053 做的事，正是 v1 接手者对 HANDOVER 做的事——读了摘要、引用了结论、没有下钻
原始现场。053 对架构 AI 而言就是一份 HANDOVER。

## 二、方法论总纲

```text
侧一（自顶向下）：系统 → 组件圈定 → 每组件"要看清什么"（判据）
                  → 该组件的认知负载清单
侧二（自底向上）：repo 内外全部现存资产（文档/代码/提示词/运行产出/外部依赖）
                  → 逐一归位：它属于哪个组件的认知负载
合拢            ：对账矩阵（绿/红/黄三色）
最终产物        ：有证据链背书的 Feature List（四要素结构）
                  → 反向裁决 12 工作包体系的裁剪与排序
```

一句话：**先看清，再裁剪，最后才谈实现。**

## 三、"看清"的定义与判据（侧一核心）

看清一个对象 = 能回答它的三类问题：

1. **存在论**：它为什么存在？没有它会怎样？（教训/反例锚）
2. **机制论**：输入→行为→输出的具体链路是什么？
3. **边界论**：它在什么条件下失效或多余？

| 层 | 要看清的对象 | 验收判据（答不出=未看清） |
|---|---|---|
| L0 系统 | 三重目的（解题/真理性验证/资产采集）的权重；边界；**当前真实水平** | "系统解决了什么手动方式解决不了的问题？""现在实际什么水平？" |
| L1 内核 | HANDOVER 必败根因；角色合同与递归消化链机制；真实效能与衰减形态 | "一条观察者论断从 trajectory 到笔记的完整生成链？""885 九轮比三轮衰在哪？""什么题观察者是纯开销？" |
| L2 支撑组件 | 各自的存在/机制/边界（窗口、形式化、key、stuck、并发、sim、资产） | 每组件 1~2 个"为什么存在+何时失效"，锚到教训 |
| L3 横切 | 生产管线实况；教训链（事故→铁律映射）；文档活性 | "p27 一题从入题到终态经过哪几站？""每条铁律背后是哪次事故？" |

判据问题的共同要求：**L1 判据必须只能从现场回答**——用文档能回答的判据形同虚设。

## 七、对账矩阵与三色处理

- **绿** = 组件认知需求有实物支撑（两侧对上）；
- **红** = 认知需求无实物来源（实践缺口：去跑实验/查现场，或需求降级）；
- **黄** = 实物无组件认领（归档历史/退役/侧一漏了组件）。

初判：红 2 项（用户裁定无载体、生产/外部实况未盘点）；黄 3 类（tmp/、历史文档群、史前层）。

**结构性发现**：所有此前无主的资产**全部属于内核**——与"认知负载分布极不均匀"互为镜像。
正因为内核的现场从未被归入任何组件清单，它们才无人认领；正因无人认领，架构 AI 才会漏掉。
两侧对账把这条因果链闭合。

## 八、Feature List 重审（最终产物）

不是从零重写 058，而是给每条 Feature 补齐**四要素**：

1. 验收语义（058 已有，可继承）；
2. 存在依据（存在论：教训或反例锚）；
3. 认知来源（对账矩阵中具体资产，精确到文件）；
4. 验证方式与状态（已验证/待验证/仅设计）。

示例：

> **Feature**：观察者必须实际执行分层 reader（scan→tail→按需 inspect），map 仅辅助
> - 存在依据：有损压缩税（053 §1；v1 HANDOVER 尸体）
> - 认知来源：R3 现场工具轨迹、885 九轮笔记锚点实况、`oc_traj.py` 本体、
>   `053a-prompt_observer.md` 原文、065 教训（map-only 反例）
> - 验证：trajectory_reads 证据 + map-only 被门禁拒绝
> - 状态：语义已验证（1962+1160）；字段级合同待真实 adapter 验证（066 §3.3）

**提示词是一等来源**：内核组件的可执行规格就是提示词——模板中每句必须/禁止都是 Feature
原始形态；模板演进序列（roundN 混合版→专职三版→v2→v3 两代）即 Feature 变更史。

**重审流程**：058 逐条过四要素。RND/AST/REL/OBS 等乙类域多有代码与生产背书，快速过；
重审集中在 ORCH/PRM/FML（内核+形式化域）约三十条——负载分布规则的再次体现。

**工作包裁决**：丙类组件若 Feature 全为"待实践验证"色，降级或推迟；工作包从"规划执行
单元"变为"Feature 集的实现批次"。

## 九、防过度设计边界

1. 不新增流程、Gate、SOP 步骤、数据库或服务平台；本方案是文档 + 一条开工约定。
2. 深度分级硬约束：重流程只用于内核；侧二不到文件级不罢休仅限内核资产。
3. 每条清单项须有教训或实物背书；无背书的项不进清单（清单自身不预支想象需求）。
4. 本文档不随讨论扩张——后续演进走执行记录，不扩本篇。
