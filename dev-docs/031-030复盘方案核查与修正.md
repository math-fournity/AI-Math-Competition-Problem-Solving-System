### B 组：030 分析错误，方案修正

**B1. 续传系统有优雅停止（030 §5.5 差距表"❌"错误）**

时间线证据：
- `monitoring/graceful_shutdown.py` 创建于 08-20 01:36 前（早于审计系统两天）
- `docs/architecture/graceful-shutdown.md`（178 行）是成体系的文档，§6 就是"新 Pipe 如何实现"清单
- `continuation_launcher.py:984` `register_shutdown("continuation_launcher")`；`:1049-1061` 主循环 `should_stop()` 检查（不再取新题，等 running 完成）；`:1205` dequeue 循环条件含 `not should_stop()`
- `stop_batch()`（`:1932-1994`）优雅/强制两种模式；`monitoring/continuation_control.py:318-320` stop 命令发 SIGINT
- git `64b027e`（08-21 00:18）还修过 stop_batch 的 NameError——机制在被使用和维护

结论：审计系统的优雅停止**应按 graceful-shutdown.md §6 的六步清单实现**（register_shutdown
+ 主循环 should_stop + dequeue 条件 + stop_batch 两模式），与续传系统同构。030 §6.5 的
Redis `paudit:stop` 键方案废弃——同一 repo 两套停止机制是分歧源。

**B2. 续传的 token_limit 已被 is_truncated 覆盖（030"未覆盖"错误）**

平凡系统 `failed_token_limit` 检测的是 pane/pipe 文本模式（"Send a message to continue"
等，`collector.py:87-88`）。续传系统检测的是 export JSON 的**结构化指标**：
`is_truncated()`（`continuation_launcher.py:229-254`）：rc>1000 且 msg=0 且 tc=0 且
comp≥24000 → 截断。且 017-sim P0 修复（git `f5d89e7`）后**截断判定先于 dead 判定**
（`:1524-1536` 注释即此修复的说明）。token 用完的 devin cli 会被正确判为 truncated 并
重入队续传——处理优于平凡系统（平凡标 failed_token_limit 不重试，续传启动下一轮接力）。

**B3. invalid_tool_use 不适用（030 把平凡系统的约束前提照搬了）**

平凡系统：AI 有 proof 但查 sessions.db 发现 tool_call → `invalid_tool_use`（`collector.py:290-327,369-372`）——前提是**平凡系统禁止解题 AI 用工具**。
本系统：`ANTI_CHEATING_CLAUSE`（`continuation_launcher.py:357-383`）明确**允许**工具
（Python/Lean/搜索），靠"主动声明义务 + 审计 AI 复查"防作弊（029 §3.0 防作弊不对称约束）。
审计 AI 同样被授权自由用工具（029 §5.3 模板"你的权限"段）。两系统的工具政策与平凡系统
相反，invalid_tool_use 检测在续传/审计系统都没有适用场景。

**B4. 续传"有 is_thinking 检测"是事实错误（030 §5.5 续传表 thinking_spin △）**

grep 全 repo：`is_thinking` / `check_ai_gave_up` / `check_tool_use` / `TOKEN_LIMIT` 在
本 repo src/ 中**零命中**。续传的 stall 检测（`continuation_launcher.py:1762-1842`）用
pane_hash 变化 + idle 时长，**无法区分 thinking spin 和真卡住**（平凡系统用
`is_devin_waiting_api`——查 devin 进程到代理 7897 的 ESTABLISHED 连接来区分）。差距
存在，但 030 给的理由（"有 is_thinking"）是错的。

**B5. 审计系统"failed_stall ✓ detect_stall() 检测"是事实错误**

`proof_audit_launcher.py:216-223` 的 `detect_stall()` **定义了但从未被调用**（死代码）。
`add_running` 时写的 `stall_since: None` 字段也从不更新。实际的超时判定是 `:408` 的
`time.time() - started_at > max_runtime`——总时长超时，不是无活动检测。且 030 说"没有
max_runtime 超时"**说反了**：有 max_runtime 超时（误名 stall_timeout），没有真 stall 检测。

**B6. ai_gave_up 误判方向 030 说反了**

030 说 AI 放弃"会被误判为 dead_session，不会正确分类"——分类错误属实（AI 放弃时
msg>0 无 proof → is_completed False → is_truncated False（msg>0）→ dead_session），
但实际害处是：dead_session ∈ INFRA_FAILURES → `retry_eligible=True`（`:1556-1563`）→
AI 主动放弃的题会被当作可重试基础设施失败**反复无意义重试**（一旦重试机制上线）。
补 ai_gave_up 检测的真实价值是防止这类题进入重试队列。

**B7. crash_recovered"待确认"已有答案——平凡系统自身不一致**

平凡系统两处定义：`collector.py:105` INFRA_FAILURES **含** crash_recovered；
`retry_infrastructure.py:37` **不含**——即平凡系统里 crash_recovered 被分类为 infra 但
不会被自动重试（平凡系统自己的遗留缺陷）。本系统 WP-I 提取共享模块时应统一：
**crash_recovered 属 infra、应入重试集合**。续传系统将 tmux server 死亡合并入
dead_session（retry_eligible=True），应对策略上与 crash_recovered 等价，仅分类标签未细分。

**B8. "SOP_02 不是每轮都跑"无证据**

SOP 是顺序状态机（`scripts/sop/_state.json`：last=04/next=05/cycle=6），`run.py` 按序
推进，无跳步逻辑。030 此说无代码依据，不采信。

**B9. 030 §5.2 与 §6.1 的"第 5 要素"自相矛盾**

§5.2 表格的 5 要素 = 做什么/为什么/检查项/论证依据/**历史教训引用**；
§6.1 模板的 5 要素 = 做什么/为什么/检查项/论证依据/**系统正常运行判断**。
两版"第 5 要素"不同。裁定见 §三 D3。

### 需求1：优雅停止（WP-P 补救 + WP-H 机制）

**WP-P 现场补救（立即执行，030 §6.7 已预授权）**——当前实测状态：5 个孤儿审计

   10 个已完成审计（5 个 launcher 判定 completed + 5 个 DB 显示 running 但实际完成的）
   的结果入库。注意：result_collector 查询条件是 `status=='completed' AND audit_status==null`，
   DB 里 5 个"running"的记录**不在候选集**——先手工把这 5 个的 status 修正为 completed
   （依据：DONE.md 存在 + export 有实质内容——直接检查），再跑收集
2. kill 5 个孤儿 tmux session（`paudit-27-full-*`，DONE.md 全在，符合铁律"绝不 kill 无

**WP-H 优雅停止机制（系统设计，方案批准后实施）**——按 `docs/architecture/graceful-shutdown.md` §6 清单实现，不引入 Redis 停止键：
