### 缺口清单

#### 缺口1：results集合为空——121个COMPLETED但0条result记录 [critical]

**现象**: `p27_continuation_results` 集合 0 条文档，但 runs 中有 121 个 final_status=COMPLETED。

**含义**: 最终结果没有归档到 results 集合。这是数据丢失风险——如果有人查 results 集合找结果，会以为什么都没完成。

**现有检查**: 无。没有任何脚本检查 results 集合。

**该谁检查**: 脚本可以检查（results数 vs COMPLETED数）。

#### 缺口2：oda和polymath全部0%完成 [critical]

**现象**: 304道oda题、207道polymath题全部0%完成。只有deepmath有31.7%完成率。

**含义**: 这是系统性问题，不是个别题的问题。可能是：
- prompt 对这些题源不适用
- model 对这些题型不胜任
- 这些 run 还都是 prepared 没跑（789个prepared中可能大部分是oda/polymath）

**现有检查**: 无。没有任何检查项按题源分组统计完成率。

**该谁检查**: 脚本可以统计（按problem_id前缀分组），AI判断含义。

#### 缺口3：789个run还是prepared状态 [critical]

**现象**: 86%的题还是prepared。进度检查只看Redis队列计数，不检查"prepared的题是否在被消费"。

**含义**: 可能是：
- 系统还没跑到这些题（队列还在消费中）
- 队列卡住了（feeder没在入队）
- 这些题的run创建后从未启动

**现有检查**: runtime_health_check [I] 检查pending堆积，但不检查prepared vs pending的关系。

**该谁检查**: 脚本可以检查（prepared数 vs Redis pending数对比）。

#### 缺口4：rounds_log全部从round=2开始 [info，需确认]

**现象**: 所有有rounds_log的run，rounds_log[0].round = 2。50/50不连续。

**含义**: 可能是设计如此（round 1是初始分析，不算续传轮），也可能是bug（round 1的数据丢失了）。

**现有检查**: 无。check_02检查rounds_log中的文件存在性，但不检查round编号连续性。

**该谁检查**: 脚本可以检查（round编号是否连续），AI确认是否by design。

#### 缺口5：27个run有launched事件但没有completed/failed事件 [warning]

**现象**: 317个有事件的run中，27个有launched但没有completed/failed。

**含义**: 可能是：
- 这些run还在运行中
- devin cli启动后崩溃了，没写完成事件
- 事件写入失败

**现有检查**: SOP_02 2d 要求AI手动检查，但没有自动化脚本。

**该谁检查**: 脚本可以检查（AQL聚合events按run_key）。

#### 缺口6：rounds_log之外的文件没有被检查 [warning]

**现象**: check_02只检查rounds_log中的6个路径字段。不检查：
- `problem.txt`（题目文件——实测50个都有，但没有自动检查）
- `DONE.md`（退出标记）
- `tmux.log`（tmux日志）
- round 1的文件（因为rounds_log从round 2开始，round 1的export/prompt等不在rounds_log中）

**现有检查**: runtime_health_check [H] 检查tmux_pipe.log和AGENTS.md，但只检查completed的run。

**该谁检查**: 脚本可以检查（work_dir下的标准文件列表）。

#### 缺口7：export.json内容语义正确性 [critical，必须AI]

**现象**: 脚本检查export文件存在、是JSON格式，但不检查内容是否真的是在解这道题。

**含义**: export.json可能存在且是有效JSON，但内容可能是：
- devin cli跑题了（在解别的题）
- thinking全是废话（重复、循环、无实质推理）
- 中途崩溃导致内容不完整

**现有检查**: 无。C5检查"续传方向"涉及这个，但只对needs_ai_review标记的run做。

**该谁检查**: **必须AI检查**（需要读thinking内容判断语义）。

#### 缺口8：跨题目模式识别 [critical，必须AI]

**现象**: 没有任何检查项做跨题目的宏观分析：
- 按题源分组的完成率差异
- 失败模式分布（truncated/no_proof/timeout/stall各占多少）
- 时间相关性（某时间段集中失败）
- 某类题目的共同数学特征

**现有检查**: 无。所有检查都是单run级别的。

**该谁检查**: 脚本可以统计分组数据，**AI判断含义和趋势**。

#### 缺口9：方向性判断 [critical，必须AI]

**现象**: 没有任何检查项做系统级方向判断：
- v2方案（HANDOVER+map）是否比v1有效
- 5轮上限是否够
- 13.2%完成率是否可接受
- 系统产出是否对Mid-Hint实验有价值

**现有检查**: SOP_Z 有"整体检查"但很空泛，没有具体检查项。

**该谁检查**: **必须AI检查**（需要领域知识和系统目标理解）。

## 四、自动化边界划分

### 脚本能做的（确定性、全量遍历）

- 文件存在性 / 文件大小 / JSON格式 / 字符串匹配
- DB字段非空 / 唯一性验证 / 统计计数
- 集合文档数对比 / events完整性
- 按题源分组统计 / 失败模式分布
- prepared vs pending对比

### AI必须做的（语义性、判断性、因果性）

- **A. 语义正确性**：文件存在但内容对不对（proof数学正确性、export是否在解这道题）
- **B. 因果分析**：为什么出了问题（读日志、查代码、看队列状态）
- **C. 决策**：发现问题后怎么办（重跑、修代码、调参数）
- **D. 跨题目模式识别**：宏观趋势（某类题系统性失败、某时间段集中失败）
- **E. 方向性判断**：系统是否在正确方向上（策略是否有效、产出是否有价值）
