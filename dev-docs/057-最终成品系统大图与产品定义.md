## 一、一句话产品定义

最终成品是一个面向高难数学问题的、可中断、可恢复、理论上可无限续传的 AI 解题与
数学真理性验证系统：它用**专职观察者**消化上一轮真实现场，用**专职解题者**推进证明，
用 OpenCode ACP 承载模型实例，用独立审计 AI 检查证明与形式化验证的充分程度；程序只
完成可靠的事实采集与确定性动作，Master Agent 通过现有 SOP 定时监督语义异常，关键
动作统一由既有 Gate 控制。

系统同时是一套运行结果资产采集系统。解出与未解出的每一轮 trajectory、提示词、笔记、
partial proof、工具调用、形式化源码和验证日志都必须保留，以支持未来继续解题、能力边界
研究和系统打磨。

执行后端方面，OpenCode ACP 是主后端，Devin ACP 是备用，legacy `-p` 在迁移期保留。三者
只提供最小同构执行能力，不复制三套题目生命周期；后端切换由 Master Agent/用户根据证据
经现有 Gate 控制，复杂 auto-fallback 不是当前必需目标。

## 二、六条根原则

### P1. 一题一条长期解题管线

一道题只有一个连续生命周期。观察者、解题者、形式化补证与审计是生命周期中的角色和
阶段，不是互相独立、互相覆盖结果的多条题目管线。同一道题任意时刻最多一个解题工作
实例；多题之间可以并行。

### P2. Round 窗口不是题目寿命

`max_rounds` 的目标语义是**本次调度窗口默认处理多少 Round**，目的是在并发环境下避免
单题长期独占资源。窗口用完只释放并发槽，不得永久判死题目。任何未得到正确答案、也未
被用户明确放弃的题目，都可在以后从下一 Round 继续，理论上没有总轮次上限。

### P3. 数学完成必须经过形式化真理性门槛

`proof.md`、`\boxed` 和解题 AI 的自述只构成“候选成功”。解题 AI 必须提交与证明匹配的
形式化验证资产；审计 AI 必须独立检查其覆盖是否充分并重跑验证。只有证明内容、形式化
覆盖和审计都通过，系统才确认数学正确。形式化不足时保留全部资产，题目继续可解。

### P4. 不追求不可靠的完全自动化

能写成确定性函数并单测覆盖的工作由程序完成：进程存活、最后通知时间、文件存在、命令
退出码、key 租约数、形式化工具结果等。需要跨源语义判断的工作由 Master Agent 完成：
疑似 stuck 是等待、发送“继续”、结束本轮还是换实例；形式化覆盖是否真正对应原题；边缘
异常如何收场。所有待人工情况必须可发现、有证据、有后续动作。

### P5. Gate 是唯一关键动作控制机制

不再建设与 Gate 平行的审批系统、冻结系统或工作流引擎。启动、kill、重入队、写终态等
关键语义动作继续通过现有 Gate；SOP 负责定时发现，Master Agent 负责判断，Gate 负责在
动作前承载检查和放行理由。底层 key 计数、文件 I/O 等普通资源操作不另设 Gate。

### P6. 不过度设计

当前系统的实现深度基本合适。未来工作优先修正错误语义、接通现有能力、完善提示词、
资产与测试，不借机重写成通用工作流平台。只有真实运行证据证明现有机制无法承载时，才
增加新的非功能组件。

## 三、最终逻辑流程

```text
题目进入系统
  ↓
建立长期 run（保留历史 current_round / rounds_log / 资产索引）
  ↓
取得本次调度窗口 + 并发槽 + OpenCode key lease
  ↓
Round 1：专职解题者
  ├─ 持续写工作笔记
  ├─ 持续保存 ACP 通知流
  ├─ 对关键命题做计算/形式化检查
  └─ 产出候选 proof 或留下可续传现场
  ↓
若未完成 / BUDGET_STARVED / 本轮异常结束
  ↓
下一轮专职观察者
  ├─ scan 上一轮 trajectory
  ├─ 必读上一轮 thinking 尾部
  ├─ 按需定点下钻，不通读全部历史
  ├─ 复核数学结论与形式化状态
  └─ 写结构化分析笔记
  ↓
下一轮专职解题者
  ├─ 只读最新分析笔记为主
  ├─ 推进一个明确数学缺口
  ├─ 增量维护工作笔记和形式化资产
  └─ 继续递归
  ↓
本次默认 Round 窗口用完？
  ├─ 是：保存现场、释放资源、题目保持可继续
  └─ 否：继续下一角色
  ↓
解题 AI 宣告候选成功
  ↓
独立 proof audit
  ├─ 检查自然语言证明
  ├─ 检查形式化覆盖充分程度
  ├─ 独立重跑形式化工具
  ├─ 检查 sorry/admit/额外公理/有限搜索冒充普遍证明
  └─ PASS / FAIL / FORMAL_INSUFFICIENT / NEEDS_REVIEW
  ↓
现有 FINALIZE Gate
  ├─ 证据充分：确认最终正确
  └─ 证据不足：不放行最终正确；保留资产，未来继续
```

## 四、观察者/解题者架构的证据来源

本架构不是凭空设计，根证据是另一个 repo 的 1962 完整实验：

- 原始 repo：`/Users/user/glm5.2-math-worktree/`
- 设计：`Tell分类学研究过程文档/poc_assets/poc_2.7.5/v2/DESIGN.md`
- 提示词：同目录 `v2/prompt_round1.md`、`prompt_observer.md`、`prompt_solver.md`
- v1 对照：`poc_assets/poc_2.7.5/workdirs/p275-1962/`
- v2 六轮：`poc_assets/poc_2.7.5/v2run/rounds/round1..6/`
- 最终 proof：`v2run/rounds/round6/proof.md`
- 机器辅助审查：`v2run/rounds/round6/math_audit.md`

同题实验显示：旧 HANDOVER 模式多轮真实推进但最终倒退、重验、未闭合；专职 R3 观察者
生成可信分析笔记后，R4 解题者攻下核心全奇定理，R5 观察者复核并偿还机器搜索欠账，R6
解题者完成 proof。成功因素是专职角色、递归消化、尾部收殓、供料替代禁令和逐轮提示词
迭代，不是简单增加 token。

1962 的机器审查仍不是严格完整形式化证明：验证脚本部分留在 `/tmp`，普遍命题未交 Lean
等可信内核检查。因此它是编排与提示词的黄金基线，也是最终形式化契约必须补强的反例。

## 五、资源模型

### 5.1 解题并发

- 目标最大并发解题管线暂定 **30**。
- 实际并发值仍由 DB batch 配置动态决定，可低于 30。
- 30 是目标容量上限，不得写成代码默认值。
- 同一道题内部观察者/解题者串行，共享一个管线槽。

### 5.2 OpenCode key

- 外部 key 来源：`/Users/user/database/email-project.md` 所述
  `email_project.openrouter_keys`。
- 系统领取外部 `active` key 后，将外部记录标成 `deactive`；从此由本系统内部 key 表管理。
- 每个 ACP 实例领取一个 key lease；key 可配置 `capacity`，可同时支持一个或多个 ACP
  实例，活跃 lease 不得超过 capacity。
- 每个实例在自己的工作目录按 `/Users/user/init-opencode.sh` 的配置结构生成
  `opencode.json`。
- ACP 回收并完成资产收集后释放该 lease，key 回到系统内部可用容量。
- key 不进入 Git、普通日志、alert 或行为流水。

## 六、Supervisor of System

程序持续提供事实：进程、ACP 最后通知、pending tool、provider error、key lease、proof、
形式化命令结果、DB/Redis/硬盘一致性。长时间无信号只标记为疑似 stuck，不盲目 kill 或
自动发送“继续”。

Master Agent 通过现有 SOP 定时查看证据，可决定：继续等待、向当前 session 发送“继续”、
安全结束当前 Round、按基础设施失败重启、换 key、或移交用户。动作复用现有 Gate，并将
理由写入行为流水。结束 stuck Round 不等于放弃题目。

---

## 七、成品不是哪些东西

- 不是永久并列的三套 launcher；观察者/解题者是策略，OpenCode/Devin/-p 是后端，应逐步
  收敛到清晰职责，但不为“统一”大重写现有系统。
- 不是达到默认 Round 数就永久失败的批处理器。
- 不是只要有 `\boxed` 就宣称数学正确的 proof 生产器。
- 不是为了完全自动化而堆启发式判定的状态机。
- 不是与 Gate 并行的第二套审批平台。
- 不是为了未来所有可能性提前抽象的通用编排框架。

---

## 八、最终完成判据

最终系统达到成品状态，至少应满足：

1. 一道未解题在任意调度窗口后都能从下一 Round 继续，不被默认轮数永久判死。
2. 生产路径使用专职观察者/解题者递归消化链，并通过 1962 风格回归测试。
3. 每轮真实 trajectory、尾部、笔记、prompt、proof、形式化源码和日志完整留存。
4. OpenCode ACP 实例按目录配置并从系统 key 池取得不超容量的 lease。
5. 最大 30 条解题管线的资源记账、动态并发和 key 容量约束一致。
6. 疑似 stuck 能被发现并进入 SOP；Master Agent 可通过现有 Gate 安全处置。
7. 解题成功只是候选；审计 AI 可独立判断并重跑形式化验证。
8. 形式化不足不会被误判为最终正确，也不会让题目永久失去继续资格。
9. 调度/判定变更经过 sim 与资产验收，不破坏旧轮次。
10. 一级文档、代码、测试和工作包对当前态/目标态的描述无冲突。
