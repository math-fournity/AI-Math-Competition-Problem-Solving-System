# 023-系统运行过程全景视图设计方案

**日期**：2026-08-20
**性质**：方案文档（make-plan 产出）
**需求来源**：用户要求 Master Agent"在认知闭包的背景知识下，分析和推理整个系统的运行，持续思考系统是否正常"。当前 SOP 检查很多局部的东西，但缺一个让 AI 看到系统整体运行过程的视图。

---

## §1 问题诊断

### 1.1 现状：数据有，过程叙事无

系统运行过程已被完整记录：

| 记录层 | 位置 | 内容 | 查看工具 |
|---|---|---|---|
| 行为流水 | `log/flow/flow-*.jsonl` | launcher 每个状态转移（13种事件） | `observability --stats/--tail/--run-key` |
| 门闸流水 | 同上（gate_*事件） | 9个语义动作的通过/等待/放行 | `step_gate --list/--pending` |
| 结构化日志 | `log/*.log` | 全模块事件流 | `log_search --event/--level` |
| DB 状态 | ArangoDB 各集合 | 存量快照（run/session/alert） | `continuation_control status` |

**矛盾**：数据完整，但现有查看工具给的是**统计聚合**（`--stats`：启动频率/判定分布）或**原始事件流**（`--tail`：逐条 JSONL），不是**过程叙事**。

### 1.2 AI 在 SOP 中看到的是什么

| SOP 步骤 | 看到的 | 缺的 |
|---|---|---|
| check_01 | `--stats --since 1h` 的统计聚合 | "系统作为一个整体在做什么"的过程描述 |
| SOP_01 §8 | 文档让 AI 手动跑 observability 命令 | AI 要从原始事件脑补系统过程，认知负担重 |
| check_Z | DB 存量快照 | 运行趋势（快照对比），过程是否顺畅 |

**核心缺口**：缺一个"从流程视角组织数据"的视图层——把行为流水+门闸流水+DB状态组织成"系统作为一个整体在如何运行"的可读叙事。

### 1.3 类比

有机器的全部传感器日志（温度/压力/转速逐秒），但缺一个仪表盘把数据组织成"机器现在在做什么、是否正常"的可读视图。数据在，但没被组织成"过程"。

## §2 设计目标

### 2.1 全景视图要回答的问题

Master Agent 在认知闭包背景下，需要回答四个层次的问题：

| 层次 | 问题 | 数据来源 |
|---|---|---|
| **L1 现状** | 系统现在在做什么？哪些管线在跑、在什么阶段、进展如何 | 行为流水（最近窗口）+ DB running run |
| **L2 流畅性** | 运行过程是否顺畅？有没有卡顿、循环、停滞 | 行为流水（事件速率/间隔分析）+ churn_suspects |
| **L3 流程合规** | 管线流程是否符合设计？dequeue→launch→judge→requeue/done 是否正常走，门闸是否正常通过 | 行为流水（事件序列完整性）+ 门闸流水 |
| **L4 趋势** | 运行趋势是什么？完成率在上升还是停滞，失败模式在变化吗 | 行为流水（时间序列对比）+ DB 快照对比 |

### 2.2 设计原则

1. **脚本生成，AI 阅读**——脚本能做的数据组织不做 AI 的认知负担；AI 的价值在"分析推理"不在"数据汇总"
2. **过程叙事，不是统计表**——输出是"系统在过去1小时做了这些事，过程是这样的"的可读描述，不是"启动了50次"的数字
3. **分层组织**——L1 现状是必读概览，L2-L4 是深化分析，AI 按需深入
4. **复用现有数据**——不新增记录层，只新增视图层；数据全部来自行为流水+门闸流水+DB

## §3 全景视图内容设计

### 3.1 视图结构（4层）

```
=== 系统运行过程全景视图 ===
窗口：过去 {N} 小时 | 生成时间：{timestamp}

--- L1 现状：系统现在在做什么 ---
（活跃管线清单 + 阶段 + 进展）

--- L2 流畅性：运行过程是否顺畅 ---
（事件速率/间隔分析 + 卡顿/循环检测）

--- L3 流程合规：管线流程是否符合设计 ---
（事件序列完整性 + 门闸通过情况）

--- L4 趋势：运行趋势是什么 ---
（完成/失败时间序列 + 失败模式分布变化）
```

### 3.2 L1 现状：系统现在在做什么

**目标**：让 AI 一眼看到"系统此刻在做什么"，不是数字而是过程。

**内容**：
1. **活跃管线清单**——从行为流水取最近窗口内所有 launch_solve/launch_handover 事件，按 run_key 聚合，输出每条管线的当前状态：
   ```
   管线 p27-full-amo_bench_00000006：
     round 3 solve 阶段，启动于 12:45，已跑 12 分钟
     上一轮判定：truncated（token不够）
     历史轨迹：R1 seed → R2 solve(truncated) → R3 solve(运行中)
   ```
2. **队列状态**——pending 数 + prepared 数（从 DB），不是数字而是"有 N 道题在等待被取出"
3. **并发槽占用**——running 数 + handover_pending 数 vs concurrency，"3/5 槽被占用，2 个在 solve，1 个在 handover"

**数据来源**：行为流水（launch_*事件 + judge事件）+ DB（running run 的 rounds_log）

### 3.3 L2 流畅性：运行过程是否顺畅

**目标**：让 AI 看到系统运行的"节奏"是否正常，不是告警而是过程描述。

**内容**：
1. **事件速率时间线**——把窗口分成若干段（如每10分钟一段），输出每段的 dequeue/launch/judge 速率，形成"速率曲线"：
   ```
   12:00-12:10: dequeue=5 launch=5 judge=4  (正常节奏)
   12:10-12:20: dequeue=8 launch=2 judge=0  (dequeue多但launch少——防抖拦截?)
   12:20-12:30: dequeue=0 launch=0 judge=0  (停滞——rate_limit? 系统停了?)
   ```
2. **卡顿检测**——找出事件间隔异常长的时段（如连续 30 分钟无 judge 事件），输出"12:20-12:50 系统无判定输出，可能停滞"
3. **循环检测**——churn_suspects 的可读化输出，不是"amo_bench_00000006: 启动8次"而是"amo_bench_00000006 在 12:15-12:25 被反复启动 8 次，其他题都在等待——失控循环"

**数据来源**：行为流水（全事件类型的时间戳序列）

### 3.4 L3 流程合规：管线流程是否符合设计

**目标**：让 AI 确认系统在按设计的流程图运行，门闸正常工作。

**内容**：
1. **事件序列完整性**——对窗口内每条管线，检查其事件序列是否符合设计流程：
   ```
   设计流程：dequeue → [skip_*|launch_solve|launch_handover] → judge → [requeue|round_done|run_completed|run_failed]
   
   p27-full-amo_bench_00000006: dequeue→launch_solve→judge(truncated)→requeue→dequeue→launch_solve→judge(completed)→run_completed ✅ 完整
   p27-full-oda_001: dequeue→launch_solve→[无judge] ⚠️ 缺判定事件（可能还在跑）
   p27-full-polymath_002: [launch_solve无dequeue] ❌ 异常——未出队就启动？
   ```
2. **门闸通过情况**——从 gate_pass/gate_done 事件统计9个门闸的通过次数，检查有无 gate_waiting（冻结）：
   ```
   门闸通过统计（过去1小时）：
     GATE-LAUNCH-SOLVE: 12次 auto通过
     GATE-START-HANDOVER: 8次 auto通过
     GATE-REQUEUE-TRUNCATED: 5次 auto通过
     ...
   门闸冻结：无（所有门闸 auto 模式，无 waiting）
   ```
3. **异常事件序列**——列出不符合设计流程的事件序列（如 launch_solve 前无 dequeue，judge 前无 launch）

**数据来源**：行为流水（按 run_key 分组的事件序列）+ 门闸流水

### 3.5 L4 趋势：运行趋势是什么

**目标**：让 AI 看到系统运行的方向，不是快照而是变化。

**内容**：
1. **完成/失败时间序列**——把窗口分段，输出每段的 run_completed/run_failed 数：
   ```
   12:00-12:30: completed=2 failed=1
   12:30-13:00: completed=3 failed=0
   → 完成速率在上升，失败在减少
   ```
2. **失败模式分布变化**——按时间段对比 run_failed 的 reason 分布：
   ```
   12:00-12:30: dead_session=1
   12:30-13:00: timeout=2 stall=1
   → 失败模式从 dead_session 转向 timeout/stall（基础设施问题?）
   ```
3. **判定结果分布变化**——按时间段对比 judge 的 outcome 分布：
   ```
   12:00-12:30: completed=2 truncated=3
   12:30-13:00: completed=3 truncated=1
   → 截断比例在下降，完成比例在上升
   ```

**数据来源**：行为流水（run_completed/run_failed/judge 事件的时间序列）

## §4 实现设计

### 4.1 脚本：`scripts/sop/system_panorama.py`

**职责**：从行为流水+门闸流水+DB 读取数据，组织成4层全景视图输出到 stdout。

**接口**：
```bash
# 默认窗口1小时，输出4层全景
python -m scripts.sop.system_panorama --batch-id p27-full

# 指定窗口
python -m scripts.sop.system_panorama --batch-id p27-full --since 2h

# 只输出某层（快速查看）
python -m scripts.sop.system_panorama --batch-id p27-full --layer L1
```

**实现要点**：
1. 复用 `src.observability.read_flow()` 读取行为流水（不重复造轮子）
2. 复用 `src.step_gate` 的 DB 查询获取门闸状态
3. 复用 `src.continuation_db_schema.connect_db()` 获取 DB 状态
4. L1 的管线轨迹：按 run_key 分组事件，重建每条管线的事件序列
5. L2 的速率时间线：按时间段分桶统计事件数
6. L3 的流程合规：定义"设计流程"的事件序列模式，逐管线校验
7. L4 的趋势：按时间段分桶统计终态事件

**输出格式**：纯文本（stdout），可直接被 SOP 脚本捕获到 check_output.txt，也可被 AI 直接阅读。

### 4.2 不新增记录层

本方案**不新增任何日志/流水记录**。所有数据来自：
- 行为流水（`log/flow/`，已有）
- 门闸流水（同上，gate_*事件，已有）
- DB 状态（ArangoDB，已有）

只新增**视图层**——从已有数据组织出过程叙事。

### 4.3 与现有 observability 的关系

| 工具 | 定位 | 输出 |
|---|---|---|
| `observability --stats` | 统计聚合 | 数字（启动频率/判定分布） |
| `observability --tail` | 原始事件 | 逐条 JSONL |
| `observability --run-key` | 单题生命周期 | 单题事件序列 |
| **`system_panorama`（本方案）** | **系统过程叙事** | **4层可读视图（现状/流畅性/流程合规/趋势）** |

`system_panorama` 是 observability 的上层视图——复用其 `read_flow()` 数据，但组织成过程叙事而非统计/原始事件。

## §5 SOP 接入设计

### 5.1 接入点：check_01（系统健康检查）

**为什么接在 01**：01 是"系统存活+进度+Session"——全景视图的 L1（现状）正是这个步骤的核心需求。AI 在 01 看到系统过程全景后，才能判断"系统是否健康"。

**接入方式**：在 `checks.py` 的 `check_01_system_health` 中，在 `_check_flow_snapshot()` 之后新增 `_check_system_panorama()`：

```python
def _check_system_panorama():
    """步骤01例行：系统运行过程全景视图——让AI看到系统整体在做什么。
    
    行为流水的 --stats 给统计聚合，--tail 给原始事件，但都不回答
    "系统作为一个整体在如何运行"。本函数调用 system_panorama 脚本，
    输出4层过程叙事（现状/流畅性/流程合规/趋势），让AI在认知闭包
    背景下分析和推理系统运行是否正常。
    """
    print("--- 系统运行过程全景视图 ---")
    try:
        result = subprocess.run(
            [sys.executable, "-m", "scripts.sop.system_panorama",
             "--batch-id", "p27-full", "--since", "1h"],
            capture_output=True, text=True, timeout=60,
            cwd=str(Path(__file__).parent.parent.parent),
        )
        if result.stdout:
            print(result.stdout)
        else:
            print("  （无全景视图输出——系统可能刚启动/无行为流水）")
        if result.stderr:
            print(f"  ⚠️ system_panorama stderr: {result.stderr[:500]}")
    except subprocess.TimeoutExpired:
        print("  ⚠️ 全景视图生成超时（60秒）")
    except Exception as e:
        print(f"  ⚠️ 全景视图生成失败: {e}")
    print()
```

## §9 设计决策记录

### 9.1 为什么是脚本生成而非 AI 组装

**决策**：脚本生成全景视图，AI 阅读后做分析推理。
**理由**：数据组织（按 run_key 分组、按时间段分桶、事件序列校验）是机械工作，做成脚本可持续改进、不占 AI 认知负担。AI 的价值在"从过程叙事中推理系统是否正常"，不在"从原始事件中组装过程"。

### 9.2 为什么接在 01 而非新增步骤

**决策**：接入 check_01，不新增 SOP 步骤。
**理由**：01 是"系统健康检查"——全景视图的 L1（现状）正是健康判断的数据基础。新增步骤会打破8步循环结构，且全景视图是"每轮必看"的，放01最合理。Z 步骤可选深化（更长窗口看趋势）。

### 9.3 为什么是4层而非单一视图

**决策**：L1 现状（必读）+ L2-L4（深化分析）分层。
**理由**：AI 每轮 SOP 的认知预算有限，L1 是"一眼概览"必读，L2-L4 是"按需深入"。分层让 AI 在健康时快速过（只看L1），异常时深入分析（L2-L4）。
