## 六、我补充的 031 未发现的新问题

### E1：check_audit_complete 只看 DONE.md 不看内容 — 语义歧义风险

`proof_audit_launcher.py:192-213` `check_audit_complete()`：
```python
done_marker = Path(export_path).parent / "DONE.md"
if done_marker.exists():
    return True  # ← 直接返回 True，不检查 export 内容
```

DONE.md 只包含 exit code（`echo $? > {done_marker}`），不包含审计是否成功。devin cli 崩溃（exit code=1）也会有 DONE.md，会被标记为 "completed"。

**影响**：launcher 标记的 "completed" 语义是"devin cli 退出了"，不是"审计成功了"。result_collector 之后解析 export 时可能得到 PARSE_ERROR。这个流程本身是正确的（launcher 标 completed → result_collector 解析 → PARSE_ERROR 时标记），但 "completed" 的语义歧义可能误导 SOP 检查——SOP_01 看到 5 个 completed 会以为审计成功了，实际可能全是 PARSE_ERROR。

**建议**：在 SYSTEM_CLOSURE 或 proof_audit_launcher.py docstring 中明确"completed = devin cli 已退出，不等于审计成功；审计成功看 p27_proof_audits 的 audit_status"。

### E2：tmux session 因 sleep 999999 不会自然消失

`proof_audit_launcher.py:145-154` devin 命令末尾有 `sleep 999999`：
```python
devin_cmd = (
    f"devin -p ... ; "
    f"echo $? > {done_marker}; "
    f"sleep 999999"
)
```

devin cli 退出后，tmux session 因 `sleep 999999` 继续存活。这意味着：
- `tmux_running(session_name)` 返回 True（session 存在）
- 但 devin cli 已经退出了（DONE.md 已写）

**影响**：如果 launcher 被 kill 后重启，重启的 launcher 会在 running 检查中看到这些 session 还在 running（tmux_running=True），但 check_audit_complete() 会检测到 DONE.md 存在并标记为 completed。这个流程是正确的，但 `tmux_running=True` + `DONE.md=True` 的组合可能让调试者困惑。

**与 031 WP-P 的关系**：031 的 WP-P 步骤 2 说"kill 5 个孤儿 tmux session"——这是正确的，因为 DONE.md 全在，符合铁律。但 031 没有解释为什么这些 session 还活着（是 sleep 999999 导致的），可能会让人误以为 devin cli 还在运行。

## 七点五、对 031（另一个 AI）的启发——适度依赖 Master Agent 介入

这一节是用户在审阅 032 后提出的设计哲学补充，对 031 的方案设计有直接影响。

### 核心思想

用户指出：**系统不必追求完全自动化判定。适度依赖外部干预（Master Agent 侧完成最终判定和收场），可以让系统的代码和运行逻辑在某种意义上更"干净"。**

如果有些东西系统无法作出完美判定，那么可以交给 Master Agent 侧来完成最终的判定和收场——而不是为了追求"自动化"而把不完美的判定逻辑硬塞进代码。

### 对 031 方案的具体影响

031 的方案中有几处已经在践行这个理念（可能是有意识的，也可能是直觉）：

| 031 的设计 | 与本原则的关系 |
|---|---|
| WP-N：PARSE_ERROR 不走 FINALIZE-FAIL，标记 `audit_passed=None` + 创建 alert + 不改 status | **完美践行**——代码不强行自动判定，标记"待人工"交给 Master Agent |
| WP-Q：审计 alert 由 SOP_07 检查创建而非 monitor 自动创建 | **完美践行**——monitor 不自动判定审计健康，SOP_07 检查后由 Master Agent 判断 |
| WP-J 第 2 步：删除死代码 detect_stall()，用 max_runtime 兜底 | **符合**——不为 stall 检测写复杂的 pane_hash 追踪逻辑，max_runtime 兜底 + Master Agent 通过 SOP 发现异常 |
| WP-I：is_devin_waiting_api 标注"可选提取"，依赖代理端口假设 | **符合**——不强行提取可能不适用的检测逻辑，标注"可选"让 Master Agent 根据实际情况决定 |

### 对 031 方案的补充建议

基于本原则，建议 031 在方案中明确以下设计准则（已记录到 AGENTS.md 新硬约束）：

1. **代码做能可靠做的事**——可靠的终态判定（有 proof/无 proof/超时）放代码
2. **不可靠的判定标记为"待人工"**——不强行自动判定（PARSE_ERROR、语义质量、边缘终态）
3. **"待人工"必须有可发现的痕迹**——创建 alert 或标记字段（`audit_passed=None`），Master Agent 通过 SOP 检查发现
4. **不为"待人工"情况写复杂的自动判定逻辑**——那是 Master Agent 的工作，不是代码的工作

### 具体到 WP-I/J/K 的范围控制

031 已经在 B2/B3 中缩减了 WP-K 的范围（删除 token_limit 和 invalid_tool_use）。基于本原则，建议进一步审视：

- **is_thinking / is_devin_waiting_api 是否真的需要提取？** 如果提取后只是为了在代码中自动区分 thinking spin 和真 stall——而 Master Agent 通过 SOP 检查 + 行为流水（`observability --stats`）也能发现并处理——那么不提取可能更"干净"。代码用 max_runtime 兜底，thinking spin 的精细区分交给 Master Agent。
- **crash_recovered 是否需要细分？** 031 的 B7 已经指出续传系统将 tmux server 死亡合并入 dead_session（retry_eligible=True），应对策略上与 crash_recovered 等价。如果细分只是为了分类精度而非应对策略差异，那么不细分可能更"干净"——代码用 dead_session 兜底，Master Agent 通过 SOP 检查发现 crash 类批量失败时人工处理。

**这不是说 031 的方案过度设计**——031 的方案在"代码能可靠判定"的范围内是精确的。本节只是提供一个设计哲学视角：**在"代码可靠判定"和"Master Agent 人工判定"之间，倾向把更多交给后者，让代码更"干净"。**

### 已记录到 AGENTS.md

本原则已作为新硬约束"适度依赖 Master Agent 介入——不追求完全自动化判定"记录到 `AGENTS.md`（位于"禁止代码中写死并发数"硬约束之后）。未来的 AI（包括执行 031 方案的 AI）在设计终态检测、错误处理、自动化判定逻辑时，应遵循此原则。

## 七点六、解题运行结果资产保留铁律（用户新增需求）

### 需求原文

用户指出：**整个系统运行的所有解题结果，无论是最终做出来了，还是没有做出来的，都是宝贵的运行结果资产，必须每一个 round 都全部保留目录、文件、export 出来的 conversation.json 等数据。**

### 含义

- **所有 round 的产出都必须保留**——不只是最终成功的那一轮，中间每一轮（包括失败轮、截断轮、dead_session 轮、stall 轮、timeout 轮）的产出都是资产
- **"产出"的范围**：目录结构（`round{N}/`）、文件（`proof.md`、`round{N}_proof.md` 归档、`round{N}_prompt.txt`、`HANDOVER.md`）、export 的 `conversation.json`（含 thinking/reasoning_content）、tmux pipe log
- **"做出来"和"没做出来"同等重要**——没做出来的 round 的 conversation.json 包含 AI 的完整推理过程（尝试了什么、为什么失败、走到哪一步），是分析 AI 能力边界的宝贵数据
- **禁止清理**——任何 round 的任何产出文件都不应被删除或覆盖（除了 `remove_old_proof` 这种"启动新一轮前清理上一轮残留 proof.md"的必要操作——但前提是上一轮的 proof 已归档为 `round{N}_proof.md`）

### 当前系统的产出保留情况（调查结果）

#### 续传系统（continuation_launcher.py）

**已保留的**：
- 每个 round 有独立目录：`{TRAJECTORY_BASE}/p27-continuation/{run_key}/round{N}/exports/conversation.json`（`:1134-1138`）
- 成功轮的 proof.md 归档为 `round{N}_proof.md`（`:1508-1512` `shutil.copy2`）
- DB rounds_log 记录每轮的 export_path / prompt_path / proof_path（`:201-225` `make_round_log_entry`）
- round1 的 export 从 seed_export 镜像到 work_dir 的 `round1_export.json`（`:787-818`）

**存在的问题**（调查发现）：
1. **round1 的 export 目录是空的**——实测 `p27-full-deepmath_103k_00001653/exports/` 目录存在但里面没有 conversation.json。round1 的 export 只存在于 work_dir 的 `round1_export.json`，而 work_dir 可能在某些情况下被清理或丢失
2. **失败轮的 proof.md 没有归档**——实测 `p27-full-deepmath_103k_00001653` 没有 `round*_proof.md` 文件（因为 dead_session 时没解出来，没有 proof 可归档）。但 dead_session 轮的 conversation.json 是保留的（round2/exports/conversation.json 存在，137KB）
3. **`remove_old_proof` 只删 proof.md 不删 export**——这是正确的（proof.md 启动新一轮前必须清理防止误判，但 export 是历史记录不应删）。但需要确认：`remove_old_proof` 的门闸检查项 2"上轮 proof 已归档"是否总是被执行

#### 审计系统（proof_audit_launcher.py）

**已保留的**：
- 审计 work_dir：`{AGENTS_DIR}/p27-proof-audit/{audit_run_key}/`（含 AGENTS.md + proof.txt）
- 审计 export：`{TRAJECTORY_BASE}/p27-proof-audit/{audit_run_key}/exports/conversation.json`

**存在的问题**：
1. 审计系统是单轮的（不需要多轮续传），产出保留相对简单
