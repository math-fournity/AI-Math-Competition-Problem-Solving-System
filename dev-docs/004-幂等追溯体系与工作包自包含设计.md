# 004-幂等追溯体系与工作包自包含设计

**日期**：2026-08-19
**性质**：核心设计文档。定义 trace.csv 与 repo 的幂等关系、工作包自包含设计、AI 工作规范。

---

## §0 用户原话

> 我们的这套系统，trace.csv与整个repo应该是实时"幂等"的，从而trace.csv的git log和整个repo的git log，也存在着幂等关系。也就是说，将来，这种幂等关系是需要维护的？那么谁在维护，当然是AI了。AI在什么之中维护？AI在工作包中维护。事实上，AI在工作包中工作的时候，是既要利用这种幂等关系辅助自己了解所有应该了解的情况，又要持续地维护这种幂等关系，从而让未来的下一个工作包的AI，可以利用这种幂等关系，帮助自己准确地了解整个repo所有的"元素"的关系。所以本质上来讲，我们这套全维度、全元素追溯体系，就是给了AI一个重要的在repo中工作的基础设施。而流程上，我们是从需求入手，也就是建立checklist中的元素，然后建立方案文档，方案文档也是一个重要的元素。在建立方案文档的过程中，就要积极利用这套幂等基础设施，从而构建起来一套完备的方案，所谓的完备，就是好像是整个repo的所有的元素都放入了AI的上下文中一样——因为这件事现实来讲，往往不可能，因为AI的上下文是受限的，尤其是我们使用的AI，只有短短的20万上下文，能够用于连续工作的上下文不超过16万，超过了16万就会被压缩，就会丧失部分记忆。所以工作包的拆解粒度是非常重要的，方案最终会被拆解成一个个的小的工作包，而工作包是自包含的，因为会在工作包中首先建立起README.md文件，其中详细列出了执行工作包的AI所需要的View，也就是看法文件，另外甚至我们还可以详细地，直接列出它需要加载的文档和代码——这是在把方案细化到工作包的过程中做的事情，这个细化过程严重依赖了trace.csv的支持。并且工作包对于AI的工作规范也是要充分定义的，比如说，要全程密集地进行git提交，提交之前，必须维护trace.csv各个层级的元素与整个repo的实时幂等关系。

## §1 逐句分析

### 句1

> 我们的这套系统，trace.csv与整个repo应该是实时"幂等"的，从而trace.csv的git log和整个repo的git log，也存在着幂等关系。

**解读**：

- **"幂等"的含义**：trace.csv 中记录的所有资产关系，和 repo 中实际存在的资产及其实际关系，必须完全一致。给定任何一个 commit 时间点，trace.csv 的状态精确反映了 repo 在那个时间点的状态。trace.csv 不是"近似索引"，不是"事后补录"，而是 repo 状态的**精确镜像**。
- **"实时"的含义**：不是事后批量同步，而是每次 repo 变更时同步更新 trace.csv。每个 commit 中既包含 repo 的变更，也包含 trace.csv 的对应变更。
- **"git log 的幂等关系"**：trace.csv 的 git log 和 repo 的 git log 是同步演进的。在任何一个 commit 上 checkout，trace.csv 的状态都精确反映那个 commit 的 repo 状态。两个 git log 不是同一个，但它们是**同步对齐**的——每个 repo 变更 commit 中，trace.csv 也被同步更新并包含在同一个 commit 中。

**推论**：trace.csv 和 repo 在同一个 git 仓库中，同一个 commit 中。不是分离的两个仓库。

### 句2

> 也就是说，将来，这种幂等关系是需要维护的？

**解读**：

- 幂等关系不是自动产生的——它需要被**主动维护**。
- 每次 repo 变更时，必须同步更新 trace.csv，否则幂等关系被破坏。
- 这是一个持续的过程，贯穿项目的整个生命周期。

### 句3

> 那么谁在维护，当然是AI了。

**解读**：

- 维护者不是人，是 AI。
- 这意味着 AI 的工作流程中必须包含"维护 trace.csv"这个步骤，不能遗漏。
- 这也意味着 AI 的工作规范中必须有硬约束：每次改 repo 时同步改 trace.csv。

### 句4

> AI在什么之中维护？AI在工作包中维护。

**解读**：

- 维护的场所是**工作包**。
- 工作包是 AI 工作的基本单元——AI 不是在"整个项目"中工作，而是在一个个具体的工作包中工作。
- 每个工作包的执行过程中，AI 既要利用 trace.csv，也要维护 trace.csv。
- 工作包是 trace.csv 维护的**最小单元**——一个工作包完成后，trace.csv 应该反映这个工作包造成的所有变更。

### 句5

> 事实上，AI在工作包中工作的时候，是既要利用这种幂等关系辅助自己了解所有应该了解的情况，又要持续地维护这种幂等关系，从而让未来的下一个工作包的AI，可以利用这种幂等关系，帮助自己准确地了解整个repo所有的"元素"的关系。

**解读**：

- **双重责任**：AI 在工作包中工作时，对 trace.csv 既是**消费者**又是**生产者**。
  - 消费者：利用 trace.csv 了解"我应该了解的情况"——当前工作包涉及哪些资产，这些资产和哪些其他资产有关系，改了某个文件会影响哪些看法文件/需求/工作包。
  - 生产者：维护 trace.csv，记录自己在这个工作包中造成的所有新关系和变更的关系。
- **跨 session 传递**：维护的目的不仅是当前工作包，更是"未来的下一个工作包的 AI"。下一个 AI 接手时，trace.csv 是它了解 repo 的基础设施。
- **"所有元素的关系"**：trace.csv 覆盖的不只是文档，而是 repo 中所有元素（需求/工作包/文档/代码/函数/章节/方案/commit）的所有关系。

### 句6

> 所以本质上来讲，我们这套全维度、全元素追溯体系，就是给了AI一个重要的在repo中工作的基础设施。

**解读**：

- trace.csv 的定位是**基础设施**——不是某个具体任务的工具，而是 AI 在 repo 中工作的底层支撑。
- 类比：trace.csv 之于 AI，就像数据库索引之于应用——不是业务逻辑的一部分，但没有它业务逻辑无法高效运转。
- "全维度、全元素"：覆盖所有维度（需求/实现/验证/变更/追溯），覆盖所有元素（从函数到方案文档到 commit）。

### 句7

> 而流程上，我们是从需求入手，也就是建立checklist中的元素，然后建立方案文档，方案文档也是一个重要的元素。

**解读**：

- 工作流程的起点是**需求**——在 checklist 中建立 checkpoint。
- 需求之后是**方案文档**——在 dev-docs 中建立方案。
- 方案文档本身也是 trace.csv 中的一个元素（`dev-doc` 类型），它和其他元素（需求/代码/工作包）之间有关系（`produces`/`changes`/`comes-from`）。
- 流程链：需求(checkpoint) → 方案文档(dev-doc) → 工作包(wp) → 执行 → commit

### 句8

> 在建立方案文档的过程中，就要积极利用这套幂等基础设施，从而构建起来一套完备的方案，所谓的完备，就是好像是整个repo的所有的元素都放入了AI的上下文中一样——

**解读**：

- 方案制定阶段就要利用 trace.csv——不是等执行时才用。
- 利用 trace.csv 的目的是让方案"完备"——考虑到所有相关元素和关系。
- **"完备"的定义**：方案制定时，AI 的认知状态等价于"整个 repo 的所有元素都放入了上下文"。
- 这不是真的把所有元素放入上下文（下一个句子解释了为什么不可能），而是通过 trace.csv 的追溯链，AI 能精确知道"哪些元素和当前方案有关"，然后只加载这些元素，但认知效果等价于"全知"。

### 句9

> 因为这件事现实来讲，往往不可能，因为AI的上下文是受限的，尤其是我们使用的AI，只有短短的20万上下文，能够用于连续工作的上下文不超过16万，超过了16万就会被压缩，就会丧失部分记忆。

**解读**：

- **硬约束**：AI 上下文窗口有限（20万 token），连续工作可用不超过16万 token，超过就被压缩，压缩导致记忆丧失。
- 这就是为什么不能"把所有元素放入上下文"——物理上不可能。
- 这也是为什么 trace.csv 如此重要——它是"外化的记忆"，让 AI 在不需要把所有元素放入上下文的情况下，仍然能精确知道所有元素的关系。
- trace.csv 本身很小（CSV 文本文件），可以快速加载和查询，但它索引的内容（整个 repo 的所有元素）是 AI 无法全部加载的。

### 句10

> 所以工作包的拆解粒度是非常重要的，方案最终会被拆解成一个个的小的工作包，而工作包是自包含的，因为会在工作包中首先建立起README.md文件，其中详细列出了执行工作包的AI所需要的View，也就是看法文件，另外甚至我们还可以详细地，直接列出它需要加载的文档和代码——

**解读**：

- **工作包拆解粒度**是方案到执行的关键转化环节。粒度太粗 → 单个工作包需要加载的元素太多，超出上下文限制。粒度太细 → 工作包数量太多，管理成本高，且工作包之间的关系复杂。
- **工作包是自包含的**——每个工作包包含执行它的 AI 所需的全部认知信息，不需要"额外去项目里找"。
- **自包含的实现方式**：工作包中有 README.md，列出：
  1. 需要的 View（看法文件）——AI 按看法文件去加载相关文档
  2. 甚至直接列出需要加载的具体文档和代码——省去 AI 自己判断的步骤
- 这就是 make-plan skill 中"认知准备"步骤的产物——在工作包 README.md 中预先准备好认知加载路径。

### 句11

> 这是在把方案细化到工作包的过程中做的事情，这个细化过程严重依赖了trace.csv的支持。

**解读**：

- 方案细化到工作包的过程，就是 make-plan skill 的执行过程。
- 这个过程"严重依赖 trace.csv"——因为要判断"这个工作包需要加载哪些元素"，必须查 trace.csv 知道"这些元素和哪些其他元素有关系"。
- 具体依赖方式：
  - `query <type> <id>` — 查某个需求关联了哪些代码/文档/工作包
  - `trace <type> <id>` — 从某个需求出发追溯完整关系链
  - `query-prefix <type> <path>` — 查某个文件下所有函数/章节的关系
  - 根据追溯结果，判断这个工作包需要加载哪些看法文件、哪些具体文档、哪些具体代码

### 句12

> 并且工作包对于AI的工作规范也是要充分定义的，比如说，要全程密集地进行git提交，提交之前，必须维护trace.csv各个层级的元素与整个repo的实时幂等关系。

**解读**：

- 工作包不只是"任务清单"，还包含**AI 工作规范**。
- **全程密集 git 提交**：不是"做完了再提交"，而是每完成一个逻辑单元就提交。
- **提交之前必须维护 trace.csv**：每个 commit 之前，trace.csv 必须先被更新到反映当前 repo 状态。commit 中同时包含 repo 变更和 trace.csv 变更。
- **"各个层级的元素"**：不只是文件级，还包括函数级、章节级——如果改了某个函数，trace.csv 中这个函数对应的记录也要同步更新。
- **"实时幂等关系"**：每个 commit 时间点上，trace.csv = repo 状态的精确镜像。

## §2 完整理解与把握

### 核心命题

**trace.csv 是 AI 在 repo 中工作的基础设施，它和 repo 保持实时幂等关系，由 AI 在工作包中双向利用（消费+生产），使 AI 在有限上下文下实现等价于"全知"的工作能力。**

### 体系架构

```
需求(checkpoint) → 方案文档(dev-doc) → 工作包(wp) → 执行 → commit
                      ↑                    ↑           ↑
                  利用trace.csv       利用trace.csv  维护trace.csv
                  构建完备方案        自包含准备      保持幂等关系
```

### 关键概念

#### 1. 幂等关系（trace.csv ↔ repo）

- **定义**：给定任何一个 commit 时间点，trace.csv 的状态精确反映 repo 在那个时间点的所有元素和关系。
- **维护方式**：每次 repo 变更时同步更新 trace.csv，两者在同一个 commit 中。
- **验证方式**：在任何一个 commit 上 checkout，trace.csv 的内容应该和 repo 的实际状态完全一致。
- **破坏后果**：幂等关系被破坏 = trace.csv 中的记录和 repo 实际状态不一致 = AI 按 trace.csv 查询得到错误信息 = 认知体系失效。

#### 2. AI 的双重责任（消费+生产）

- **消费**：利用 trace.csv 了解当前工作包涉及哪些元素，这些元素和哪些其他元素有关系。
- **生产**：在工作包执行过程中，持续更新 trace.csv，记录自己造成的所有新关系和变更关系。
- **传递性**：维护的目的不仅是当前工作包，更是下一个工作包的 AI。

#### 3. 工作包自包含设计

- **定义**：每个工作包包含执行它的 AI 所需的全部认知信息。
- **实现方式**：工作包 README.md 中列出：
  1. 需要的 View（看法文件）
  2. 甚至直接列出需要加载的具体文档和代码
- **依赖**：工作包的自包含性依赖于方案细化过程对 trace.csv 的利用——通过追溯链精确判断"这个工作包需要哪些元素"。

#### 4. 上下文限制的应对

- **硬约束**：AI 上下文窗口有限（20万 token），连续工作不超过16万 token，超过被压缩。
- **trace.csv 的角色**：外化的记忆——本身很小，但索引了整个 repo 的所有元素关系。
- **工作包拆解的角色**：把大任务拆成小任务，每个小任务只需要加载相关元素（通过 trace.csv 精确定位），不需要加载整个 repo。
- **"完备"的定义**：方案制定时，通过 trace.csv 的追溯链，AI 能精确知道"哪些元素和当前方案有关"，只加载这些元素，但认知效果等价于"全知"。

#### 5. AI 工作规范

- **全程密集 git 提交**：每完成一个逻辑单元就提交。
- **提交前维护 trace.csv**：每个 commit 之前，trace.csv 必须先被更新到反映当前 repo 状态。
- **分层维护**：不只是文件级，还包括函数级、章节级。
- **commit 包含两者**：repo 变更和 trace.csv 变更在同一个 commit 中。

### 工作流程（完整版）

```
阶段1：需求建立
  → 在 checklist 中建立 checkpoint
  → trace.csv 记录 checkpoint 元素

阶段2：方案制定
  → 利用 trace.csv 追溯当前需求关联的所有元素
  → 在 dev-docs 中建立方案文档
  → 方案文档"完备"——通过 trace.csv 追溯链，认知等价于"全知"
  → trace.csv 记录 dev-doc 元素及其关系

阶段3：工作包拆解
  → 利用 trace.csv 追溯每个工作包涉及的元素
  → 把方案拆解成一个个小工作包
  → 每个工作包自包含：README.md 列出需要的 View 和具体文档/代码
  → trace.csv 记录 wp 元素及其与 checkpoint/dev-doc 的关系

阶段4：工作包执行
  → AI 加载工作包 README.md → 按 View 加载看法文件 → 加载具体文档/代码
  → 执行工作，更新 repo 中的文档和代码
  → 全程密集 git 提交
  → 每次提交前维护 trace.csv（各个层级的元素与 repo 的幂等关系）
  → commit 同时包含 repo 变更和 trace.csv 变更

阶段5：验证
  → 验证 trace.csv 与 repo 的幂等关系
  → 验证三层架构完整性
  → commit
```

### 设计原则

1. **trace.csv 是基础设施**——不是某个任务的工具，是 AI 在 repo 中工作的底层支撑
2. **幂等关系是铁律**——trace.csv 和 repo 必须实时一致，破坏幂等 = 认知体系失效
3. **AI 是维护者**——维护 trace.csv 是 AI 工作流程的硬约束，不是可选步骤
4. **工作包是维护单元**——一个工作包完成后，trace.csv 应反映这个工作包的所有变更
5. **工作包是自包含的**——README.md 列出执行 AI 需要的全部认知信息
6. **方案细化依赖 trace.csv**——工作包拆解粒度依赖于 trace.csv 的追溯支持
7. **上下文限制通过拆解+追溯应对**——不把所有元素放入上下文，而是通过 trace.csv 精确定位相关元素
8. **提交前必须维护 trace.csv**——commit 同时包含 repo 变更和 trace.csv 变更
9. **分层维护**——文件级、函数级、章节级，所有层级的元素都要保持幂等
