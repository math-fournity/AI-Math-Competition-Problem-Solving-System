# 025 - 题目来源审查报告

> **日期**：2026-08-21
> **触发**：用户担忧续传系统的题目来源——"我们只做另外一个平凡解题系统处理过但却没做出来的、tier=1 的题"
> **结论**：题目来源链有缺陷，混入了 tier=2/tier=3 和已被 normal-solver 解出的题。但所有不符合条件的题都是 prepared 状态（还没做），没有浪费做题资源

## 1. 题目来源链

```
normal-solver (devin_problem_runs)          ← A 系统，按 tier 选题做题
    ↓
export_new_problems.py                      ← 导出脚本，查 A 系统失败题
    ↓
data/poc_2.7/problem_list.json              ← 题目清单（6083 题）
    ↓
continuation_collector.py                   ← 续传系统 collector，从清单取题
    ↓
p27_continuation_runs (DB)                  ← 续传系统做题队列
```

### 各环节代码位置

| 环节 | 代码 | 关键逻辑 |
|---|---|---|
| A 系统做题 | `/Users/user/AI-Math-Normal-Solver/` pipe 系统 | feeder `--tier 1,2,3` 选题，collector 判定终态写入 `devin_problem_runs` |
| 导出失败题 | `scripts/export_new_problems.py` | 查 `devin_problem_runs` 中 status ∈ MODEL_FAILURE_STATUSES 的题，写入 problem_list.json |
| 续传收集 | `src/continuation_collector.py` | 从 problem_list.json 取题，创建 `p27_continuation_runs` 记录 |

## 2. 最终 tier 分布（全部 6082 题都查到了 tier）

### tier 追溯方法（三层）

| 层 | 数据源 | 覆盖题数 | 说明 |
|---|---|---|---|
| 1 | `problem_extraction_progress` DOCUMENT JOIN（_key=problem_id） | 5866 题 | polymath/deepmath/oda_math 等题的 _key = problem_id 字符串 |
| 2 | `devin_problem_runs.difficulty_tier` | 216 题 | compfiles/omni_math/fate/aime_2024/mathnet 等题的 _key 是数字，DOCUMENT JOIN 查不到，但 devin_problem_runs 有 difficulty_tier 字段 |
| 3 | exp_id 中的 tier 标记（如 `tier2-auto`/`t1-`） | 辅助验证 | 与层2结果一致 |

### 最终分布

| tier | 题数 | 占比 | 是否符合条件 |
|---|---|---|---|
| tier=1 | 6005 | 98.7% | ✅ 符合 |
| **tier=2** | **67** | 1.1% | ❌ 不符合 |
| **tier=3** | **10** | 0.16% | ❌ 不符合 |
| **总计** | **6082** | 100% | — |

### problem_extraction_progress 的两种记录格式

| 格式 | _key 示例 | problem_id 字段 | 数量 | 说明 |
|---|---|---|---|---|
| 字符串 _key | `polymath_00048` | null | 2,424,305 | 大部分题，_key = problem_id 字符串 |
| 数字 _key | `329030` | `compfiles_imo1963p5` | 36,005 | 少数题，_key 是数字，problem_id 字段存题名 |

DOCUMENT JOIN `DOCUMENT(CONCAT("problem_extraction_progress/", r.problem_id))` 只能查到字符串 _key 的题。数字 _key 的题需要通过 `devin_problem_runs.difficulty_tier` 追溯。

### devin_problem_runs.difficulty_tier 可靠性验证

- 对 polymath tier=1 的 20 题样本：devin_problem_runs 中 difficulty_tier 全部为 null（不可靠）
- 对 compfiles/omni_math/fate/aime 题：devin_problem_runs 中 difficulty_tier 有值且与 exp_id 中的 tier 标记一致（可靠）
- 结论：devin_problem_runs.difficulty_tier 对数字 _key 的题可靠，对字符串 _key 的题不可靠（为 null）

## 4. 发现的问题

### 问题 1：export_new_problems.py 没有 tier=1 筛选

`scripts/export_new_problems.py:27-31,48-58` 的查询只按 status 过滤，**完全没有 tier 条件**：

```python
# 第27-31行：只列模型能力失败的 status
MODEL_FAILURE_STATUSES = [
    'failed_token_limit', 'ai_gave_up', 'failed_thinking_spin',
    'failed_tool_stall', 'failed_no_proof', 'failed_stall'
]

# 第50-57行：查询只 FILTER r.status IN @statuses，不 JOIN problem_extraction_progress 过滤 tier
def get_a_failed_problems(db):
    failed = list(db.aql.execute(
        'FOR r IN devin_problem_runs '
        'FILTER r.status IN @statuses '
        'COLLECT pid = r.problem_id INTO runs = r '
        'LET last_run = (FOR x IN runs SORT x.ended_at DESC LIMIT 1 RETURN x)[0] '
        'FILTER last_run.status IN @statuses '
        'RETURN {problem_id: pid, exp_id: last_run.exp_id, status: last_run.status}',
        bind_vars={'statuses': MODEL_FAILURE_STATUSES}, ttl=300))
    return failed
```

normal-solver 的 feeder 默认 `--tier 1,2,3`，所以 tier=2/tier=3 的失败题也会被导出。

### 问题 2：problem_list.json 历史构建不干净

216 题（compfiles/omni_math/fate/aime_2024/mathnet）不在 problem_extraction_progress 中（_key 是数字，DOCUMENT JOIN 查不到），但出现在 problem_list.json 里。通过 devin_problem_runs.difficulty_tier 成功追溯了所有 216 题的 tier。

### 问题 3：混入了已解出的题

15 题 candidate_solved（14 tier=2 + 1 tier=1）被 normal-solver 解出来了，但仍然在续传系统队列中。虽然 `MODEL_FAILURE_STATUSES` 列表里没有 `candidate_solved`，但这些题还是混入了 problem_list.json——说明它们是通过早期版本的脚本或手动操作进入的，不是通过当前 export_new_problems.py 导出的。

### 问题 4：混入了基础设施失败的题

5 题 tier=2 dead_session（基础设施失败，不是模型能力失败）在续传系统队列中。`MODEL_FAILURE_STATUSES` 列表里没有 `dead_session`，说明这些题也是通过其他途径进入的。

## 5. 影响评估

### 对已完成题的影响

**无影响**——所有 77 题 tier≠1 和 1 题 tier=1 已解出的题都是 `prepared` 状态（还没做）。128 题 COMPLETED 全部是 tier=1 的题。

### 对系统资源的影响

- 78 题（1.3%）不符合条件但在队列中等待被做
- 其中 15 题 candidate_solved 是纯浪费——已经解出来了再续传
- 5 题 dead_session 是基础设施失败，续传可能也无法解决
- 46 题 tier=2 模型能力失败 + 10 题 tier=3 模型能力失败——这些题续传系统可能能解出来，但不符合"只做 tier=1"的定位

### 对数据可信度的影响

- 98.7% 的题是 tier=1，大部分是对的
- 但"题目来源是否正确"这个基本问题没有保证——下一个 AI 无法信任 problem_list.json 的正确性

## 6. 根因分析

### 根因 1：export_new_problems.py 不 JOIN problem_extraction_progress 过滤 tier

查询只查 `devin_problem_runs`，不 JOIN `problem_extraction_progress` 验证 tier。导致 tier=2/tier=3 的失败题混入。

### 根因 2：problem_list.json 历史构建不干净

216 题通过非 export_new_problems.py 途径进入 problem_list.json。可能来源：
- 早期版本的 export 脚本逻辑不同
- 手动添加
- problem_extraction_progress 集合后来才建立的

### 根因 3：export_new_problems.py 的 status 列表不排除 candidate_solved 和 dead_session

虽然 `MODEL_FAILURE_STATUSES` 列表里没有 `candidate_solved` 和 `dead_session`，但这些题还是混入了 problem_list.json。说明 problem_list.json 的构建历史不干净。

---

## 7. 建议修复方向

### 修复 1：export_new_problems.py 加 tier=1 筛选

在 `get_a_failed_problems` 的 AQL 查询中 JOIN `problem_extraction_progress` 并 `FILTER p.difficulty_tier == 1`。注意需要处理两种 _key 格式（字符串和数字）。

### 修复 2：写清洗脚本

从 problem_list.json 和 p27_continuation_runs 中移除：
- tier ≠ 1 的题（77 题）
- A 系统最后 status = candidate_solved 的题（15 题）
- A 系统最后 status = dead_session 的题（5 题）

所有不符合条件的题都是 prepared 状态，移除不会影响已完成的题。

### 修复 3：加 source 验证到 collector

`continuation_collector.py` 加载 problem_list.json 时验证每道题的 tier，跳过 tier≠1 的题。

## 8. 审查方法说明

### 三层证据交叉验证（按 verify-with-logs rule）

| 层 | 工具 | 查什么 |
|---|---|---|
| DB 结果 | AQL DOCUMENT JOIN `p27_continuation_runs` → `problem_extraction_progress` | 覆盖 5866 题（字符串 _key） |
| DB 结果 | AQL 查 216 题在 `devin_problem_runs` 中的 `difficulty_tier` | 覆盖 216 题（数字 _key） |
| DB 结果 | AQL 查 216 题在 `devin_problem_runs` 中的最后 `status` | 验证是否真的是失败题 |
| 代码 | 读 `export_new_problems.py` 源码 | 查询逻辑是否有 tier 筛选 |
| 文件 | 读 `problem_list.json` | 题目清单的实际内容 |
| exp_id | 正则提取 `tier\d+` / `t1-` / `t2-` 标记 | 辅助验证 tier |

### 关键 AQL 查询

```aql
// 层1：DOCUMENT JOIN（字符串 _key）
FOR r IN p27_continuation_runs
  LET p = DOCUMENT(CONCAT("problem_extraction_progress/", r.problem_id))
  COLLECT tier = p ? p.difficulty_tier : null WITH COUNT INTO n
  RETURN {tier: tier, count: n}

// 层2：对 DOCUMENT JOIN 查不到的题，查 devin_problem_runs
FOR a IN devin_problem_runs
  FILTER a.problem_id == @pid
  SORT a.ended_at DESC LIMIT 1
  RETURN a.difficulty_tier
```

### problem_extraction_progress 的两种 _key 格式

```
格式1：_key="polymath_00048"  problem_id=null  tier=1  （242万题，DOCUMENT JOIN 可查）
格式2：_key="329030"  problem_id="compfiles_imo1963p5"  tier=1  （3.6万题，DOCUMENT JOIN 不可查）
```
