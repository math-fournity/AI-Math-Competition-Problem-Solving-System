## 七、新需求：session.db 落盘快照检测 thinking spin + 提示词等待时长限制（用户提出）

### 需求原文

用户指出：
> 注意，我们给 AI 的做题时间几乎是没有限制的，只要它真的在工作。这一点其实可以很容易地确定，因为 devin cli 中的 AI 在 thinking spin 阶段是在 session.db 中没有落盘的。所以完全可以对某个 devin 实例在 session.db 中的落盘情况进行快照，如果 5 分钟之后没有任何变化，那么说明这个 devin cli 很可能遭遇了限流或者其他卡住的情况。另外这样就需要在给 devin cli 的提示词中明确告知 AI，等待任何内容的时长，不能超过 2 分钟，2 分钟等待之后没有结果，必须输出等待的次数用于在 session.db 中落盘相关的 trajectory 记录。

### 需求拆解

1. **做题时间无限制原则**：只要 AI 真的在工作，就给它足够时间——不设硬性超时
2. **"真的在工作"的判定方法**：devin cli 在 thinking spin 阶段在 session.db 中没有落盘 → 可以用 session.db 落盘快照对比检测
3. **5 分钟快照对比**：对 session.db 落盘情况做快照，5 分钟后对比，无变化 = 可能遭遇限流或卡住
4. **提示词约束**：告知 AI 等待任何内容的时长不能超过 2 分钟，2 分钟后无结果必须输出"等待第 N 次"标记，用于在 session.db 中落盘 trajectory 记录

### 可行性调查（深入代码 + 实测）

#### 调查1：session.db 的落盘时机

实测 `~/.local/share/devin/cli/sessions.db`（32GB SQLite）：
- `sessions` 表：有 `last_activity_at` 字段
- `message_nodes` 表：每条消息一行，有 `created_at` 时间戳

**关键发现**：`-p` 模式（非交互模式，本系统使用的模式）下，`message_nodes` 在 devin cli **退出时一次性写入**，不是实时落盘：
- 审计 session `ripe-sandwich`：33 条 message_nodes，全部 `created_at = 1787313557`（同一秒）
- 续传 session `deserted-canvas`：message_nodes 全部 `created_at` = 07:03:02，而 session 创建于 07:00:37——2.5 分钟的 thinking 过程中 session.db 无任何新记录

**结论**：用户的核心洞察"thinking spin 阶段在 session.db 中没有落盘"是**正确的**，但原因比用户想的更极端——`-p` 模式下**整个运行期间** session.db 都不落盘（不只是 thinking spin 阶段），直到 devin cli 退出时才一次性写入。

**这意味着**：用户提出的"5 分钟 session.db 快照对比"方案在 `-p` 模式下**不直接适用**——因为运行期间 session.db 始终无新记录，5 分钟对比无变化是常态（无论 AI 是否在 thinking spin），无法区分"正在 thinking"和"卡住了"。

#### 调查2：tmux pipe log 是实时落盘的

`continuation_launcher.py:691,733`：`tmux pipe-pane -t {session_name} "cat >> {tmux_pipe_path}"` 实时把 tmux pane 输出写入 `tmux_pipe.log`。

实测 `00001653/round2/tmux/tmux_pipe.log`：1380 字节，包含 AI 的输出文本——**这是实时落盘的**。

**结论**：tmux pipe log 是 `-p` 模式下唯一实时落盘的 AI 输出源。用户方案的检测目标可以从 session.db 切换到 tmux pipe log：
- **5 分钟 tmux pipe log 文件大小快照对比**：5 分钟前 `stat -f%z tmux_pipe.log` vs 现在，无变化 = AI 未输出任何内容 = 可能卡住

#### 调查3：提示词中要求 AI 输出"等待标记"的可行性

用户提出：提示词中告知 AI "等待任何内容的时长不能超过 2 分钟，2 分钟后无结果必须输出等待的次数"。

**可行性分析**：
- AI 输出的文本会实时出现在 tmux pane 中（被 `tmux pipe-pane` 实时写入 `tmux_pipe.log`）
- 如果 AI 每 2 分钟输出一次"等待第 N 次"标记，`tmux_pipe.log` 会持续增长
- launcher 可以检测 `tmux_pipe.log` 的增长——5 分钟内无增长 = AI 既没有在 thinking 也没有输出等待标记 = 真卡住了
- 如果 `tmux_pipe.log` 在增长（AI 在输出等待标记）但 export 文件不存在（devin cli 没退出）= AI 在等待某个外部条件（如 rate limit 恢复）

**但有一个问题**：thinking spin 时 AI 不输出任何文本到 tmux pane——thinking 内容在 devin cli 内部处理，不写入 stdout。所以即使 AI 在正常 thinking，`tmux_pipe.log` 也不会增长。

**这正是用户方案要解决的**：如果提示词要求 AI "等待超过 2 分钟时必须输出等待标记"，那么：
- AI 在 thinking → 不输出 → `tmux_pipe.log` 不增长 → 但这是正常的（thinking 本来就不输出）
- AI 在等待外部结果（如 rate limit）→ 提示词要求它每 2 分钟输出"等待第 N 次" → `tmux_pipe.log` 增长 → launcher 知道 AI 还活着
- AI 卡住了 → 既不 thinking 也不输出等待标记 → `tmux_pipe.log` 不增长 → 但怎么区分"正常 thinking"和"卡住了"？

**关键问题**：thinking spin 和真卡住在 `tmux_pipe.log` 层面表现相同（都不增长）。用户的提示词方案能解决"等待外部结果"的情况（AI 输出等待标记），但不能解决"thinking spin vs 真卡住"的区分——因为 thinking 时 AI 不会输出等待标记（它在思考，不在等待）。

#### 调查4：devin cli 的 thinking 输出机制——**用户纠正，我之前推断错误**

我之前从 `collector.py:90` 的 `THINKING_PATTERNS = ["Thinking ·", "Thinking...", "thinking", "⠐", "⠒"]` 推断"thinking 时 devin cli 输出状态标记到 tmux pane"——**这是错误的**。

**用户指出**：非交互模式下 tmux pane 中没有有效的 devin cli 运行时内容。

**实测验证（用户纠正后）**：

| 指标 | 结果 |
|---|---|
| pipe log 大小 / export 大小 | **0%-2.5%**（10 个样本全部 < 5KB，export 都是 130-290KB） |
| pipe log 中 "Thinking" 标记 | **10/10 全部 0 匹配** |

`THINKING_PATTERNS` 是交互式 TUI 模式的渲染行为——TUI 模式下 devin cli 在终端渲染 "Thinking ·" 等状态字符。`-p` 非交互模式下**没有 TUI 渲染**，pane 里只有 AI 的最终 message content（输出到 stdout 的文本），thinking/reasoning_content 完全不在 pane 里。

**结论**：非交互模式下 tmux pane 中确实没有有效的 devin cli 运行时内容。pipe log 只捕获了 AI 的最终 message content（如 "Let me write the proof to proof.md" + proof 内容、审计报告 XML），是最终输出的 1-2%，thinking 期间 pipe log **不增长**。

### 两个方案都不可行——需要重新思考

基于调查 1-4 的实测结果：

| 方案 | 可行性 | 原因 |
|---|---|---|
| session.db 快照对比 | **不可行** | `-p` 模式下 message_nodes 退出时一次性写入，运行期间无新记录 |
| tmux pipe log 快照对比 | **不可行** | `-p` 模式下 pane 只有最终 message content，thinking 期间 pipe log 不增长——无法区分"thinking"和"卡住" |

**核心困难**：`-p` 非交互模式下，AI 的 thinking/reasoning_content 既不写入 session.db（退出时才落盘），也不输出到 tmux pane（无 TUI 渲染）。在 thinking spin 期间，**没有任何实时落盘的数据源**能反映 AI 的工作状态。

pipe log 不增长的 4 种情况（无法区分）：
1. AI 在 thinking（正常）
2. AI 在等待 tool 执行（正常）
3. AI 遭遇 rate limit（异常但可能自动恢复）
4. AI 卡住了（异常）

用户的提示词方案（让 AI 每 2 分钟输出等待标记）在 `-p` 模式下也有局限：
- AI 在 thinking 时不会检查"是否等了 2 分钟"——它在思考，不在等待，不会输出等待标记
- AI 在等待 tool 结果时被阻塞，不能输出 message
- 只有 AI 主动生成 message 时才会输出到 stdout

### 待用户决策的替代方向

既然 session.db 和 pipe log 都不可行，可能的替代方向：

**方向A：进程级检测（不依赖落盘数据）**
- 检测 devin cli 进程的 CPU 使用率——thinking 时有 CPU 活动，卡住时 CPU 低
- 检测 devin cli 进程的网络连接——到 API 的 ESTABLISHED 连接（is_devin_waiting_api 思路）
- 问题：033 裁定"不提取 is_devin_waiting_api"（依赖代理端口假设）；CPU 检测也不是确定性的

**方向B：放弃精确检测，用 max_runtime 兜底 + Master Agent SOP 检查**
- 033 的方案：max_runtime 兜底（如 600s），不试图区分 thinking 和卡住
- Master Agent 通过 SOP 检查发现异常（如某 session 运行时间异常长）
- 问题：无法在 max_runtime 之前发现问题——但符合"适度依赖 Master Agent"原则

**方向C：提示词约束 + pipe log 检测的组合（部分可行）**
- 提示词要求 AI 在**两次 tool 调用之间**的等待超过 2 分钟时输出等待标记
- 这只能覆盖"等待 tool 结果"的情况，不能覆盖"thinking spin"
- 配合 pipe log 快照：pipe log 增长 = AI 输出了 message（正常）；pipe log 不增长 = AI 在 thinking 或卡住（无法区分，用 max_runtime 兜底）

**方向D：改变运行模式**
- 用交互模式而非 `-p` 模式——交互模式有 TUI 渲染，pane 有 "Thinking ·" 标记
- 问题：`noninteractive-solver-run` rule 要求 `-p` 模式；交互模式不便于批量运行

**方向E：devin cli 增加心跳机制（需要改 devin cli 本身）**
- devin cli 在 thinking 时定期输出心跳标记到 stdout（如每 30 秒输出 "[HEARTBEAT] thinking..."）
- 这需要修改 devin cli 的代码，不是本系统能控制的
