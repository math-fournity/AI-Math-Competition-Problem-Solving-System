# 未来实现 AI 启动提示词

你将实现“最终成品解题系统”的一个工作包。不要从旧 commit message 或单份设计文档猜目标。

## 第一阶段：强制认知加载

按顺序完整读取：

1. 根 `README.md`；
2. 根 `AGENTS.md`；
3. `dev-docs/057-最终成品系统大图与产品定义.md`；
4. `dev-docs/058-最终成品系统Feature-List与需求追踪.md`；
5. `dev-docs/064-当前实现差距与实施路线总图.md`；
6. `dev-docs/065-工作包分层Trajectory设计缺陷复盘与纠偏记录.md`；
7. 本目录 `README.md`；
8. 你领取的 `WP-XX-*.md` 全文；
9. WP“前置认知”列出的专题文档、代码、测试和外部只读资料。

不要跳过当前代码事实复核。行号会漂移，用函数名/关键字定位。

## 第二阶段：领取前检查

```bash
git status --short --branch
git log -5 --oneline
```

- 用户/其他会话的改动不得覆盖。
- `tmp/` 等现有运行资产不属于你。
- 若前序 WP 接口与文档不同，先读执行记录并查代码；无法安全适配时报告，不猜。
- 若工作需要修改外部 key 表、生产 DB/Redis、真实进程，确认 WP 明确授权且用户已批准。

## 第三阶段：实施纪律

1. 只做本 WP 的目标和必要文档同步。
2. 不顺手实现后续包。
3. 不新增与 Gate 平行的控制机制。
4. 不把用户语义改成“更容易编码”的旧语义。
5. Round 窗口结束不是题目永久失败。
6. `proof+boxed` 不是最终数学正确，形式化审计才是门槛。
7. key capacity 可配置；不写死一 key 一实例或两实例。
8. 目标最大并发30不是代码默认 concurrency。
9. 语义不确定时保留证据、交 Master Agent，不堆启发式。
10. 所有失败/测试/验证资产保留；不只写 `/tmp`。
11. 文件修改使用显式路径；破坏性动作先 dry-run。
12. 改调度/终态/审计后跑工作包指定的 sim/测试门禁。
13. Observer必须亲自使用分层reader读取完整原始trajectory；map/HANDOVER/notes只作索引，
    只有notes无scan/tail/inspect使用证据不得验收。

## 第四阶段：完成定义

只有同时满足以下条件才可声明 WP 完成：

- 覆盖的 Feature ID 有代码/文档/测试证据；
- WP 验收 checklist 全部通过；
- 当前态与目标态文档同步；
- 没有泄漏 key/secret；
- 没有删除历史 Round 资产；
- 兼容/迁移行为有测试；
- 写执行记录；
- 明确下一 WP 可依赖的接口和仍未解决的事项。

若只能完成一部分，诚实标为 partial，不要为了勾选状态扩大实现或伪造验证。
