## 一、工作宪法

1. 先读根 README、AGENTS，再读 057、058、自己的 WP 全文。
2. 每次只执行一个 WP；发现跨包需求写入交接，不顺手扩大范围。
3. 当前态以代码/测试/实物为准，目标态以 057~063、065纠偏和用户裁定为准。
4. 不把默认 Round 数作为题目寿命；未正确解答的题保留无限继续资格。
5. 解题候选成功必须经过充分形式化验证和独立审计。
6. key 是带 capacity 的资源，ACP 实例领取 lease，不假定永久一对一。
7. 目标最大并发解题管线暂定30；实际值由 DB/用户决定，不写死默认。
8. 不追求不可靠完全自动化；边缘语义交 Master Agent/SOP。
9. Gate 是唯一关键动作控制机制；不新增平行控制系统。
10. 不过度设计；优先最小修正现有代码和文档。
11. 每轮全部资产保留；验证脚本不得只留 `/tmp`。
12. 调度、终态、key、审计改变必须有隔离测试/sim，再触碰生产。
13. 外部 key 表、生产 DB、Redis 和运行实例的真实修改需要对应 WP 授权及用户确认。
14. Git 显式路径 add；不碰用户现有 `tmp/` 和其他无关改动。
15. 053分层trajectory是既有硬要求：observer必须亲自使用reader扫描完整原始现场；map、
    HANDOVER、notes只能作索引，只有notes无reader使用证据不得判编排完成。

## 六、用户决策点

以下参数/外部动作不能由执行 AI 擅自决定：

- 实际 batch concurrency（目标最大30，但运行值由用户设置）；
- 每个 key 的 capacity；
- 从外部 key 表实际领取多少 key；
- 是否/何时迁移历史 `TRUNCATED_AT_MAX` DB 记录；
- 何时开始真实30并发放量；
- 形式化工具无法覆盖某题时，是否接受其他可信证明方案；
- 是否启用任何自动 backend fallback。

执行 AI 可以实现配置能力、dry-run、测试和证据，不得替用户拍板真实数值或外部变更。
