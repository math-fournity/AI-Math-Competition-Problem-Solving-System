# WP-02 — 生产观察者/解题者核心编排

> **覆盖 Feature**：ORCH-01~11、AST-02/04/05、CON-04
> **依赖**：WP-01、WP-03、WP-04
> **吸收旧包**：056/WP-R2 的 v3 方案，但必须用新 Round 和形式化合同修订后实施。

## 一、目标

在生产解题管线接入专职 round1 solver、后续 observer、后续 solver 的串行递归消化链。
observer/solver 每个都是独立 ACP/legacy 实例和独立资产角色；同题只占一条管线槽。v1/v2
旧路径在迁移验证前保留回退，不因 v3 接线大改 DB/队列/Gate 架构。

### 当前代码基线与预期触点

`templates/v3` 三文件，尚无 `start_observer/check_observer` 和 v3 sim。预期触点：launcher、
round log/schema、模板渲染、`src/sim/fake_devin.py`/scenarios/assertions、相关 Gate docstring、

## 三、角色与状态合同

- R1：solver。
- 后续未完成：先 observer 消化紧邻前轮，产分析笔记；再 solver 推进明确缺口。
- observer 和 solver 不并发，且都属于同一题/同一管线槽。
- 角色实例分别保存 prompt、ACP通知、thinking、notes、formal、result metadata。
- 窗口额度按 WP-01 的可靠计数，不把 observer/solver 混乱重复计成题目寿命。
- observer 失败不覆盖前轮现场；由现有失败/Supervisor机制处理。

## 四、实施任务

1. 根据 WP-03 的模板/资产合同实现 render，不复制散落 prompt 字符串。
2. 实现 observer 启动、完成检查和资产登记；验证 notes mtime/非空/角色归属。
3. solver 启动只注入题目、最新分析笔记、当前 formal 状态和必要路径。
4. 主循环接入角色轮换、窗口计数和中断恢复。
5. rounds_log 增加最小角色/notes/formal/instance 元数据，兼容旧记录。
6. BUDGET_STARVED、proof候选、observer完成和异常分别写直接证据。
7. 保持同一管线槽：observer pending + solver running 总数纳入现有并发。
8. 复用启动/kill/重入队 Gate；更新 docstring 论证，不复制新控制体系。
9. 为旧 `--method v2` 做行为零变化回归；新策略默认切换需用户后续决定。

## 五、1962 行为验收

- observer 首动作是 scan/tail，不通读完整 thinking；
- 能识别笔记尾部盲区、数学欠账和旧笔误；
- notes 有推导骨架、死路原因、单一下一缺口、形式化状态；
- solver 不大面积重做已闭环 case；
- solver 的新增数学/形式化资产被下一 observer 接上；
- 任何验证脚本从临时目录归档。

## 六、明确不做

- 不在本包实现 key 池/真实 per-instance config（WP-06/07）。
- 不实现 formal audit（WP-05）。
- 不删除 v1/v2。
- 不把三个后端抽象成庞大平台；只实现本包所需接口。
- 不新增第二套 Gate。

## 七、测试

1. R1截断→observer notes→solver完成。
2. observer失败/无notes，旧资产不丢、可恢复。
3. solver再截断→下一observer消化尾部。
4. 跨窗口继续，角色和绝对Round正确。
5. 形式化不足审计意见进入下一observer输入。
6. 同题任意时刻最多一个实例；多题并发不超过DB值。
7. legacy v2 回归不变。
8. sim全部资产字段和flow顺序断言。
