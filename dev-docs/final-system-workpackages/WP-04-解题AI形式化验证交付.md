# WP-04 — 解题 AI 形式化验证交付

> **覆盖 Feature**：FML-01~05、FML-11、PRM-05、AST-07
> **依赖**：无（模板最终由WP-03/02消费）
> **边界**：建立解题侧资产与验证合同，不实现审计裁决。

## 一、目标

让解题 AI 的“候选成功”同时产出 proof、形式化源码、可重跑命令、覆盖说明和日志；支持
跨 Round 增量形式化，杜绝验证只写自述或脚本遗留 `/tmp`。

### 当前代码基线与预期触点

当前 v2/v3 solver模板已有笼统“整体形式化验证”文字，但 launcher只以proof/boxed判候选，
没有formal目录合同、运行器、日志或rounds_log路径。预期触点：三类模板、一个最小形式化
执行/归档模块（命名由现有src结构裁定）、资产检查、round log接口、单测fixture；生产接线
留给WP-02。

## 二、前置认知

读 057、058、060、061、1962 R6 proof/工作笔记/math_audit 和当前 `templates/v2/v3`。
检查 repo 可用 Lean/Python/Sage 等环境，但不要擅自安装大型新工具或联网依赖；以现有环境
和可隔离测试为准。

## 三、实施任务

1. 冻结最小目录合同：`proof.md`、`formal/`、`formal_verification.md`、`formal_logs/`。
2. 提供通用验证运行器/归档 helper（若现有函数可复用则不新建框架）：执行命令、捕获
   stdout/stderr/版本/退出码，不接受只在 `/tmp` 的输入。
3. 在 round1/solver prompt 中加入增量形式化、诚实边界、候选成功语义。
4. observer notes 合同加入 formal 状态和失败日志索引。
5. 完成候选 proof 时登记 formal 路径到 rounds_log/资产合同接口（生产接线由WP-02）。
6. 提供至少一个可信内核正样本和一个有限 Python 旁证样本，清楚区分作用。
7. 检查 secret、答案泄漏和外部依赖不进入 formal 包。

## 四、充分形式化原则

- 普遍命题默认需要可信证明内核；
- Python 有限扫描不能单独证明无限完备性；
- 若数学证明先归约到有限集合，程序必须保存归约依据和完整覆盖程序；
- `sorry/admit/额外axiom` 必须显式报告，候选可保存但不得声称充分；
- 形式化工具失败是下一轮输入，不删除 proof。

## 五、明确不做

- 不承诺一轮完成所有形式化。
- 不自研证明助手。
- 不实现 audit PASS/FAIL（WP-05）。
- 不为形式化建立新 Gate/SOP。
- 不把所有题强行塞进同一个固定 Lean 模板。

## 六、测试

1. 正样本：源码和命令成功，日志归档。
2. `sorry` 样本：运行器记录，不能被上层当充分。
3. Python有限样本：coverage说明明确有限。
4. `/tmp`脚本：回收前复制；缺失时报错而非虚构通过。
5. 跨Round：前轮formal失败，后轮读取并修复，旧日志保留。
6. prompt渲染包含候选成功/形式化合同且不含题目专属答案。

- [ ] 临时脚本资产化
- [ ] solver/observer合同更新
- [ ] 正反样本通过
- [ ] 没有把有限搜索称为普遍证明
- [ ] 给WP-05提供稳定输入接口
