## 五、todo_write 接线点完备性

### 5.1 ✅ 完备

8 个 SOP 文档末尾均有"你需要建立的 todo list"段，且 `run.py:print_todo_directive` 每次执行后打印：
```
请用 todo_write 建立本轮 todo list。
todo list 的最后一项必须是：
  执行下一个脚本: python -m scripts.sop.run
```

每个步骤的 todo 指令都包含：
- 该步骤的具体任务（读检查结果/分类/判断/修复/写报告）
- "填写 report.md 报表"（8 步都有）
- "最后一项固定是：执行下一个脚本"

### 5.2 ⚠️ 潜在风险

todo 指令是**打印到 stdout**，AI 需自己读到并执行 `todo_write`。如果 AI 上下文被压缩，stdout 内容可能丢失。但 SOP 文档本身也被打印（含 todo 段），所以只要 AI 读了 SOP 文档就能看到 todo 要求——**双重冗余**，风险可控。

## 六、SOP 拆分粒度合理性

### 6.1 当前 8 步负载分布

| 步骤 | 负载 | 自动化检查 | AI 判断 | 说明 |
|---|---|---|---|---|
| 01 系统健康 | **重** | 8项+门闸Y+行为流水 | SESS深度+ENV+H1综合判断 | 塞了太多：进程+进度+Session+门闸+流水+SESS+ENV |
| 02 数据完整性 | **重** | 全量200run+6项DB级 | 5项深度(2a-2e) | 自动化部分重，AI 深度部分也重 |
| 03 alert分类 | 轻 | 查询50条 | 逐个分类 | 合理 |
| 04 C类AI判断 | 中 | 查询10条候选 | C1-C6逐个读文件判断 | 合理（AI 核心价值步） |
| 05 代码修复 | 中 | git log | 汇总+修复+验证+sim门禁 | 跨步骤信息传递是断点 |
| 06 报告+Self-check | 中 | WORKLOG状态 | 写报告+22项self-check+resolve alert | 合理 |
| Z 元检查 | **重** | SOP全貌 | 元检查6步+整体6项+方向性3项+审计7项 | "反思一切"步，容易做不充分 |
| OP 运营知识 | 轻 | ENV验证 | 读运营知识 | 合理 |

### 6.2 粒度问题

1. **01 过重**：系统健康+进度+Session+门闸+行为流水+SESS深度+ENV 全塞一步。可考虑把 SESS 深度和 ENV 拆到 OP（OP 现在很轻）。
2. **02 过重**：全量文件检查+6项DB级+5项AI深度。自动化部分和 AI 深度部分可拆分。
3. **Z 过重**：元检查+整体+方向性+审计四部分，是"反思一切"步骤。实际执行中容易只做前两部分就跳过。
4. **05 跨步骤断点**：依赖 03/04 的汇总，但 check_05 不自动汇总。
5. **OP 过轻**：只做 ENV 验证+读运营知识，和 01 的 ENV 检查重复。

### 6.3 建议（不强制，供 Z 步骤决策）

- 考虑把 01 的 SESS 深度检查移到 OP（OP 现在过轻，且 OP 是循环末尾适合做深度检查）
- 考虑给 check_05 加 DB 查询：查 `p27_monitor_alerts` 中 `status=new` 且 `alert_type` 属于代码 bug 类的 alert，自动汇总给 AI
- 考虑把 Z 的"审计"部分（AUDIT-01~07）独立成每 5 轮一次的额外步骤，不每轮都做
