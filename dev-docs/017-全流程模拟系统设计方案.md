# 017 — 全流程模拟系统（full-flow simulation）设计方案

> **这是什么**：把"devin cli 扮演的世界"换成代码剧本演员，让解题系统的
> 全流水线（launcher调度/多轮续传/截断判定/防抖/门闸/注册表/Redis队列）
> 在完全隔离的环境里 100% 真代码真跑的模拟系统。
>
> **为什么值得建**：016 事故的核心教训是"判定+调度逻辑的 bug 只有真跑才
> 暴露，而真跑烧配额、建真 session、动真数据"。本系统建成当天（2026-08-20）
> 首批 7 个剧本运行即捕获 **5 个真 bug**（§5），其中 P0 级一个——多轮续传
> 的截断引擎在当前代码里不可达，生产中真实截断被误判为 dead_session。
>
> **与其他机制的关系**：行为流水管"看见"（observability）、门闸管"拦住"
> （step_gate）、每事故回归测试管"不复吃旧堑"（test_016_*）、本系统管
> **"整条流水线还转得对"**——四者互补。与 StepGate 范式的关系见
> `docs/patterns/StepGate.md`（sim 还可作为门闸机制本身的全流程测试场）。

---

## 1. 核心思想：命令行层注入，世界=文件+进程行为

模拟"AI 世界"的可行注入点不在内部接缝（mock 返回值会破坏控制流，且
需要逐点塞模拟分支），而在**命令构造处**：`launch_solve`/`start_handover`
用 tmux 启动 `devin -p` 的那一个 f-string。

SIM_MODE=1 时命令换成 `python -m src.sim.fake_devin ...`，但**命令结构
与生产完全一致**（同样的 `--export`、同样的 `echo $? > DONE.md`、同样的
`sleep 999999`）。于是：

- 世界对外的一切输出（export JSON / proof.md / HANDOVER.md / DONE.md /
  tmux pane 内容 / 进程退出）由剧本演员按剧本真实产生；
- launcher/feeder/门闸/注册表/判定函数面对的是**真文件、真 tmux session、
  真 DB/Redis 写入**——一行被测代码都不用改；
- Pipe A 的 conversation_mapper（面包屑地图）是真代码真跑，被测逻辑不变。

这就是"最大程度的模拟"的正确实现：不是重写系统，是给系统喂一个
可编程的世界。

## 2. 隔离设计（可与生产并行）

| 层 | 旋钮 | sim 取值 | 生产取值 |
|---|---|---|---|
| ArangoDB | `ARANGO_DB`（env化） | `p27sim`（独立库，setup自动创建） | `xishujuzhen_math_glm52` |
| Redis | `P27_REDIS_PREFIX`（env化） | `p27sim:`（独立键空间） | `p27:` |
| 文件根 | `SOLVER_BASE`/`TRAJECTORY_BASE`（既有env） | `<repo>/tmp/sim/...` | D盘 |
| tmux/注册表 | batch_id 派生命名 | `p27sim-*`（题目id强制`sim_`前缀） | `p27-full-*` |

三重安全护栏（setup/teardown 都检查）：SIM_MODE=1、ARANGO_DB≠生产库名、
SOLVER_BASE 不在 /Volumes/data——任一不满足拒绝执行，防误伤生产。

题目 id 强制 `sim_` 前缀的原因：tmux session 名带 pid 后缀
（`p27-s{seq}-solve-{pid}-r{N}`），且 launch_solve 启动前有同名清理
`tmux_kill`——pid 撞名会误杀生产 session。

## 3. 组件与用法

```
src/sim/
  scenarios.py    剧本库（7个，每个对应launcher一条真实分支路径）
  fake_devin.py   剧本演员（solve/handover两角色，读work_dir/sim_scenario.json）
  setup.py        造批次（run字段与continuation_collector完全一致）
  run_sim.py      编排：setup→真feeder→真launcher→等终态→断言→teardown
  assert_final.py 四源终态断言：DB终态/Redis归属/flow事件链+016不变量/tmux残留
  teardown.py     清场（默认保留DB和文件现场供post-mortem）
```

用法：
```bash
.venv/bin/python -m src.sim.run_sim --scenario solve3            # 跑完自动清场
.venv/bin/python -m src.sim.run_sim --scenario chaos_016 --keep  # 保留现场排查
```

剧本清单及覆盖路径：

| 剧本 | 剧情 | 考的分支 | 结果(2026-08-20) |
|---|---|---|---|
| solve3 | seed截断→R2截断→R3完成 | 多轮续传主干全链 | 8/8 ✅ |
| first_try | R2直接完成 | 单轮完成+kill(completed) | 8/8 ✅ |
| never | 永远截断(max=3) | TRUNCATED_AT_MAX | 8/8 ✅ |
| dead | 退出无proof无export | dead_session判定+清理 | 8/8 ✅ |
| stall | 光思考不产出 | stall检测(--stall-seconds 20) | 8/8 ✅ |
| h_timeout | Pipe A挂起不产出 | 超时kill+v1回退 | 8/8 ✅ |
| chaos_016 | 4题并发永远截断 | 016三道P0闸回归（无快速重launch/launch不超轮数/无requeue风暴） | 23/23 ✅ |

断言层的 016 不变量：同一 run 无 5 秒内重复 launch_solve（失控循环特征）、
launch 次数 ≤ max_rounds、requeue 事件密度在轮数合理范围内、redis
pending/running 清零、四源（DB/Redis/flow/tmux）交叉一致。

## 5. 首日战果：7 剧本捕获 5 个真 bug（全部已修+回归全绿）

### P0（最重要）：截断→重入队引擎不可达，真实截断被误判 dead_session

- **现象**：solve3 首跑，fake 按剧本产出教科书截断 export
  （rc=1360c/msg=0/comp=25000），被判 `dead_session` 进 failed 队列。
- **根因**：sweep 里 devin 退出→无proof→`is_completed`（截断export必返
  False）→ **dead 分支抢占**；`is_truncated` 只在"已完成"之后才被咨询
  ——截断分支结构性不可达。
- **生产实证**：生产唯一的 dead_session run
  `p27-full-deepmath_103k_00004712`，用生产自己的 is_truncated 重判其
  export=**TRUNCATED**（rc=70632c/msg=0/comp=25000）。生产 rounds_log
  全部 299 条均为 completed 条目、零 truncated 条目——多轮续传引擎
  从未真正执行过（5957 prepared 堆积尚未触发）。
- **修复**：截断判定提前到 dead 之前（comp False→先 is_truncated→
  trunc 则走重入队/TRUNCATED_AT_MAX，都不满足才 dead）。
- **影响**：本系统核心使命（判定"截断vs方向错误"）的截断半边此前完全
  失效。**生产 launcher 重启加载新代码后生效**；4712 该 run
  retry_eligible=True，可人工置回 prepared 重跑。

### P1：主循环退出条件漏 handover_pending

- **现象**：solve3 首跑 launcher 3 秒即退出，题晾在 handover 生成中。
- **根因**：`if not running and pending_count(r)==0: break` 不看
  handover_pending；should_stop 分支同病。
- **生产为何没炸**：队列常年有垫底题。排空到最后一题时同样发生（题被晾、
  重启后多跑一轮）。已修（两处都加 handover_pending）。

### P1：round 编号 off-by-one，R2 被重跑一次

- **现象**：修复 P0 后 rounds_log=[2,2,3]、launch 3 次（期望 [1,2,3]、
  2 次）——多耗一次 handover+solve，且 round2 traj 目录被二次启动覆盖。
- **根因**：`current_round = len(rounds_log)+1`，但 round-1（seed 重判）
  不往 rounds_log 补条目。
- **修复**：round-1 precheck 处补录条目（顺带让 round 1 历史在 DB 完整
  可见）。修复后轮序 [1,2,3] ✅。

### P2×2：终态不进行为流水黑匣子

- TRUNCATED_AT_MAX 两处不写 `run_completed`；unknown_state/rate_limit/
  timeout/stall 四处 failed 终态不写 `run_failed`。016 建黑匣子的本意是
  全过程可审计——终态恰是最该记的。已全部补上。

（另有 sim 自身 bug 一枚：断言层 flow 过滤只认 batch_id 字段，漏掉不带
该字段的事件——已改 run_key 前缀兜底。）

## 6. 边界：sim 不测什么

- devin cli 真实智能（剧本是确定性的——"不考虑AI出错"是设计前提）；
- 模型截断的真实形态分布（fake 只造教科书式截断；真实 export 的边角
  形态靠判定审计+生产回归测试覆盖）；
- Pipe 1-3（legacy）——机制可移植（换 COLLECTION/前缀/命令注入点），
  复活时按 017 模式接。
