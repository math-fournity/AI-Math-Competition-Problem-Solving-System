### 5.1 5 并发决策依据溯源

**结论：5 并发是我自己拍脑袋设的，没有依据。**

溯源链：
1. `src/proof_audit_config.py:42` — `AUDIT_DEFAULT_CONCURRENCY = 5`，注释"审计任务比解题快——只读 proof 不解题"
2. 这个数字照搬了续传系统 `src/continuation_config.py:75` — `DEFAULT_CONCURRENCY = 5`
3. `dev-docs/029:550` 写了 `--concurrency 5`，`dev-docs/029:634` 写了"并发 5，每题约 3 分钟，约 83 分钟完成"
4. 但 029 方案中的 5 也是我写方案时拍的，没有给出推理依据

**用户上下文中没有任何位置提示"用 5 并发"。** 这个数字完全是我自己的决策，没有经过实验、没有经过推理、没有依据。注释"审计任务比解题快"只是事后合理化，不是决策依据。

**问题本质**：违反了全局 AGENTS.md §5 时间估计纪律——"禁止拍脑袋时间估计"。并发数虽然不是时间估计，但同理——没有依据就给数字是瞎说。

### 5.2 门控 docstring 对比分析

**续传系统门控（成熟模式，以 GATE-LAUNCH-SOLVE 为例）**：

```
这个函数做什么：
- 用tmux启动一个devin -p子进程跑续传解题prompt；
- 分配全局session编号（allocate_seq），创建注册表记录（p27_sessions）；
- 清理上一轮的DONE.md标记；建立tmux日志管道。

为什么追踪这个动作：
- 启动即消耗GLM-5.2 API配额、创建session、随后主循环会把run标记为
  running（DB+Redis）——这是系统里最重的状态改变；
- 016事故的失控循环就是"启动"这个动作被高频触发（18分钟上千次），
  Master Agent当时既看不见也拦不住。

放行前Master Agent应检查并论证：
【检查项】（每项含查法+正常值）
1. work_dir存在且属于该run → 查法：ls work_dir + DB run记录的work_dir字段比对
2. 该run无活跃session → 查法：find_active_session(db,run_key,pid)返回None
3. 并发槽空闲 → 查法：len(running)+len(handover_pending)<concurrency
4. prompt内容合理 → 查法：head prompt_file，确认题目文本+上轮reasoning/HANDOVER

【论证依据——放行/不放行判定】
可放行：1✓+2✓+3✓+4✓。理由：系统最重动作的所有前置条件满足——产物归属正确、
   无重复启动(016 P0-1)、并发不超限(016根因)、输入完整。启动不会产生失控循环
不可放行：2✗(有活跃session)→重复启动=016失控循环直接原因；
   3✗(并发满)→超并发=016"设1跑6"直接原因；4✗(prompt空)→devin立即失败=浪费配额
```

**成熟模式的 5 个要素**：

| # | 要素 | 作用 | 续传门控有 | 审计门控有 |
|---|---|---|---|---|
| 1 | "这个函数做什么" | 让 Master Agent 知道门控保护的是什么动作 | ✓ | ✓ |
| 2 | "为什么追踪这个动作" | 让 Master Agent 理解门控存在的理由 | ✓ | ✓ |
| 3 | 【检查项】含查法+正常值 | 让 Master Agent 知道查什么、怎么查、正常值是什么 | ✓ | △（查法不够具体） |
| 4 | 【论证依据——放行/不放行判定】 | 让 Master Agent 知道检查结果如何转化为放行/不放行决定 | ✓ | ❌ |
| 5 | 历史教训引用 | 让 Master Agent 理解不放行的后果有多严重 | ✓（016事故） | ❌ |

**我写的审计门控（以 GATE-AUDIT-LAUNCH 为例）**：

```
这个函数做什么：
- 用 tmux 启动一个 devin -p 子进程跑审计 prompt；
- 建立 tmux 日志管道；
- 返回 session_name。

为什么追踪这个动作：
- 启动即消耗 GLM-5.2 API 配额、创建 session；
- 审计是选题池的准入门槛——审计通过=进入选题池，审计失败=排除。

放行前 Master Agent 应检查：
1. 待审计的 proof.md 存在且非空 → 查法：ls work_dir/proof.txt + wc -c > 0
2. 审计 work_dir 已准备好（AGENTS.md + proof.txt） → 查法：ls work_dir
3. 审计并发未超限 → 查法：paudit:running 的 hlen < concurrency
```

**差距**：
- ❌ 没有【论证依据——放行/不放行判定】——Master Agent 不知道检查结果如何转化为决定
- ❌ 查法不够具体——"ls work_dir/proof.txt"没有说"对比 DB 中 proof_text 字段是否一致"（028 教训：DB 有 proof_text 但硬盘可能没有 proof.md）
- ❌ 没有引用历史教训——028 教训是审计系统最相关的教训（DB completed 但硬盘无 proof）
- ❌ 没有"系统运行到这个位置时，Master Agent 应该如何判断系统运行是否正常"——用户明确要求的

### 5.3 SOP 门控检查模式

### 5.4 SOP 检查的"间接 vs 直接"问题

**028 教训**：DB 显示 138 题 completed，但硬盘上只有 14 题有 proof.md。124 题的 proof.md 在 018 事故中被 rmtree 删除了。

**间接检查**：查 DB/Redis 的状态字段就下结论
- 例：SOP_01 查 DB `status=completed` 就认为题做完了——但硬盘上可能没有 proof.md
- 例：查 Redis `paudit:completed` 的 llen 就认为审计完成了——但 export 文件可能是空的

**直接检查**：直接看到底层（硬盘文件、tmux session 实际状态、export 文件实际内容）
- 例：SOP_02 查 `work_dir/proof.md` 是否存在——这是直接检查
- 例：查 tmux `has-session` 确认 session 真的在——这是直接检查

**现有 SOP 检查的分类**：

| SOP 步骤 | 检查项 | 直接/间接 | 问题 |
|---|---|---|---|
| SOP_01 | 进度（pending/running/completed 数量） | 间接 | 只查 DB/Redis，不验证硬盘 |
| SOP_01 | 进程状态（launcher/monitor 是否活着） | 直接 | tmux has-session |
| SOP_01 | 门闸Y通道 | 间接 | 只查 DB waiting_for 字段 |
| SOP_01 | 行为流水快照 | 直接 | 查 log/flow 文件 |
| SOP_02 | 6个路径字段文件是否存在 | 直接 | ls 文件 |
| SOP_02 | proof.md 质量统计 | 直接 | 读文件内容 |
| SOP_02 | results 集合检查 | 间接 | 只查 DB 集合文档数 |
| SOP_04 | needs_ai_review 的 run | 间接 | 只查 DB 字段 |

**问题**：SOP_01 的进度检查是间接的——只查 DB status 字段，不验证硬盘。028 教训就是这个问题导致的——DB 说 completed 但硬盘没有 proof.md，而 SOP_01 没有发现这个问题，因为 SOP_01 只查 DB 进度。

**SOP_02 是直接检查**——它查文件是否存在。但 SOP_02 不是每轮都跑的（SOP 循环中 SOP_02 是第二步，但实际上很多轮只跑 SOP_01 就跳过了）。

## 六、方案

### 6.1 门控 docstring 认知闭包标准

**标准**：每个 @gated 函数的 docstring 必须包含以下 5 个要素：

```
【门闸: GATE-XXX-YYY】

这个函数做什么：
- <具体动作描述>

为什么追踪这个动作：
- <门控存在的理由>
- <历史教训引用（如有）>

放行前Master Agent应检查并论证：
【检查项】（每项含查法+正常值）
1. <检查项> → 查法：<具体命令/工具> + 正常值=<什么算正常>
2. ...

【论证依据——放行/不放行判定】
可放行：<条件组合>。理由：<为什么放行是安全的>
不可放行：<条件>→<后果>；<条件>→<后果>

【系统正常运行判断】
系统在此门控处正常运行的表现：<描述>
系统在此门控处异常的表现：<描述>，异常时<如何处置>
```

**新增第 5 要素"系统正常运行判断"**——这是用户明确要求的："让未来的AI知道：在这个门控处，系统运行到这个位置的时候，Master Agent应该对系统的运行是否正常，作出怎样的判断"。

### 6.2 补全 4 个审计门控的 docstring

**需要补全的内容**：

#### GATE-AUDIT-LAUNCH

检查项需要补充：

### 6.4 直接检查铁律

**需要写成新的项目级 rule**：`.devin/rules/direct-verification-ironlaw.md`

**核心原则**：所有 SOP 检查——无论是脚本化的检查还是使用了 AI 智能的检查——都必须是"直接"的，必须直接看到底层（硬盘文件、tmux session 实际状态、export 文件实际内容），而不是看到 Redis 和数据库就放心了。

**判定标准**：

| 检查类型 | 间接（禁止） | 直接（要求） |
|---|---|---|
| 题目完成状态 | 查 DB status=completed | + ls proof.md 存在 + grep boxed proof.md |
| 审计完成状态 | 查 DB audit_status=PASS | + 读 export 文件确认有 XML 块 |
| 进程存活 | 查 DB session status=running | + tmux has-session 直接验证 |
| 队列状态 | 查 DB run status=prepared | + Redis ZCARD paudit:pending 直接验证 |
| 审计结果 | 查 DB audit_passed=True | + 读 export XML + 读 proof.txt 交叉验证 |

**028 教训引用**：DB 显示 138 题 completed 但硬盘只有 14 题有 proof.md——如果 SOP 检查是"直接"的（不只查 DB status，还查硬盘 proof.md），这个问题在 018 事故后第一次 SOP 检查时就会被发现，而不是等到 027 报告才发现。
