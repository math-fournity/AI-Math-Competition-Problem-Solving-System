## 三、全局铁律（每个工作包都适用，违反=审计不通过）

1. **git 显式路径 add**——禁止 `git add -A` / `.` / `-u`
2. **改代码必须同步更新第一级文档**（docs/architecture / docs/specs / docs/sop/
   SYSTEM_CLOSURE.md）——各 WP 文档的"文档同步"节列了具体清单
3. **绝不 kill 无 DONE.md 的 session**（dead_session 判定分支是唯一例外）
4. **禁止 inline 脚本**——超过 3 行的逻辑写成文件放 scripts/
5. **人话铁律**——文档/注释/commit message 用人话
6. **DB-文件双向可追溯 / 痕迹保留**——操作写 WORKLOG.md，alert 入 ArangoDB
7. **改调度/判定逻辑后跑 sim 发布门禁**（src/sim；涉及 launcher 主循环的 WP-H/J/K/L
   注意——各 WP 文档写了替代验证方案）
8. **禁止代码写死并发数**——WP-G 的核心内容；其他 WP 不得引入新的并发常量
9. **适度依赖 Master Agent 介入**——可靠判定（确定性函数可单测）进代码；语义判断
   标"待人工"+alert。边界判据："能否写成确定性函数并单测覆盖？"
10. **解题运行结果资产保留**——任何 round 的产出（export/proof/prompt/HANDOVER/
    tmux log）不得删除，唯一例外见 WP-S 的 partial proof 归档后删除逻辑
11. **py_compile 每个改动的 .py**；测试脚本放 scripts/test_*.py（先例：
    scripts/test_016_step_gate.py）
12. **判断系统状态必须直接查证**（硬盘文件/tmux/session.db），不能只看 DB/Redis——
    这正是本批工作包要修的问题，执行过程自己先要做到

```

6. 填"验收 checklist"（逐项勾选+贴验证输出）
7. 写执行记录 + 填总控状态表 + git commit（显式路径）
8. 汇报：本 WP 完成、验收结果、下一 WP 是什么
```

## 六、设计者留给审计的话（执行 AI 也应读——这是验收标准的精神）

这批工作包的设计遵循三条用户级洞察（030~036 链的收敛结论）：

1. **直接检查**——所有 SOP/监控检查必须看到最底层（028 教训：DB 说 completed 但硬盘
   没有 proof.md）。本批工作包多处要求"查 DB + 查文件交叉验证"。
2. **适度依赖 Master Agent**——代码只做可靠判定（确定性模式匹配/超时/存在性），
   不可靠的标记待人工（PARSE_ERROR 语义、C7-C9 复核）。
3. **资产保留**——每个 round 的所有产出是资产（包括失败的），partial proof 也要归档。

审计将按每个 WP 文档的"验收 checklist"逐项核对，并额外检查：有没有做文档没让做的
事（scope 蔓延）、有没有违反 §三全局铁律、commit 是否干净（一个 WP 一个或少数几个
逻辑 commit、显式路径）。
