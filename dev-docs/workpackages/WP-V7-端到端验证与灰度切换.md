## 3. 灰度阶梯（框架——🔶 门槛值以 049 为准）

```
第 0 级（端到端回归）：sim 全剧本（7+2+down 场景）+ 双 launcher 各 1 题真实验证
  ——V4/V5 已各做过单题，本级是 V6 适配后的复验（检查体系在环）
第 1 级（单题灰度）：opencode_acp 跑 1 道续传题（含截断续传轮——多轮场景首次真实）
  门槛：全链产物完整+判定正确+SOP 检查无双后端误报
第 2 级（小批量）：10 题（含 2 道审计）——判定正确率对照 047 基线；静默窗口误判率
  （组装/完成检测的错判计数）；spin 检测无误报
第 3 级（中批量）：50 题（🔶 按 049；或按用户当期进度需求定规模）
  门槛：无系统性异常（错误率不随量放大）；通知日志资产完整率 100%
切换执行（前置：用户已对 049 决策点 1 拍板"Ox Alpha 作默认"且上述达标）：
  set-backend opencode_acp + 续传批次正式跑 + 首 24h SOP 加密观察（🔶 频率）
回退演练：切换后人为触发一次 down（kill 进程）→ auto_fallback（若启用）或手动
  set-backend devin_acp → 验证 048 场景预期
```

## 4. 任务分解（框架）

1. 第 0-3 级逐级执行，每级产出数据段（判定明细/异常计数/门槛核对）进 050 报告
2. 任一级失败：停下→根因→修复（小修可本包做并记录；结构性问题上报用户，本包按
   "停在 N 级"收尾）
3. 切换执行（若获批）+ 回退演练
4. 050 报告：`dev-docs/050-ACP灰度验证与默认切换报告.md`
5. 最终文档同步：AGENTS.md 启动指令/SYSTEM_CLOSURE 默认后端表述（-ptmux 退役时间
   🔶 按用户决策点 4）

## 5. 禁止事项

- ❌ 门槛是硬的——数据不达标不放量（"差不多"不算过）
- ❌ 默认切换前必须有用户明确拍板记录（引用用户原话/决策点编号）
- ❌ 灰度期间的系统性异常不得"边跑边修不改判"（异常计数真实进报告）
- ❌ 回退演练不做破坏性操作（kill 的是自己起的灰度进程，不碰生产续传批次）
