## 二、ACP 模式调研结果

### 2.1 ACP 是什么

**Agent Client Protocol (ACP)** 是一个开放协议，允许编辑器（IDE）与 AI agent 之间通过 JSON-RPC 2.0 over stdio 通信。

Devin CLI 支持 ACP 模式：
```bash
devin acp                    # 启动为 ACP server
devin acp --model opus       # 指定模型
```

**来源**：
- 官方文档：https://docs.devin.ai/cli/reference/commands#devin-acp
- 协议规范：https://agentclientprotocol.com/protocol/v2/overview
- 已被 Zed / JetBrains / Xcode 等编辑器集成

### 2.2 ACP 的通信模型

ACP 是 JSON-RPC 2.0 over stdio——Devin 作为 subprocess 运行，通过 stdin/stdout 与 client（我们的 launcher）交换结构化 JSON 消息。

**消息流**（官方文档）：
```
Client → Agent: initialize              # 建立连接、协商能力
Client → Agent: auth/login              # 认证（如需要）
Client → Agent: session/new             # 创建新 session
Client → Agent: session/prompt          # 发送用户消息（题目）
Agent → Client: session/prompt response # 确认接受 prompt
Agent → Client: session/update (各种)   # 实时推送状态和内容
Client → Agent: session/cancel          # 取消（如需要）
Agent → Client: state_update: idle      # 工作完成
```

### 2.3 ACP 的关键信号——session/update 通知

这是 ACP 的核心优势：**Agent 通过 `session/update` 通知实时推送状态和内容**，不需要轮询或快照对比。

`session/update` 通知的变体（v2 协议）：

| 通知变体 | 含义 | 对检测的价值 |
|---|---|---|
| `state_update: running` | AI 开始工作 | **开始计时** |
| `agent_thought_chunk` | **thinking 内容流式更新** | **thinking spin 期间持续推送**——核心信号 |
| `agent_message_chunk` | message 内容流式更新 | AI 输出文本 |
| `agent_thought` | thinking 整条消息 upsert | thinking 完整内容 |
| `agent_message` | message 整条消息 upsert | message 完整内容 |
| `tool_call_update` (status: pending) | 工具调用开始 | AI 在调用工具 |
| `tool_call_update` (status: in_progress) | 工具执行中 | 工具正在执行 |
| `tool_call_update` (status: completed) | 工具调用完成 | 工具执行完毕 |
| `tool_call_content_chunk` | 工具输出流式更新 | 工具输出内容 |
| `plan_update` | 执行计划更新 | AI 的计划 |
| `state_update: requires_action` | 需要权限批准 | 等待权限 |
| `state_update: idle` + `stopReason` | 工作完成 | **结束计时** |

### 2.4 ACP 的 thinking 检测能力

**这是解决 034 §七 核心困难的关键**：

`-p` 模式下 thinking 不落盘、不输出到 pane——ACP 模式下 thinking 通过 `agent_thought_chunk` **实时流式推送**。

ACP 协议规范（prompt-lifecycle）明确：
> The Agent can report internal reasoning with the same message-update or chunk patterns. `agent_thought` updates patch fields for the same thought `messageId`; `agent_thought_chunk` updates append new content.

**检测逻辑**：
```
state_update: running 但 5 分钟内无任何 agent_thought_chunk /
agent_message_chunk / tool_call_update = 疑似卡住
```

这比 pipe log 文件大小快照精确得多——能区分：
- thinking spin（有 `agent_thought_chunk`）
- 工具执行中（有 `tool_call_update` status: in_progress）
- 等待权限（`state_update: requires_action`）
- 真卡住（`state_update: running` 但无任何 chunk/update）

### 2.5 ACP 的 tool_call kind 枚举

ACP 协议定义了 tool_call 的 `kind` 字段：

| kind | 含义 |
|---|---|
| `read` | 读取文件/数据 |
| `edit` | 修改文件/内容 |
| `delete` | 删除文件/数据 |
| `move` | 移动/重命名文件 |
| `search` | 搜索信息 |
| `execute` | 运行命令/代码 |
| `think` | **内部推理或规划** |
| `fetch` | 获取外部数据 |
| `other` | 其他（默认） |

注意 `think` kind——这可能是 thinking spin 的另一个信号（如果 devin cli 在 thinking 时发送 `tool_call_update` with kind=think）。

### 2.6 ACP 的权限处理

ACP 有权限请求机制：
```
Agent → Client: session/request_permission   # 请求权限
Agent → Client: state_update: requires_action # 等待权限
Client → Agent: Permission response           # 授予/拒绝
Agent → Client: state_update: running         # 恢复运行
```

这对应 `-p` 模式的 `--permission-mode` 参数。ACP 模式下需要 client（launcher）处理权限请求——可以自动批准（对应 `--permission-mode dangerous`）或按规则批准。

### 2.7 Devin CLI ACP 的实际协议版本

**重要发现**：Devin CLI 的 `devin acp` 实际使用 **ACP v1 协议**（`protocolVersion: 1`），不是 v2。

v1 与 v2 的关键差异：
| 特性 | v1 | v2 |
|---|---|---|
| 完成信号 | `session/prompt` response 含 `stopReason` | `state_update: idle` + `stopReason` |
| session 创建 | `session/new`（需 `mcpServers` 字段） | `session/new`（`mcpServers` 可选） |
| session 恢复 | `session/load`（replay 历史） | `session/resume`（不 replay） |
| session 关闭 | `session/close`（需 `sessionCapabilities.close`） | `session/close` |
| tool_call 创建 | `tool_call` 通知（首次）+ `tool_call_update`（后续） | 只有 `tool_call_update`（首次创建） |
| thinking 通知 | `agent_thought_chunk` | `agent_thought_chunk`（相同） |

**Devin CLI ACP 的 sessionCapabilities**：`list` / `delete` / `additionalDirectories`——**没有 `close`**，所以 `session/close` 报 Method not found。关闭 session 用 `session/cancel` + 进程终止。

### 2.8 Devin CLI ACP 的自定义通知

Devin CLI 在标准 ACP 通知之外，还发送自定义通知（`_` 前缀，ACP 协议允许的扩展）：

| 自定义通知 | 含义 |
|---|---|
| `_cognition.ai/thinking_complete` | thinking 阶段结束——AI 完成思考，即将开始输出 message 或调用工具 |
| `_cognition.ai/agent_stopped` | agent 停止——session 结束 |

### 实测发现的关键技术细节

1. **Devin CLI ACP 用 v1 协议**（不是 v2）——`session/new` 必须带 `mcpServers` 字段（空数组也行），`session/prompt` 是 request-response（response 含 `stopReason`）

2. **`session/close` 不被支持**——Devin CLI 的 `sessionCapabilities` 没有 `close`，用 `session/cancel` + 进程终止替代

3. **权限请求的 id 是 string UUID**（不是 number）——response 必须用相同的 id

4. **权限响应格式**：`{outcome: {outcome: "selected", optionId: "allow_once"}}`——不是简单的 `{outcome: "allow"}`

5. **`agent_thought_chunk` 是 thinking 的实时流式推送**——在 thinking 期间持续推送（实测2 中 22 个 chunk 持续约 1 秒，实测3 中 11 个 chunk 持续约 3 秒）

6. **`_cognition.ai/thinking_complete` 是 thinking 结束的精确标记**——在最后一个 `agent_thought_chunk` 之后、第一个 `agent_message_chunk` 或 `tool_call` 之前发送

7. **`tool_call` 通知含 `kind` 字段**——实测看到 `read` 和 `edit`，可用于区分工具类型

8. **`tool_call_update` 的 `status` 流转**：pending → in_progress → completed（或 failed）

### thinking spin 检测逻辑（实测验证后确定）

基于实测结果，thinking spin 检测逻辑可以精确到：

```
检测窗口：5 分钟

state_update: running（或 session/prompt 已发送但未收到 response）
  且 5 分钟内无任何以下信号：
    - agent_thought_chunk（thinking 中）
    - agent_message_chunk（message 输出中）
    - tool_call / tool_call_update（工具调用中）
    - session/request_permission（等待权限中）
    - _cognition.ai/thinking_complete（thinking 刚结束）
  = 疑似卡住 → 创建 alert
```

**这比 pipe log 文件大小快照精确得多**——能区分：
- thinking spin（有 `agent_thought_chunk`）
- 工具执行中（有 `tool_call_update` status: in_progress）
- 等待权限（`session/request_permission`）
- 真卡住（无任何信号）

## 三、方案对比

### 3.1 方案1：ACP 模式（`devin acp`）

**机制**：JSON-RPC over stdio，结构化通知

**能获得的信号**（全部实时）：
- `state_update: running` / `idle` / `requires_action`——精确状态
- `agent_thought_chunk`——thinking 内容流式更新（核心信号）
- `agent_message_chunk`——message 内容流式更新
- `tool_call_update`——工具调用状态（pending/in_progress/completed）
- `plan_update`——执行计划
- `stopReason`——完成原因

**检测逻辑**：
```
state_update: running 但 5 分钟内无任何 agent_thought_chunk /
agent_message_chunk / tool_call_update = 疑似卡住 → 创建 alert
```

**优点**：
- 结构化 JSON-RPC，不需要解析 TUI 渲染的 ANSI 转义码
- thinking 内容通过 `agent_thought_chunk` **实时流式传输**——比 `--export` 的 conversation.json 更好（实时 vs 退出时一次性写入）
- 状态信号精确（running / idle / requires_action）——能区分 thinking / tool 执行 / rate limit / 卡住
- 不需要 tmux（直接 stdio 通信）

**缺点**：
- **改造量大**——需要写 ACP 客户端：
  - `initialize`：协商协议版本和能力
  - `auth/login`：认证（或用 `WINDSURF_API_KEY` 环境变量）
  - `session/new`：创建 session
  - `session/prompt`：发送题目
  - `session/update`：处理所有通知变体（thought/message/tool_call/plan/state）
  - `session/request_permission`：处理权限请求（自动批准或按规则）
  - `session/cancel`：取消运行
  - `session/close`：关闭 session
- 需要替代 `--export`——ACP 模式没有 `--export`，需要从 `session/update` 通知中自己组装 conversation.json（或等 session 结束后用 `session/resume` replay 获取）
- 需要处理权限请求（`session/request_permission`）——对应 `-p` 模式的 `--permission-mode`
- 并发管理需要重写——当前 launcher 用 tmux session 管理并发，ACP 模式下需要用 subprocess + stdio 管理
- `noninteractive-solver-run` rule 需要更新（ACP 是另一种非交互模式）

**改造量估计**：
- ACP 客户端库（initialize/auth/session_new/session_prompt/session_update/session_cancel/session_close）：约 300-500 行
- 权限处理：约 50-100 行
- conversation.json 组装（从 session/update 通知）：约 100-200 行
- launcher 改造（替换 tmux session 管理为 subprocess + ACP 客户端）：约 200-300 行
- 总计：约 650-1100 行新代码 + 现有 launcher 大幅修改

### 3.2 方案2：交互模式（去掉 `-p`）

**机制**：TUI 渲染到 tmux pane，`tmux pipe-pane` 实时捕获

**能获得的信号**：
- pipe log 文件大小增长——TUI 在渲染（含 "Thinking ·" 状态标记）
- pipe log 文件大小不增长——TUI 无渲染（卡住）

**检测逻辑**：
```
pipe log 5 分钟不增长 = 疑似卡住 → 创建 alert
```

**优点**：
- **改造量极小**——只去掉 `-p`，`--prompt-file` / `--export` / `--model` 等都不变
- `--export` 仍然在退出时写入 conversation.json（不变）
- 现有 launcher 代码几乎不用改（只改 devin_cmd 字符串，去掉 `-p`）
- tmux session 管理不变

**缺点**：
- pipe log 内容是 TUI 渲染的 ANSI 转义码——很乱，需要清理才能检测 "Thinking" 标记
- 信号质量低——只能检测"pipe log 是否增长"，不能区分 thinking / tool 执行 / rate limit
- 需要验证交互模式 + `--prompt-file` 是否真的能自动开始处理（不等待用户输入）并自动退出
- 违反 `noninteractive-solver-run` rule（需要更新 rule）
- TUI 渲染会占用更多终端资源（大量 ANSI 转义码写入 pipe log）

**改造量估计**：
- launcher 修改（去掉 `-p`）：约 5 行
- pipe log 检测逻辑（文件大小快照对比）：约 30-50 行
- `noninteractive-solver-run` rule 更新：约 10 行
- 总计：约 45-65 行

### 3.3 方案3：保持 `-p` 模式 + max_runtime 兜底（033 的方案）

**机制**：不试图检测 thinking spin，用 max_runtime 兜底

**检测逻辑**：
```
session 运行超过 max_runtime（如 600s）= 超时 → kill
```

**优点**：
- **零改造**——033 的 WP-J/WP-K 已经包含 max_runtime 兜底
- 符合"适度依赖 Master Agent"原则——Master Agent 通过 SOP 检查发现异常

**缺点**：
- 无法在 max_runtime 之前发现问题——一个卡住的 session 要等到 600s 才被 kill
- 浪费时间——如果 AI 在第 10 秒就卡住了，要等 590 秒才被处理
- 无法区分"正常 thinking 时间长"和"卡住了"——可能误 kill 正在长时间思考的 AI

## 四、推荐方案

## 五、ACP 的额外价值（超出 thinking 检测）

ACP 模式除了解决 thinking 检测问题，还有以下额外价值：

### 5.1 实时 trajectory 采集

当前系统依赖 `--export` 在 devin cli 退出时一次性写入 conversation.json。ACP 模式下，`session/update` 通知实时推送所有内容（thought/message/tool_call/plan），可以：
- **实时落盘** trajectory——不需要等退出
- **实时分析** AI 行为——Master Agent 可以在 AI 工作过程中就发现问题
- **实时干预**——如果 AI 走偏，可以通过 `session/cancel` 及时取消

### 5.2 权限控制

ACP 的 `session/request_permission` 机制比 `-p` 模式的 `--permission-mode` 更精细：
- `-p` 模式：全局设置（dangerous / auto / accept-edits / smart）
- ACP 模式：每个工具调用单独请求权限——可以按工具类型/参数决定是否批准

### 5.3 session 管理

ACP 的 `session/new` / `session/resume` / `session/list` / `session/close` 提供了结构化的 session 管理——比 tmux session 更可靠（tmux session 可能因 server crash 丢失）。

### 5.4 多 session 并发

ACP 模式下，一个 `devin acp` 进程可以管理多个 session（通过 `session/new` 创建）。当前系统每个题目一个 tmux session——ACP 模式下可以用一个 ACP server 管理所有题目的 session，减少进程数。
